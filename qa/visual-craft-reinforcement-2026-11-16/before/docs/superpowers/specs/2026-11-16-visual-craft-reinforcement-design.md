## 6. 검증 설계

1. **참조 갭과 행동 갭을 분리**:실제 기존 파일/heading과 retrieval 결과를 남긴다. 기존 참조가 이미 해당 선택법/예시까지 갖추면 재사용한다. 없는 예시의 부재를 창작 능력 실패로 바꾸지 않는다.
2. **편집 전 기준선**:아래5개 과제를 fresh context에서 현재 오너로 수행. 각 산출물의 실제 내용·선택·미확인을 보존한다. 기존5/5 통과 전례를 고려해 실패를 유도/위조하지 않는다.
3. **편집 후 같은5개 적용**:관련 참조만 통해 실제 예시를 산출하고 전부 사람이 읽는다. 새로운 문구를 되풀이한 것만으로 통과하지 않는다.
4. **문구 강제/새 필수 행동을 도입할 경우만** 그 실패 유형을 별도 대조 microtest5회 이상/variant로 확인한다. 이 설계의 기본은 조건부 reference/technique이며 새 강제 규칙을 만들지 않는다.
5. **설치/회귀**:기존 installer/file-link 검사, sync 테스트, version check, pytest 전체와 diff/보존 검사를 실행한다. 문장 포함 여부를 검사하는 가짜 품질 테스트는 추가하지 않는다.
6. **독립 최종검수1명**:요구/기존 오너 보존/실제10개 답안/근거 상태/선택 조건을 함께 검수한다. 관객 감정·미디어 성공·통계적 개선의 승인이 아니다.

V1–V3가 채택되면 해당 전/중/후 또는 분업이 실제로 포함된 짧은 적용 사례를 별도로 검수한다. 근거가 보류된 후보를 적용 성공으로 계상하지 않는다.

## 7. 성공·실패·권한

성공:8묶음 각각이 `재사용/참조·예시 보강/미채택 사유`로 추적되고, 새 예시가 기존 슬롯에 인계되며, 일반 대사/무성/비인간/비서사 범위를 보존한다. V1–V3는 근거/보류 상태가 명확하다. 실제 설치 경로에서 파일·참조·버전이 일치하고 독립 검수의 Important/Critical 미해결이 없다.

유료/외부 호출·생성·업로드·게시·패키지 설치·Git commit/merge/push/파괴 작업은 범위 밖이다. 원본은 읽기 전용이다. 기존 사용자 미커밋 변경, 특히09 편집 템플릿·26 연속성·storyboard-contract와 진행 중ad-rofan/continuity 문서를 보존한다. 이번 과제의 수정 때문에26 등이 정말 필요하면 현재 내용/해시를 먼저 고정하고 국소 추가만 별도 설명한다.

## 8. 실행·승인·배포

권고 실행 방식은 **부모가 순차 직접 구현＋필요한 제한 원본 확인＋fresh 최종 검토자1명**이다. 독립 문서/증거 검토는 허용된 도구로만 수행하고 동시 작업은 읽기 전용에 한정한다. 복잡도만으로 다수 워커를 늘리지 않는다.

사용자가 설계와 작업지시서 범위를 승인한 뒤 구현한다. 작업지시서는 `docs/superpowers/plans/2026-11-16-visual-craft-reinforcement.md`의 초안이다. 실행 전 정확한 source snapshot/보존 해시를 남기고 격리 작업한다. 최종 반영은 변경 파일만 원본 기준 해시가 여전히 일치할 때 수행한다. 실행 중 원본이 바뀌면 중단해 해당 파일의 병합 결정을 받는다.

최종 예정 버전은2.45/25skills. 실행 전 기준선2.44가 바뀌었으면 현재 버전을 확인해 충돌을 해결한다. 완료 후 기존 sync 스크립트의 dry-run으로 네 루트의 변위/백업 필요를 확인하고 승인 범위의 링크만 동기화한다. 기존 실체 폴더나 예상 밖 링크가 발견되면 자동 덮어쓰지 않는다. 실제 파일 반영과 Pi `/reload`/다른 에이전트 재스캔은 구별해 보고한다.
