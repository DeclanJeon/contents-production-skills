# 스토리보드 타임라인을 실제 영상 요청문으로 전달하기

제작용 보드에서 영상 프롬프트를 만들거나 생성 길이를 변경할 때 필수 적용한다. 발화/청자 반응의 설계 정본은 [스토리보드 계약](../../video-production-assets/references/storyboard-contract.md#대사별-발화-얼굴과-청자-반응)이다. 이 문서는 그 설계를 요청문으로 옮기는 절차이며 새 프로젝트 스키마·승인 원장·공급자 API가 아니다.

## 1. 길이보다 먼저 고정할 것

현재 보드의 버전과 전체 scene/shot/beat/panel/speech/audio cue ID를 읽는다. 시간순으로 설계된 발화 화면, 중요한 반응, 손/소품 인서트, 정보 공개와 정착 구간을 추출한다. 화면 밖 화자·청자 유지·동일 프레임 안의 반응·의도적인 유보도 보드 그대로 전달하며 발화마다 별도 얼굴 컷을 추가하지 않는다. 각 행은 다음 정보를 유지한다.

| 기존 인계에 기록할 항목 | 내용 |
|---|---|
| 출처 | 보드 버전, scene/shot/beat/panel ID, 실제 이미지 asset/file/hash 또는 미생성 |
| 시간 | 전체 편집 구간, shot-local 구간, 생성 작업과 그 generation-local 구간, seconds 또는 frame/FPS 기준 |
| 화면 | 발화/반응/인서트 기능, 가시 인물, 샷 크기·축·시선, 시작→정점→끝 상태 |
| 연기 | 연결 발화 ID, 화자·청자, 반응 계기와 시작·정점·정착, 눈/입/고개/몸의 관측 가능한 변화 |
| 음성 | 정확한 원문·화자·발화 구간, 화면 안/밖, 립싱크 적용 대상, 침묵·환경음·음향 cue |
| 연결 | 손/소품 점유·방향·공개/유보, 직전 끝과 다음 시작, 실제 입력 슬롯 |
| 제출 대응 | 위 구간을 구현하는 실제 최종 요청문 문장과 HARD_CONTROL / SOFT_PROMPT / UNSUPPORTED / UNVERIFIED |

보드에 필수 반응이나 정점이 없으면 먼저 해당 보드를 보완하고 현재 버전으로 연결한다. 프롬프트에서 잠긴 대사를 몰래 고치거나 새 반응을 추가해 기존 보드를 소비했다고 표시하지 않는다. 문서 경로나 “첨부 콘티를 따르라”는 문장만으로 실제 소비를 대신하지 않는다.

## 2. 생성 길이에 맞춰 묶고 시간을 변환하기

1. 선택한 실행자의 현재 길이·입력·컷/카메라·네이티브 음성 지원을 확인한다. 5/10/20/30초는 예시일 뿐 고정 길이·최대 길이·현재 모델 지원을 뜻하지 않는다.
2. 생성 작업의 수와 내부 샷/프레이밍 구간 수를 분리한다. 기존 컷 경계와 반응을 보존한 채 지원 길이에 맞춰 묶는다. 긴 생성 작업도 내부 컷별 명세를 모두 가진다. 짧은 생성 작업도 필요한 발화·반응을 생략하지 않는다.
3. 한 작업이 최종 편집의 `[G0,G1)`을 담당하고 앞 핸들이 `H`초면, 1배속에서 `generation-local = global - G0 + H`, `shot-local = global - shot_start`다. 앞뒤 핸들이 없으면 `H=0`. 생성 길이 `D = 앞 핸들 + (G1-G0) + 뒤 핸들`이며 채택 source in/out도 기록한다. 서로 다른 시간 basis를 같은 타임스탬프로 오인하지 않는다.
4. 각 행을 해당 작업의 로컬 시간으로 옮긴다. 필요한 구간 전체가 `[0,D)` 안에 있고 컷 경계·순서·발화 길이·반응 지연·공개 시점이 보드와 일치하는지 대조한다. 프레임 기준은 FPS와 끝 프레임을 명시한다. 보드나 실제 음성이 추정이면 그 상태를 유지한다.
5. 남는 시간에는 승인된 정착/침묵/편집 핸들의 대상과 길이를 지정한다. 빈 시간을 채우려고 대사를 반복하거나 반응을 늘이고, 영상 길이에 맞춰 전체 비트 시간을 비례 축소하지 않는다. 길이가 부족하면 보드의 인과·호흡을 지키는 추가 분할/길이 변경을 제안하고 해당 실행·비용 범위를 다시 확인한다.
6. 작업 경계는 문장·반응 정점·접촉/소유권 전환을 가급적 끊지 않는 곳으로 잡는다. 필수 상태 중간을 자르면 경계용 상태/패널·음성 연속·채택 in/out을 설계한다. 시작/끝 이미지 두 장만으로 중간 컷과 표정까지 통제됐다고 주장하지 않는다.

모델이 시간표/내부 컷을 hard control로 받지 않으면 SOFT_PROMPT로 표시한다. 정확한 컷 타이밍이 필수인데 제어가 불충분하면 개별 샷 생성 후 편집하는 경로를 제안한다. 비용·작업 수·원테이크 형식 변경은 기존 승인 절차를 따르며, 긴 요청문 하나를 보냈다는 이유로 컷별 제작을 완료했다고 보고하지 않는다.

## 3. 실제 제출문으로 직렬화하기

기존 [AI 인계 템플릿](../../video-production-assets/assets/11-ai-handoff-template.md)에 위 대응표와 전체 최종 요청문을 둔다. 대상 실행자의 실제 문법으로 다음을 작성한다.

- 작업 헤더: 보드 버전/소스 ID, 전체 담당 구간과 생성 길이, 원테이크/컷 편집 형식, 참조 입력의 실제 역할과 시작/끝 상태.
- VISUAL: **모든 내부 컷/프레이밍 구간**의 로컬 시작/끝, 화면 대상·크기·축, 행동/반응의 계기·정점·정착, 소품 상태와 다음 컷 연결. 같은 순서로 보드의 각 행을 풀어 쓴다.
- AUDIO: 같은 로컬 시간 기준의 원문·화자·발화/침묵·cue·화면 안/밖을 별도 구획에 쓴다. 네이티브 음성을 쓰면 같은 요청문에 포함하고 별도 음성 생성을 자동 추가하지 않는다.
- 현재 지원 API 필드에는 실제 길이·해상도·화면비 등을 지정한다. 자연어 시간표나 패널 ID는 존재하지 않는 API 제어 필드를 만들지 않는다.

제출 전 보드→대응표→**실제로 보낼 전체 본문/파라미터/첨부**를 역대조한다. 보드가 요구한 발화 화면/중요 반응의 누락, 원문·화자 변경, 반응의 계기 소실, 컷 합침, 공개/손 점유 순서 역전, 타임라인 충돌은 해당 ID/구간의 FIX이며 제출을 막는다. 보드의 같은 프레임 안 반응이나 화면 밖 발화는 별도 얼굴 컷이 없다는 이유로 실패시키지 않는다. 요약문이나 가독성 없는 와이드로 필요한 반응을 지운 경우는 FIX다. 실제 요청문은 기존 history/요청 스냅샷에 보존한다.

## 4. 같은 30초 보드를 5/10/20/30초로 묶는 예시

아래는 이미 교차 편집을 선택한 가상의 텍스트 설계 예시다. 실제 이미지·음성·지원 모델·생성 결과나 완결된 제작 패키지가 아니다. 모든 행은 같은 S01 안에 있고, P01→P02 등의 패널은 시작→반응 정점/끝을 나타낸다. 이 예제의 컷을 길이 변환 중 합치지 않는다. 2초 발화+3초 반응의 반복은 주소 변환을 설명하기 위한 배분이며 권장 리듬이나 발화별 컷 공식이 아니다. 다른 보드의 투샷·청자 유지·원테이크도 그 설계대로 변환한다.

| global 초 | shot / panel | 기능과 화면 | 발화 또는 관측 가능한 전환 |
|---|---|---|---|
| 60–62 | SH01 / P01→P02 | A 발화 CU | D01 A: “문 열었어?” 문→B로 시선 |
| 62–65 | SH02 / P03→P04 | B 무언 반응 CU | D01을 듣고 눈썹이 올라감→문을 봄→입을 다문 채 정착 |
| 65–67 | SH03 / P05→P06 | B 발화 CU | D02 B: “난 열쇠가 없는데.” |
| 67–70 | SH04 / P07→P08 | A 무언 반응 CU | D02를 듣고 웃음 멎음→B와 문을 번갈아 봄 |
| 70–72 | SH05 / P09→P10 | A 발화 MCU | D03 A: “밖을 봐.” |
| 72–75 | SH06 / P11→P12 | B 무언 반응 CU | D03 뒤 문밖을 확인→눈을 가늘게 뜸→정착 |
| 75–77 | SH07 / P13→P14 | B 발화 MCU | D04 B: “아무도 없어.” |
| 77–80 | SH08 / P15→P16 | A 무언 반응 CU | D04 뒤 어깨 긴장→한숨→정착 |
| 80–82 | SH09 / P17→P18 | A 발화 CU | D05 A: “열쇠는?” |
| 82–85 | SH10 / P19→P20 | B 무언 반응 CU | D05 뒤 A의 손을 봄→한쪽 눈썹을 올림 |
| 85–87 | SH11 / P21→P22 | B 발화 CU | D06 B: “네 손에 있잖아.” |
| 87–90 | SH12 / P23→P24 | A 무언 반응 CU | D06 뒤 자기 손을 봄→민망해 입을 다묾→정착 |

| 선택 길이 | 작업별 global 담당 구간 / 소스 샷 | 작업별 로컬 컷 경계 |
|---|---|---|
| 5초 | 60–65 SH01–02; 65–70 SH03–04; 70–75 SH05–06; 75–80 SH07–08; 80–85 SH09–10; 85–90 SH11–12 | 각 작업 0,2,5초 |
| 10초 | 60–70 SH01–04; 70–80 SH05–08; 80–90 SH09–12 | 각 작업 0,2,5,7,10초 |
| 20초 | 60–80 SH01–08; 80–90 SH09–12는 10초 작업 | 첫 작업 0,2,5,7,10,12,15,17,20초; 둘째 0,2,5,7,10초 |
| 30초 | 60–90 SH01–12 | 0,2,5,7,10,12,15,17,20,22,25,27,30초 |

20+10은 실행자가 두 길이를 지원할 때의 예시다. 고정 20초만 지원하면 남은 10초와 승인된 핸들/정착을 구별하거나 다른 묶음을 제안한다. 어떤 경우에도 마지막 두 발화와 반응을 누락하거나 30초 설계를 20초 안으로 압축하지 않는다.

예를 들어 SH10의 global 82–85초는 5/10초 묶음의 마지막 작업에서는 local 2–5초, 20초 묶음의 둘째 작업에서도 local 2–5초, 30초 작업에서는 local 22–25초다. SH10의 shot-local은 모두 0–3초다. 소스와 감정 변화는 같고 작업 로컬 주소만 달라진다.

5초 첫 작업의 실제 제출문 모양은 다음과 같다. 이 자연어 예시는 특정 API의 hard control 문법이 아니다.

```text
SOURCE: board vX, S01, SH01/P01-P02 + SH02/P03-P04.
GLOBAL: [60,65). GENERATION: 5s. HANDLES: 0. FORMAT: two edited shots.
VISUAL:
[0.0,2.0) SH01: A close-up, speaking toward B. Eyes move from the door to B.
[2.0,5.0) CUT to SH02: B close-up, silently reacting to D01.
  [2.0,2.5) Brows rise on hearing the question.
  [2.5,4.0) Eyes turn toward the door; reaction peaks.
  [4.0,5.0) Settle with lips closed, ready for the next shot.
AUDIO:
[0.0,2.0) D01, A only: "문 열었어?"
[2.0,5.0) Room tone; B is silent. No repeated question.
```

10/20/30초 작업도 표에 배정된 **모든 소스 행**을 이 형태로 직렬화한다. 긴 길이에 맞춘다는 이유로 헤더·첫끝 이미지와 “두 사람이 대화한다”만 남기지 않는다.

## 5. 인계 완료와 실제 검수

인계는 모든 소스 행이 최종 요청문의 구간/문장에 대응하고, 범위·컷·발화·반응·상태가 역대조될 때 완료다. 텍스트 예제나 표 채움은 실제 결과 검수가 아니다.

실제 생성/편집 검수는 [생성 영상 QA](../../video-production-assets/references/21-generated-video-qa-retry.md#대사-반응과-보드-타임라인-대조)가 소유한다. 작업 로컬 시간과 최종 편집 global 시간을 함께 써서 의도와 관측을 비교한다. 네이티브 음성도 실제 청취로 원문·화자·명료성·립싱크를 확인하며, 원문 프롬프트와 오디오 트랙 존재를 발화 성공의 증거로 쓰지 않는다. 지원/청취/재생 도구가 없어 검사하지 못한 항목은 미검증으로 남긴다.
