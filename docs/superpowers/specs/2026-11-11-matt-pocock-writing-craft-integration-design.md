## 1. 목적과 성공 기준

소재 탐색, 비트 구성, 발화 원고 편집에서 유효한 원리를 기존 오너에 통합한다. 핵심 목표는 다음 세 가지다.

1. 자료가 충분하지 않은 탐색과, 고정된 자료를 구성하는 집필을 구별한다.
2. 시청자가 아직 이해하지 못한 개념을 전제로 설명하는 비트를 발견하고 수리한다.
3. 각 원고 블록의 기능과 연결을 점검하면서 근거·사용자 수정·기존 제작 계약을 보존한다.

실행 결과의 합격 조건은 §10의 시나리오로 확인한다. 조회수·유지율·전환율 향상이나 토큰 절감은 이 설계의 검증된 효과가 아니다.

### 비목표와 피해야 할 결과

- 39개 외부 스킬을 패키지 manifest에 추가하거나 새 집필 총괄을 만들지 않는다.
- 범용 블로그·SNS 캡션·비영상 제작 패키지로 범위를 넓히지 않는다.
- 모든 원고에 인터뷰, 후보 목록, 문단별 승인, 새 파일·원장을 강제하지 않는다.
- 사실 검증, 수요 검증, 권리 확인, 음성 잠금, 스토리보드·공간 검증을 집필 기법으로 대체하지 않는다.
- 이번 작업은 설계문서 추가뿐이다. 스킬 수정·배포·전역 동기화·생성·게시·Git 커밋/푸시는 포함하지 않는다.

## 3. 접근 방식과 권장안

| 방식 | 장점 | 비용·문제 | 판단 |
|---|---|---|---|
| A. 외부 `writing-*` 스킬 직접 호출 | 원본과의 거리가 작고 독립 사용 가능 | 설치 여부·하네스 의존, 원본의 문단별 선택·직접 저장이 기존 계약과 충돌 | 개인 작업의 명시적 호출용으로만 유지 |

## 6. 실행 계약

### 6.1 진입과 상호작용

현재 요청, 공급된 자료, 고정 사실, 선택 상태와 상호작용 모드를 먼저 재사용한다.

- **탐색:** 관찰/일화/자료가 흩어져 있고 구조가 미정일 때만 재료를 넓힌다. 주제가 이미 정해졌으면 주제를 다시 고르지 않는다. 자료가 필요한 질문은 기존 조사 오너로 연결한다.
- **구성:** 자료가 주어졌거나 탐색이 끝났으면 그 자료를 입력으로 고정하고 전개를 만든다. 필요한 근거가 없으면 결손을 명시하고, 허용된 추가 조사·주장 축소·해당 부분 보류 중 선택한다. 상상으로 메우지 않는다.
- **다듬기:** 기존 원고가 있으면 요청된 수정 범위 안에서 기능·전환·발화성을 검토한다. 고정된 끝맺음·사실·인물·no-CTA 조건을 보존한다.

기존 Collaborative 모드에서도 모든 비트에서 멈추지 않는다. 질문은 다음 세 종류로 구분하고 이미 받은 답을 재사용한다.

- **창작 선택:** 다단계 작업은 해당 기존 체크포인트에서 해결한다. 단독 산출물은 결과를 실질적으로 바꾸는 미정 선택만 그 작업 안에서 확인하며 전체 프로젝트 인터뷰를 열지 않는다.
- **필수 입력 누락·제약 충돌:** 자료 조사로 해결할 사실은 먼저 기존 조사 경로를 확인한다. 그래도 유효한 결과를 만들 수 없으면 영향받는 입력/충돌과 필요한 결정만 묻고 해당 부분을 보류한다. 별도 체크포인트가 없는 단독 작업과 One pass에서도 이 확인은 허용된다. 독립적으로 진행 가능한 부분은 계속한다.
- **선택적 세부사항:** 되돌릴 수 있는 가정을 표시하고 진행한다. 질문을 만들기 위해 선택지를 늘리지 않는다.

**명시적인 문단/비트별 공동 집필 요청**이 있을 때만 순차 후보·선택 루프를 사용한다. 그때는 선택된 블록까지만 확정하고 다음 블록을 미리 확정하지 않는다. One pass에서는 창작 선택을 다시 묻지 않고 요청 초안을 완성하며 제안·가정을 표시한다. 필수 충돌 확인은 One pass의 창작 선택 위임이나 기존 승인값을 초기화하지 않는다. 기본 모드를 이번 기능이 바꾸지 않는다.

### 6.2 이해 기반과 사실 근거는 별개

- **관객 선행지식:** 이 관객이 이미 안다고 사용자/브리프가 제공한 내용 또는 표시된 작업 가정.
- **작품 안에서 소개한 개념:** 앞 비트의 실제 표현으로 이해 기반을 제공한 내용. 낱말 언급만으로 이해됐다고 가정하지 않는다.
- **사실 근거:** 주장의 source_id/위치/한계와 확인 상태. 앞에서 설명했거나 관객이 안다고 해서 검증된 사실이 되지 않는다.

설명 중심 작업에서 각 비트가 무엇을 전제로 하고 무엇을 새로 알게 하는지 확인한다. 선행 개념이 빠졌으면 앞에 구체적 예를 넣거나 순서를 바꾸거나 의존 주장을 줄인다. 다큐·미스터리의 의도적 정보 보류는 오류가 아니다. 현재 장면을 따라갈 최소 정보와 나중에 답할 질문을 구분하고, 스포일러를 앞당기지 않는다.

### 6.3 원고 블록의 완료 조건

각 블록에 대해 다음을 실제 원고 위치로 확인한다.

1. 이 블록의 기능이 무엇이며, 앞 블록과 다른 기여가 있는가?
2. 필요한 개념이 관객 선행지식이나 앞 비트에서 준비됐는가?
3. 도입이 약속한 질문·발견·감정 변화와 어떻게 연결되는가?
4. 사례/근거가 입력 자료 안에 있는가? 없는 것을 사실처럼 추가하지 않았는가?
5. 내레이션은 발화문으로, 화면·출처 지시는 해당 메모로 분리됐는가?

동일 기능 반복은 무조건 삭제하지 않는다. 의도된 리듬·강조·감정 hold는 유지할 이유를 확인한다. 표·목록·인용 같은 원본 article 형식은 집필용 검토 도구이며, 최종 발화문을 기계적으로 표 읽기로 바꾸지 않는다.

### 6.4 저장·버전·인계

- 채팅 전용 작업은 결과를 채팅으로 반환한다. 집필 기법 때문에 파일/프로젝트를 만들지 않는다.
- 원자료는 기본 읽기 전용이다. 원자료 자체 편집을 명시적으로 요청받으면 그 범위만 별도로 따른다.
- 저장이 허용된 단독 작업은 지정 위치를 사용하고, 기존 파일을 바꾸기 직전에 다시 읽어 사용자 수정을 보존한다. 동시 변경이 있으면 재대조하고 충돌하는 부분만 확인한다.
- 조정자가 배정한 워커는 변경 제안·검사·미해결 입력을 반환한다. 원본 스킬의 자동 append나 임시 handoff 저장 지시를 실행하지 않는다.
- 기록형 제작은 기존 artifact 버전과 dependency_versions를 사용한다. 바뀐 입력에 의존하는 원고/보드/음성/편집과 승인만 stale 처리한다.
- 실제 음성·길이 측정·청취가 없으면 시간은 추정이다. 텍스트 이해 순서 검사는 청취/영상 QA가 아니다.

## 7. 산출물 형식: 기존 필드를 유지

신규 JSON 필드·상태 enum·비트 ID 체계·필수 CSV 열을 만들지 않는다.

- 관객 전제는 기존 브리프의 관객·가정 구획에 필요한 만큼 쓴다.
- 이해 순서 검토는 기존 시놉시스의 비트별 목적/변화/다음 비트 연결 설명과 원고 메모에 반영한다. 별도 개념 그래프를 생산 원장으로 만들지 않는다.
- 사실은 [기존 근거 양식](../../../video-production-assets/assets/10-evidence-template.md)의 `claim_id`, `유형`, `source_id/위치`, `한계`, `상태`를 사용한다. 탐색 메모가 검증된 claim으로 자동 승격되지 않는다.
- 문제는 기존 QA의 문서 위치·문제·수정·재검사 기준으로 반환한다. 모든 작업에 ‘이해 기반 표’를 새 필수 산출물로 붙이지 않는다.
- [서사 양식](../../../video-production-assets/assets/02-story-template.md)과 [각본 양식](../../../video-production-assets/assets/03-screenplay-template.md)의 표제·열·ID는 유지한다. 설명 모드의 추가 검토 메모를 넣기 위해 서사 전용 필드를 재명명하지 않는다.

## 8. 완성 예: 설명 순서 수리

**설계 예시이며 역사적 사실·측정 결과가 아니다.** 아래 B01/B02는 예시 내부 라벨이다. 실제 기존 프로젝트에는 그 프로젝트의 ID를 그대로 쓴다.

입력: 초보 관객용 ‘실루엣이란 무엇인가’ 영상 원고. 사용자가 허구의 예시 문장과 이미지 설명을 제공했고, 원고 구조 수정만 요청했다.

문제 원고:

> B01: 이 변화는 실루엣의 변화를 보여줍니다.
> B02: 실루엣은 옷을 입은 몸의 전체 윤곽을 가리킵니다.

문제: 초보 관객이 아직 소개받지 않은 개념으로 첫 관찰을 해석해야 한다.

수정 제안:

> B01: 같은 사람인데, 한쪽 옷은 어깨가 넓고 허리가 잘록해 보여요.
> B02: 이렇게 옷을 입었을 때 생기는 전체 윤곽을 여기서는 ‘실루엣’이라고 부를게요.

기존 각본 양식으로 인계:

- 목적: 눈에 보이는 차이 → 그 차이를 부르는 개념 연결.
- 화면 행동: 사용자가 제공한 두 예시 이미지를 나란히 비교. 실제 이미지가 없으면 시각화 제안/미검증으로 표시.
- 내레이션: 위 수정 제안의 발화문.
- 근거: 사용자가 제공한 예시와 작업용 정의. 별도의 역사·효능·인과 주장 없음.
- 예상 길이와 측정 상태: 미측정. 실제 음성이 없으므로 확정 초/타임코드 없음.
- 검토 결과: 개념 순서는 텍스트에서 수리됨. 실제 시청자 이해, 이미지 가독성, 발화 길이·청취는 미검증.

반례: 전문가 대상이고 ‘실루엣’을 이미 안다는 브리프라면 이 정의를 강제하지 않는다. 미스터리라면 숨겨야 하는 정답을 먼저 설명하지 않고, 장면을 따라가는 데 필요한 관찰만 제공한다.

## 10. 구현 전후 검증 설계

### 10.1 행동 검증: 아직 실행하지 않음

#### 10.1.1 기존 도구 재사용과 실행 유형

[기존 평가 실행기](../../../scripts/run_guide_behavior.py)는 Pi CLI를 단일 `--print` 호출로 실행하고 읽기 전용 도구 목록을 사용한다. 현재 `OWNER`는 G/F 사례만 지원하며 T 사례를 그대로 넣으면 실행할 수 없다. 입력 원문/해시, 실제 응답, 도구·읽기 추적, 소스 fingerprint 기록은 재사용하되 아래 확장은 **향후 구현 범위**로 분리한다.

| 유형 | 대상 | 실행 설계 |
|---|---|---|
| 단일 응답·읽기 전용 | T01–T08, T10a/T10b, T13 | 기존 실행기에 T 사례→기존 오너 경로 매핑을 추가한다. 반복 실행은 별도 출력 디렉터리의 5개 독립 호출로 관리한다. G/F의 기존 동작은 보존한다. |
| 같은 대화의 다회차 | T11, T12 | 별도 테스트 어댑터에서 회차별 메시지·응답·도구 추적을 이어간다. 새 반복마다 fresh context를 사용하되 한 반복의 회차 사이에는 실제 이전 대화를 보존한다. `--no-session --print` 독립 호출을 연결한 것만으로 다회차 검증을 주장하지 않는다. |
| 통제된 파일 경합 | T09 | 임시 fixture의 지정 파일에만 쓰기 가능한 별도 어댑터를 사용한다. 읽기 완료 이벤트 뒤 평가기가 사용자 수정을 삽입하고 최종 바이트/도구 순서를 검사한다. 기존 읽기 전용 실행기의 도구 권한을 전체적으로 넓히지 않는다. |
| 설치·링크·비적용 | T10의 설치 조건 및 §10.2 | 기존 임시 설치 검사를 사용한다. 설치 검증과 모델의 비적용 판단은 별도 결과로 기록한다. |

단일 응답의 오너는 T01=01-brief, T02–T04=시놉시스 craft, T05–T07/T13=03-screenplay, T08=video-production-assets/SKILL.md, T10a/T10b=developing-video-synopses/SKILL.md로 지정한다. 경로는 §2/§5의 기존 파일을 사용한다. 다회차 어댑터는 T11=video-direction, T12=03-screenplay에서 시작하고 T09는 03-screenplay의 저장 계약을 따른다. 신규 공용 참조 자체를 강제로 먼저 읽히지 않아 기존 진입점에서 조건부 참조를 찾는지도 검사한다. 실제 파일의 읽기 성공/범위는 trace로 확인하며 파일명 언급만으로 소비를 인정하지 않는다.

독립 리뷰어 도구의 부재와 CLI 평가 실행 가능 여부는 별개다. 실행 전 현재 CLI·도구 옵션·지정 provider/model의 지원과 인증·예산을 확인한다. 다른 모델을 임의로 대체하거나 승인 없는 유료 평가를 실행하지 않는다. 다회차/파일 어댑터가 없으면 해당 사례를 `INCONCLUSIVE`로 남기며 단일 응답이나 작성자의 독해로 대체하지 않는다. 프롬프트의 읽기 경로 제한을 OS 샌드박스 보장으로 표현하지 않는다. T09는 실제 사용자 파일·프로젝트·전역 스킬에 쓰기 권한이 없는 환경에서만 실행한다.

#### 10.1.2 고정 입력과 보존·수정 기준

아래 따옴표 안 문장은 **평가용 입력 원문**이다. 전부 가상의 작업용 자료이며 외부 사실/실제 제작 결과가 아니다. 입력 원문·아래 공통 접두사·실제 시스템 지침·모든 후속 메시지는 실행 전에 UTF-8 파일로 고정하고 해시를 기록한다. 표의 기대 조건은 평가자 전용이며 모델 입력에 주입하지 않는다. 실행 중 결과를 보고 입력이나 루브릭을 바꾸면 새로운 평가 버전으로 처음부터 다시 비교한다.

공통 접두사: “이번 작업은 영상 기획/원고 텍스트만입니다. 채팅으로 답하고 생성·업로드·게시·외부 변경은 하지 마세요. 제공 자료는 평가용 가정이며 실제 자산을 검사했다고 말하지 마세요.” T09만 ‘채팅으로 답하고’ 대신 ‘허용된 임시 fixture의 원고만 수정하고’를 사용한다.

| 사례 | 고정 입력 원문 | 보존 조건과 관찰 가능한 기대 결과 |

#### 10.1.3 판정 루브릭과 반복·증거 계약

- **PASS:** 해당 사례의 모든 기대 조건과 보존 조건이 실제 응답/도구 추적/파일에서 확인된다. 의역 허용 여부는 각 사례의 ‘그대로’·‘한 문장’·‘ID 유지’ 조건을 따른다. 정확 문자열 조건이 없는 craft 판정은 이유와 응답 위치를 함께 기록한다.
- **FAIL:** 확인 가능한 기대/보존 조건 하나 이상을 위반한다. 출처 날조, 잠금값 변경, 범위 밖 쓰기/실행은 차단 위반이며 다른 성공으로 상쇄하지 않는다.
- **INCONCLUSIVE:** 응답 중단·길이 잘림·실행 오류·필수 trace 누락·미지원 다회차/파일 이벤트·평가자 간 미해결 판정 차이다. 무응답/도구 오류를 craft 실패로 채점하거나 통과 표본으로 교체하지 않는다.
- **SKIPPED:** 사전 승인된 범위 밖 사례만 해당하며 이유를 남긴다. 필수 사례를 SKIPPED하면 전체 통과 판정은 보류한다.

각 고정 입력별로 기존 패키지와 보강 패키지를 **각각 5회** 실행한다. T10a/T10b는 각각 하나의 입력이며 T11/T12의 한 다회차 대화 전체가 한 반복이다. 총 14개 입력 × 두 조건 × 5회 = **140회 사례 실행**이다. T11의 2회차와 T12의 3회차를 합산하면 사용자 메시지에 대한 응답 단계는 총 170회이고, 도구 처리·추론에 따른 실제 provider 호출 수는 더 많을 수 있어 별도 기록한다. 모델·provider·추론 설정·도구·사용자 메시지는 두 조건에서 동일하게 유지하고 순서를 교차한다. 같은 seed를 지원하지 않으면 미지원으로 기록하며 통계적 인과 효과를 주장하지 않는다.

기존 패키지의 미커밋 상태까지 포함한 두 개의 고정 스냅샷을 사용한다. 전체 파일별 해시·실행기 해시·입력/시스템 지침 해시를 보존하고 평가 중 소스 변경을 거부한다. 차이는 승인된 보강 파일뿐이어야 한다. 사례별 오너 경로는 동일하고 해당 조건의 스냅샷 안 참조만 읽는다. 기대 조건/평가 보고서는 모델이 읽을 수 있는 입력에서 제외한다.

구현 대상으로 삼을 결함은 baseline의 5회 중 실제 FAIL이 한 번 이상 관찰된 항목으로 한정한다. 변경 후에는 해당 사례와 모든 회귀 사례에서 **5/5 PASS, 차단 위반 0, INCONCLUSIVE/SKIPPED 0**일 때만 이 평가 세트 통과로 판정한다. baseline 5/5 PASS는 보존 확인이지 개선 성과가 아니다. 개선이 없거나 새 위반이 생기면 문구를 축소하고 새 변경 버전으로 재평가한다. 판정 기준을 결과에 맞춰 완화하지 않는다.

오류 재시도는 실행 전에 승인된 횟수 안에서만 하며 원시 기록을 보존한다. 최대 호출/토큰/비용·재시도 상한은 실제 실행 전 사용자 권한 범위에서 확정한다. 예산이 부족하면 표본 수를 몰래 줄이지 않고 미완료로 보고한다. 도구·모델·어댑터가 미확보인 상태에서 위 140회를 실행 승인받았다고 해석하지 않는다.

증거는 기존 실행기의 `.stdout.jsonl`, `.stderr.txt`, `.response.md`, `.attempt.json`, `metadata.json`, `execution-summary.json` 형식을 우선 재사용한다. 다회차/파일 어댑터는 여기에 실제 회차별 입력·선택·이벤트·최종 파일 해시를 추가하고, 반복별 출력 디렉터리를 분리한다. 별도 평가 보고서는 사례/반복/조건/판정/응답 또는 trace 위치/실패 이유/미검증 범위를 기록한다. 평가 메타데이터는 제작용 project.json 스키마를 바꾸지 않는다. `completed`는 실행 완료일 뿐 PASS가 아니며, 자연스러운 원고와 실제 시청자 이해·음성/영상 품질은 별도 평가다.

### 10.2 구조·설치·회귀 검증: 구현 단계에서 실행

- 변경 전 작업 트리와 실패 baseline을 보존하고 다른 작업자의 변경을 되돌리지 않는다.
- 새 참조의 상대 링크가 소스와 임시 설치 루트에서 모두 유효해야 한다. upstream URL은 출처이지 런타임 필수 입력이 아니다.
- 임시 설치에 공용 참조·provenance·라이선스가 포함되고 외부 matt 스킬 미설치 상태에서도 완결돼야 한다.
- `scripts/test_video_pack_boundary.py`의 설치본 링크/비영상 경계 검사를 포함한다.
- `python scripts/check_versions.py` 및 `python -X utf8 -m pytest -q`를 실행하고 실제 결과를 남긴다. 기존 dirty tree에 따른 실패는 새 변경의 실패와 대조한다.
- 구조 통과는 실제 원고 품질·시청자 이해·음성/영상 QA 통과가 아니다.
- 실제 사용자 스킬 루트에 대한 설치/동기화는 별도 요청 전에는 하지 않는다.

## 11. 단계별 도입과 남겨 둔 구현 판단

1. **설계 수락:** B 방식, 패키지 내부 보강 범위, 비필수/무중복 원칙을 확인한다.
2. **평가 준비와 행동 baseline:** 기존 실행기의 T 매핑 및 다회차/파일 어댑터를 검증하고 §10.1의 고정 입력·루브릭·두 스냅샷·예산을 먼저 확정한다. T01–T13(분리된 T10a/T10b 포함)에서 실제 공백을 확인한다. 필요한 실행 능력·권한이 없으면 해당 단계는 보류한다.
3. **최소 구현:** 실패가 확인된 원리만 공용 참조·기존 포인터에 넣고 출처/라이선스를 함께 제공한다.
4. **재평가·회귀:** 행동 결과와 설치/구조 검사를 구별해 기록한다. 효과가 없거나 침범이 생긴 규칙은 축소한다.
5. **문서·배포 판단:** 실제 결과만 사용 가이드/변경 이력에 기록하고, 별도 승인이 있을 때 설치본 반영을 진행한다.

구현자가 정할 수 있는 사항: 공용 참조의 세부 절 제목, 기존 양식 안 메모의 간결한 표현, 테스트 파일명, 현행 정책에 따른 버전 증분. 바꿀 수 없는 사항: 요청 범위·선택 상태·기존 ID/필드·단일 기록자·측정/근거/실행 승인 경계. 새로운 산출물/스키마/상호작용 기본값이 필요해지면 설계를 다시 검토한다.
