[완전한 스토리보드 계약]의 dynamic scene integration/QA 게이트를 따른다.\r\n- 전체 이미지 기반 패키지와 그 다운스트림에는 [v5.1 프로덕션 무결성](references/contract.md#v51-프로덕션-무결성-look에셋-게이트계보provenance패키지)을 적용한다. 활성 LOOK을 `look_asset_id`로 카메라·Blender 전문 스킬로 인계한다.\r\n4. 애니메이션 계획은 08, 편집·사운드·타이밍은 09, AI 인계는 11을 적용한다. 모든 비트→씬→샷→키패널을 매핑하고 필요한 이미지 슬롯/고유 이미지/시트 수를 계산한 뒤 실제 정지 이미지를 생성·등록·검사한다. 이미지 단독 전체 순서 검수를 대표 이미지나 텍스트 self-check로 대체하지 않는다.\r\n5. 14로 제작 일정·비용·에셋 원장을 작성하고 실제 납품 요청이면 15로 자막·출력 규격을 정한다. 12로 KEEP/FIX/미검증과 수정 사유·방식·추가 준비물·근거 있는 소요시간을 작성하고 승인 범위 안에서 수정→재검수한다. 프리뷰 영상/움직이는 렌더는 별도 승인된 실행 범위 안에서만 수행한다.\r\n6. 실제 산출물별 상태와 수정 의존성을 기록한다. `review.md`와 실제 파일 경로·이미지·검수 결과를 사용자에게 보고하고 검토 대기한다. 해당 버전의 프리프로덕션 수락과 별도 영상 실행 승인을 구분한다.\r\n7. `python scripts/validate_project.py <project.json> --profile plan`으로 ID·시간·참조를 검사한다. 실제 파일 납품은 `--profile delivery --base-dir <프로젝트폴더>`로 추가 검사한다. 이 검사는 감정·연기·미디어 디코딩·실제 영상 품질을 확인하지 않는다.\r\n상세 제작 보드는 `python scripts/validate_storyboard.py <project.json>`을 추가 적용하고 실제 이미지 인계는 `--require-images --base-dir <프로젝트폴더>`로 검사한다. 최대 8패널 시트를 만든 직후 `scripts/split_storyboard.py --sheet <시트> ...`에 모든 시트를 순서대로 지정해 clean 패널·장면 overview를 분리·등록하고 전수 재열기 검수를 수행한다. 정확한 등록/완료 게이트는 [공통 패키지 계약](references/contract.md#전체-프리프로덕션-패키지)을 따른다. 구조/파일 통과는 실제 스토리텔링 품질을 증명하지 않는다.\r\n패키지 납품이 요청되면 `python scripts/package_production.py <project.json> --base-dir <project-root> --output <새-출력> [--zip] [--require-final]`로 v5.1 패키지 트리를 실제 등록 파일로만 조립한다(파생 매니페스트·게이트 보고·`.history` 감사 사본 포함, 기존 출력 덮어쓰기 없음). 잠금 전 패키징은 열린 게이트를 보고하며 `--require-final`은 그 경우 거부한다.\r\n\r\n## 산출물 인계\r\n프로젝트 브리프, 채워진 해당 모듈 에셋, 전체 패키지의 필수 산출물·실제 Markdown/이미지·전체 보드·인물 페르소나/SSOT·참조와 해시를 검사한다. `--base-dir` 필수, 이미지 모드에는 Pillow 필요. 예술성·동일 얼굴·권리·사용자 승인 진위를 인증하지 않는다. plan 성공은 이 준비 완료 판정을 대신하지 않는다.\r\n- delivery: plan 검사에 실제 파일 존재·해시·측정 시간·열린 blocker·납품 검사 기록을 추가한다. `--base-dir`을 프로젝트 폴더로 지정한다. 파일 재생, 디코딩, 음량 측정, 사실의 진위나 동의의 진위는 이 코드가 확인하지 않는다.\r\n- 필수 테이블 scenes/shots/artifacts는 비어 있으면 안 된다. 등장인물이 없는 영상은 characters=[]를 허용한다.\r\n- scene.purpose는 장면 기능, character.locked_traits는 문자열 또는 비어 있지 않은 목록/객체로 기록한다.\r\n- target_duration_s와 shot.start_s/end_s는 fps 기준 프레임 경계에 맞춘다. 초는 실수로 허용하고 반올림 오차를 제한한다.\r\n- shot.source_duration_status: estimated/measured. 계획의 원본 길이는 추정이며 실제 생성/촬영 후 측정한다.\r\n- shot.source_in_s는 선택 테이크의 소스 시작 초, playback_rate는 소스 초/최종 초(기본 1). 배속·슬로모션에서 필요한 소스 길이는 source_in_s+(end_s-start_s)*playback_rate다.\r\n- shot.asset_ids는 asset_registry의 선택된 참조 ID 목록이다. 프롬프트의 경로·룩·의상·소품은 CSV 연속성 원장과 맞춘다.\r\n- artifact.dependencies는 ID 목록이고 dependency_versions는 **정확히 그 ID들**의 {artifact_id: 입력 버전} 객체다. 선언되지 않은 키는 오류다. 현재 산출물은 상위 버전과 일치해야 하고, stale 산출물만 과거 입력 버전을 보존할 수 있다.\r\n- approved artifact는 approval={by, at, evidence}를 기록한다. 승인자·시간·근거는 실제 기록을 사용한다. 생성/검증 산출물에는 asset_ids, verified에는 evidence가 필요하다.\r\n\r\n## 전체 프리프로덕션 패키지\r\n\r\n단일 텍스트/프롬프트 요청은 이 확장을 요구하지 않는다. 전체 이미지 기반 제작은 **시놉 MD, 인물별 페르소나·SSOT MD와 실제 한 장짜리 Identity Sheet A, 통합 기술 콘티 MD, 모든 패널을 이야기 순서로 덮는 합본 스토리보드 이미지 세트(시트당 최대 8패널, 순서 있는 1장 이상)**를 인계한다. 캐릭터 없는 작품은 인물 산출물만 비적용이다. 텍스트 전용 전체 설계는 이미지 제출/파일/지출을 추가하지 않는다.\r\n\r\n- `preproduction={mode:text|image_backed,synopsis_artifact_id,storyboard_artifact_id,storyboard_sheet_artifact_ids,storyboard_split_asset_id}`를 기존 project.json에 둔다. 이미지 모드에는 합본 시트 artifact ID의 **정렬된 배열**이 필수다. 한 장도 배열로 기록하며 기존 단수 선언은 같은 ID의 한 항목 배열로 이전한다. 시놉 type은 synopsis, 보드 type은 storyboard이며 각각 정확히 한 실제 `.md` 에셋을 연결한다.\r\n- 전체 패키지의 각 `characters[]`에는 `persona={role,personality,observable_behavior,speech}`, `ssot_artifact_id`를 둔다. 네 페르소나 값은 구체적인 비지 않은 문자열이며 무대사에는 이유를 적는다. character_sheet artifact는 시놉 입력 ID/버전과 실제 SSOT MD 에셋 하나를 연결한다. 공급된 캐릭터는 원본을 보존하고 시놉 적용 범위의 인계 시트를 버전으로 연결한다.\r\n- 이미지 모드의 `identity_sheet_asset_id`는 kind=character_identity_sheet, entity_type=character, 해당 entity_id의 실제 이미지다. 전신 정면/3·4/측면/후면 + 얼굴 정면/3·4/측면의 7뷰를 한 장에 구성하고 각 뷰의 고정 앵커를 실제 검사한다. 장면 초상 하나는 대체물이 아니다. 해당 에셋의 `source_asset_ids`에는 그 캐릭터 SSOT artifact가 가리키는 실제 Markdown asset ID가 포함돼야 하며, 검사기가 연결을 확인한다. 인물이 등장하는 모든 샷의 asset_ids에 이 정본을 연결한다.\r\n- storyboard artifact는 현재 시놉과 모든 캐릭터 character_sheet의 정확한 버전에 의존한다. 각 샷/패널에 원문·beat/scene/shot/panel/캐릭터·페르소나/SSOT·카메라·시간·실제 이미지 참조를 통합한다. 각 패널은 해당 beat·가시 캐릭터·audio cue·speech ID를 직접 기록한다.\r\n- 합본 `type=storyboard_sheet` artifact는 보드의 현재 버전에 의존하고 `kind=storyboard_sheet` 이미지 에셋 정확히 하나를 연결한다. PNG의 `storyboard_sheet.panel_traceability` metadata와 표시 캡션은 panel별 ID 매핑을 담는다. 입력 시트/crop은 합본 출력의 대체물이 아니다.\r\n- 이미지 모드의 `storyboard_sheet_artifact_ids`는 이야기 순서로 정렬된 `type=storyboard_sheet` artifact 배열이다. **한 시트에는 최대 8개 패널**만 둔다 — 패널 수·정보 밀도·씬 경계로 장수를 정하고 한 장에 욱여넣지 않는다. 각 시트 artifact는 보드의 현재 버전에 의존하고 `kind=storyboard_sheet` 이미지 에셋 정확히 하나를 연결한다. 각 시트 에셋의 `panel_ids`는 자기 구간의 정본 panels 순서이며, 모든 시트를 순서대로 이어 붙이면 정본 전체 순서와 일치한다(누락·중복 없음). 시트가 두 장 이상이면 각 에셋에 `sheet_index`(1부터)·`sheet_count`를 기록한다. `source_asset_ids`는 그 시트 패널의 실제 픽셀 입력(source_sheet_asset_id가 있으면 그 ID, 없으면 image_asset_id)을 같은 순서로 담고 `source_sha256`는 해당 입력 ID→현재 해시 맵이다.\r\n- `render_storyboard_sheet.py <project.json> --base-dir <root> --output 04_STORYBOARDS/sheets/<새.png> [--font <font.ttf>] [--panels-per-sheet 1..8]`는 clean 패널과 외부 촬영 캡션을 순서 있는 PNG 세트로 조립한다. 각 시트의 실제 path/hash/패널·소스 매핑과 동일 traceability PNG metadata를 반환하며 원장을 쓰지 않는다. 총괄이 모든 시트를 등록하고 실제 합본을 연다.\r\n- 합본을 만든 직후 `split_storyboard.py --sheet <프로젝트-relative 시트>`를 이야기 순서로 반복 지정해 장면 overview와 clean 패널을 추출한다. 실제 JSON manifest를 `kind=storyboard_split_manifest`로 등록하고 `preproduction.storyboard_split_asset_id`에 연결한다. 각 추출 이미지도 실제 경로·SHA-256으로 등록한다. manifest의 `file`은 manifest 폴더 기준, `sheet_path`·`sheets[].path`·`band_sources`는 프로젝트 root 기준 상대 경로다. 원본 패널 입력을 추출 이미지로 바꾸지 않는다.\r\n- preproduction/FINAL은 manifest의 주장만 신뢰하지 않는다. 각 panel/scene의 실제 등록 파일·SHA-256, canonical scene/shot/panel, source asset/version/hash 및 asset pins가 서로 일치해야 하며 다른 패널 파일을 alias한 split은 거부한다.\r\n- `package_production.py --require-final`은 명시적인 현재 FINAL 보드, 완료된 이미지 기반 패키지, 정렬된 현재 시트/hash와 일치하는 split manifest, 전체 scene/panel 이미지의 실제 등록을 요구한다. ZIP의 root `project.json`은 휴대 가능한 파생 스냅샷이며 registry 경로가 실제 패키지 파일을 가리킨다. 표준 폴더 경로는 유지하고, 구형 평면 경로는 asset ID를 포함해 충돌 없이 배치한다. CSV manifest는 정본의 파생물이고 모든 실제 패키지 파일을 열거한다.\r\n- ZIP 재개봉은 asset registry 경로와 split 내부 `file`/`sheet_path`/overview source 참조를 같은 relocation map으로 재투영하고 파생 snapshot hash를 갱신한다. 원본 정본은 변경하지 않으며, 실제 복사 byte stream이 등록 지문과 다르면 게시를 중단한다.\r\n- 모든 필수 실제 파일에는 SHA-256을 기록한다. 이미지 디코딩·현재 종속 버전·전체 커버리지·열린 blocker도 검사한다. reviewed/approved인 preproduction_review 또는 approved인 video_execution_plan에는 plan에서도 이 완결 게이트를 자동 적용하며 이미지 모드를 요구한다. 검토는 시놉·보드·합본을 dependency 그래프로 소비해야 한다.\r\n- 누락 상태는 draft/stale로 보존하고 strict preproduction 검사에서는 준비 미완료로 반환한다. 프롬프트·가상 path·planned 에셋·검사 기록만으로 실제 산출물이라고 표시하지 않는다. 구조 통과 뒤에도 캐릭터 7뷰 정체성, 전체 clean 컷 읽힘, 합본 누락/가독성, 장면 내 제품·빛·그림자·반사 통합을 실제 검수하고 사용자 수락을 별도로 받는다.\r\n\r\n\r\n## 실제 파일과 부가 시간표\r\n- asset_registry: {id, kind, version, path, status, sha256}. 실제 path는 프로젝트 폴더 기준 상대 경로를 권장하며 `--base-dir` 검사에서 resolve한 결과가 그 폴더 밖이면 거부한다(절대 경로/..//symlink 포함). planned는 path=null을 허용한다. available/verified는 실제 경로를 갖고 base-dir가 있으면 파일 존재와 제공된 해시를 확인한다. 최종 파일에는 verified와 SHA-256이 필요하다.\r\n- asset_registry 선택 provenance 필드(있을 때만 채운다): entity_type(character/product/prop/location/wardrobe/look/lighting/graphic/environment), entity_id, authority(authoritative/inferred/derived), source_asset_ids, prompt, provider, model, workflow, result_asset_id. 사용자가 준 SSOT·바이블은 authoritative로 기록하고 임의로 변경하지 않는다. 확인되지 않은 provider/model을 기록하지 않는다.\r\n- source_asset_ids/result_asset_id는 실제 asset_registry ID를 참조한다. entity_id가 있으면 비어 있지 않은 문자열이어야 하고 entity_type=character는 characters의 ID와 일치한다. 캐릭터 Identity Sheet A의 source_asset_ids에는 해당 캐릭터 SSOT artifact의 유일한 Markdown asset ID가 반드시 포함된다. 다른 entity_id는 해당 전문 바이블 locator로서 실제 소스를 인계하며 새 임의 테이블을 강제하지 않는다. shot.claim_ids가 있으면 claims의 실제 ID를 참조한다.\r\n- shot.retry_budget: 최초 생성 이후 허용된 최대 재시도 수(선택, 0 이상 정수). 승인된 video_execution_plan의 상한에서 온다. 0이면 최초 1회만 허용하고 attempt의 최대값은 1+retry_budget이다. 필드 부재는 무제한 실행 허가가 아니다.\r\n- generation_attempts: {id, shot_id, attempt(최초=1, 이후 샷별 중복 없는 양의 정수), route, model?, changes?, observed_failures?, preserve?, result(accept/reject/conditional), result_asset_id?, failure_class?, notes?}. 실제 시도만 기록한다. accept는 available/verified인 실제 결과 에셋 ID를 참조해야 하며 planned 에셋을 성공 결과로 기록하지 않는다. 기록/구조 검사 자체가 실행 승인이나 미디어 품질 검사는 아니다.\r\n- audio_mode: no_audio / no_dialogue / dialogue. audio_cues: {id, start_s, end_s, layer, shot_id?, asset_id?}. 소리는 겹칠 수 있지만 전체 영상 구간을 벗어나지 않는다.\r\n- captions: {id, start_s, end_s, text, shot_id?}. 오디오 음소나 자막 타이밍의 의미 적합성은 실제 재생으로 검사한다.\r\n- issues: {id, severity: blocker/major/minor, status: open/resolved, evidence?, fix?}.\r\n- delivery_spec: {destination, width, height, container, video_codec, caption_mode: none/sidecar/burned_in, final_asset_id, caption_asset_id?}. 기존 소스에서 현재 목적지 규격을 추정하지 않는다.\r\n- delivery_checks: {id, category: playback/timing/visual/audio/captions/continuity/claims, status: pass/fail/unverified/not_applicable, evidence?, reason?}. pass는 실제 검사 위치, N/A는 비적용 이유를 갖는다. 실제 확인하지 않고 pass를 적지 않는다.\r\n\r\n## 버전 변경과 범위\r\n변경된 산출물과 그 하위 인계를 stale로 표시하고 입력 버전을 갱신한 뒤 관련 항목만 재검수한다. 계획 패키지가 완성됐어도 실제 영상이 완성된 것은 아니다. 참고 후보·예산·도구 기능이 미정이면 계획에서 가정으로 남기고 실제 실행 직전에 확인한다.\r\n\r\n## 프리프로덕션 검토와 영상 실행 승인\r\n[프리프로덕션·검토 절차](preproduction-review.md)의 `review.md`는 `type=preproduction_review` artifact로 등록하고 검토 대상의 ID·버전을 dependencies/dependency_versions로 연결한다. 실제 사용자 수락 때만 approved와 approval 근거를 기록한다. 문서·이미지의 generated/verified 상태는 사용자 수락을 뜻하지 않는다.\r\n\r\n별도 `type=video_execution_plan` artifact는 승인된 검토 패키지 버전과 명시적 샷·모델/endpoint·실행/재시도/비용 상한을 참조한다. 실제 사용자 실행 승인 뒤에만 approved로 기록한다. 프리프로덕션 중 모델/가격 미정은 허용하지만 실행자 기본값으로 보충하지 않는다. 변경된 에셋의 종속 검토/실행 계획은 stale로 표시하고 새 버전에 이전 승인을 재사용하지 않는다. 사용자 승인과 파일 존재/구조 검사는 별개의 증거다.\r\napproved 영상 실행 계획은 dependency 그래프에 현재 approved인 preproduction_review를 반드시 포함한다. 이 구조 검사는 실제 사용자 권한·비용·음성/이미지의 품질을 인증하지 않는다.\r\n\r\n프리뷰와 최종은 별도 허가다. `video_execution_plan`의 승인 범위에 프리뷰 단계가 포함되면 승인된 프리뷰 입력 버전·설정·샷/출력 수·상한을 그대로 기록하고, 프리뷰 승인만으로 최종 생성·추가 과금을 허가하지 않는다. 프리뷰 실제 출력·검수 결과·수락 근거는 연결된 artifact(result_asset_id, generated/verified, evidence)로 남기고, 승인된 최종 계획은 프리뷰 판정과 최종 승격 경로를 dependencies로 참조한다. 프리뷰와 최종 범위를 하나의 plan 버전으로 함께 승인한 경우에만 최종이 같은 승인 안에서 현재 입력 버전·조건·상한으로 진행되며, 그렇지 않으면 현재 버전의 stale가 되고(재핀하기 전까지), 이 계보를 따라 이어지는 derivative도 연쇄로 stale가 된다. 비stale 에셋이 옛 버전을 핀하거나 stale 마스터에서 파생되면 검사가 거부한다.\r\n- 캐릭터 마스터는 7뷰 정체성 시트 외에 서사 관련 표정·의상(WD ID)·DO-NOT-CHANGE 락을 포함한다. 장소 마스터는 생산상 중요한 장소에 4공간뷰(establishing/reverse/lateral/top-down)와 출입·창·장애물·광원 앵커를 둔다 — 수치는 추정이면 `ESTIMATED`로 명시한다. 소품/도구/제품은 연속성이 문제가 될 때만 전/후/측/3/4·상태 변형·스케일 참조를 둔다. 장식 보드를 위해 에셋을 만들지 않는다.\r\n\r\n### 에셋 게이트: preliminary 표시하고 스토리보드를 역설계 소스로 쓰지 않는다.\r\n- `required_asset_versions`의 에셋 버전이 바뀌면 핀을 업데이트하지 않은 해당 artifact는 `update_project`가 자동으로 stale 처리한다. 무관한 다운스트림은 유지된다.\r\n\r\n### 패널 자산 참조\r\n- `storyboard.panels[]` 선택 합성은 허용되지만 action scene에서 source packshot 전체를 배경 위에 평면으로 얹지 않는다. 원근·면 방향·스케일·광원·반사·접촉 그림자·가림을 통합해 실제 공간의 물체로 읽혀야 한다. 제품을 쥐거나 열거나 도포하는 컷은 손과의 접촉/소유 상태 변화를 보여준다. 정면 packshot 합성은 계획된 frontal hold에 한해 사용하며 정확한 로고·법적 문구는 승인 아트워크로 보존한다.\r\n6. 손/피부/도포의 접촉은 [생성 영상 QA·재시도](21-generated-video-qa-retry.md)의 모션 절차, 모델 연속성은 [비주얼 모드·SSOT](20-visual-mode-ssot.md)로 라우팅한다.\r\n\r\n7. 액체 튐·물방울·성분 세계·불가능한 매크로 전환은 레이어 합성 계획으로 분리한다.\r\n8. QA: 실루엣·캡 형상·로고 위치·라벨 문구·재질·내용물 수위·색·손 접촉·최종 팩샷.\r\n\r\n### 분리형 부품의 상태·소유 인계\r\n\r\n제품을 열거나 캡 등 분리형 부품을 떼어 내는 경우, 제품 SSOT의 `캡/마개`와 불변 속성은 제품 아이덴티티를 고정하는 데 쓰고, 상태 전이는 기존 26 템플릿 행으로 기록한다. 실제 템플릿의 `대상 ID`, `시작 상태와 근거`, `끝 상태와 근거`, `후속 유지 범위 / 리셋 조건`, `동작 → 대상 변화 → 잔류 결과`, `검사한 동작/접촉 구간`을 연결하고, 샷/컷에서 어느 손이 제품과 분리 부품을 지지·소유하는지, 내려놓기/넘김이 어디서 일어나는지를 기존 `인물 블로킹`과 shot-local cue에 명시한다. 부품이 분리되면 명시적으로 놓거나 넘기기 전까지 소유 손에 남는다. 컷이나 화면 밖에서 부품/손의 상태가 저절로 바뀐 것으로 전제하지 않는다. 오프스크린 처리가 제품 물성에 영향을 주면 위치/후속 소유 상태는 `미확인`으로 두고 모순되는 샷 계획을 내지 않는다.\r\n\r\n제품 사용(분사·열기·도포 등) 직전 샷에서 제품 SSOT의 `캡/마개` 상태가 해당 동작을 허용하는지 맞춘다. 캡이 병에 남아 있는 상태라면 분사하지 않는다. 사용하려면 기존 06 shot row/cue에서 캡의 눈에 보이는 분리·놓기/보유를, 26 기존 행에서 손/부품 상태 전이를 계획하고, 이후 샷에서 해당 상태를 일관되게 유지한다. 분리·배치 과정은 필요하지 않다고 생략할 수 있지만, 그 경우에도 사용 시점의 `시작 상태`·손 소유·부품 처리가 앞뒤 샷과 모순되지 않아야 한다.\r\n\r\n제품 내용물·사용 뒤 피부/표면 잔류가 브리프나 승인된 자료에 특정되지 않으면 액적·광택·잔류를 사실/효능으로 만들지 않는다. brief가 창작된 시각 흔적을 요청하면 제안으로 표시하고 위치·시작/끝 상태·가림 뒤 유지 또는 명시적 reset을 기존 26 템플릿 행에 연결한다; 속성이 정해지지 않으면 `미확인`/`N/A`로 남긴다.\r\n\r\n### 형태·환경 은유를 제품 공개로 연결할 때\r\n\r\n제품을 늦게 드러내는 재료/풍경 순서는 필요할 때만 설계한다. 와이드 환경→가까운 표면/질감→일부 실루엣→제품·라벨에 서로 다른 정보 역할을 주고, 제안한 연결이 실제 컷·연속 이동·합성 중 무엇인지는 확인 전까지 단정하지 않는다. 제품 등장 뒤에는 SSOT의 실루엣·면·표식을 다시 회수한다. 풍경·반사·물방울은 방수/향/원산지/성능 증거가 아니다.\r\n\r\n제품과 세계의 형태를 맞출 때 **표면 대응**(원·곡선·색·질감)과 **의미 해석**(예: 힘·속도·향)을 따로 적는다. A03식 구체 대응이 필요하면 `assets/06-shots-template.md`의 기존 `공개 정보`, `관점·감정/구도 의도`, `카메라 동작`, `종료 프레임`에 양쪽 대상의 화면 위치·크기·방향·가림·질감 anchor, 대응 근거와 공개 시점을 기록한다. 시간상 대응에는 템플릿의 cue timeline을 쓰고, 별도 상태라면 기존 shot/panel row를 쓴다. 제안 전·중·후 frame에서 실제 변화가 읽히는지 계획/검수 상태를 구분해 확인하고, hard cut/dissolve/morph/mask 중 무엇을 쓸지와 대안을 비교한다. 전자는 화면 관계, 후자는 새 해석 제안이며 둘 다 주장을 증명하지 않는다. 시각 대응이 제품을 왜곡하거나 표식/라벨을 덮으면 단순 cut, 고정 하이라이트, 승인된 그래픽 레이어를 대안으로 검토한다.\r\n\r\n브리프에 불가능한 스펙터클이 있을 때만 그 진입·환상 범위·복귀를 정하고, 뒤 제품 히어로에서 승인된 스케일/라벨/조명/정체성을 재확립한다. 불·물·차량·섭취 등 위험하거나 불가능한 장면을 실제 사용법·안전성·제품 성능으로 오인시키지 않는다. 환상 신호가 충분하지 않으면 스펙터클을 제거하거나 비기능적 그래픽/애니메이션으로 바꾼다. 각 사례는 실제 관객·에셋·안전/권리 조건에 맞게 검토한다.\r\n\r\n산출물: 스폰서 요구 요약, 통합 모드, 이야기 호환 사용 사례, 광고 비트 맵, 필수 주장/비주얼 체크리스트, 고지 계획, 본편 복귀, 톤/신뢰 위험. 제품 영상은 추가로 제품 SSOT·시각 시퀀스·히어로 조명 계획·매크로/도포 슬롯\r\n\r\n해당 조건의 필드만 쓰고, 나머지는 비워 둔다. 각 필드는 기존 ID·artifact 버전·실제 근거 위치(파일/프레임/타임코드/로그)에 묶는다.\r\n\r\n- **대상과 범위**: 대상 ID(기존 prop/character/location/asset ID) · 변화가 적용되는 영역/속성 · 변화와 무관하게 보존되어야 할 영역/속성.\r\n- **시작/끝 상태**: 관찰 가능한 기술(색·형태·온도·젖음·개수·위치 등)과 근거 위치. 끝 상태는 생성 요청의 끝 상태와 후속 샷의 시작 상태 양쪽에 연결된다.\r\n- **후속 유지 범위**: 이 변화가 유효한 후속 샷/구간, 다시 리셋되는 조건(세척·교체·다른 대상), 리셋이 의도인지 오류인지. 바로 다음 컷뿐 아니라 문서화된 리셋까지 범위 안의 모든 해당 재등장·경계를 검사한다. 중간 가림은 의무를 지우지 않으며 관측 불가 구간만 미확인으로 남긴다. 액체 sheen, 물기, 먼지, 손자국처럼 남는 결과는 보이는 동안 계속 추적한다. 프레임 밖/가림은 리셋이 아니며, 자연 소실을 의도하면 표현·시간 경과의 근거와 새 상태를 명시한다.\r\n\r\n요청된 동선/시퀀스가 실제로 커버하는 단계와 그 사이에 생략된 단계를 적는다.\r\n- **의도적 생략(elision)**: 중간 과정을 보여주지 않고 생략 전 상태 → 생략 후 상태로 자른다. 생략 양쪽의 관찰 가능한 상태를 각각 적고, 생략으로 생긴 결과가 다음 컷에서 유지돼야 하면 그 유지 조건(다시 리셋되는 조건 포함)을 인계한다.\r\n\r\n실제 경과시간·촬영 구간·간격·공백은 확인 가능한 근거가 있을 때만 적고 없으면 `미확인`으로 둔다. 원본 길이와 출력 길이의 비율(예: \"4시간 / 8초\")만으로 실제 playback_rate·촬영 간격·획득 방식을 확정하지 않는다 — 그 비율이 촬영 샘플링·편집 배속·구간 선택 중 무엇의 결과인지 구분할 수 없기 때문이다. 획득 방식이 미확인이면 최종 출력 구간과 생략 전후 상태만 기록하고 방식별 근거는 비워 둔다.\r\n\r\n상태가 바뀌는 압축·생략(재료가 익음, 액체가 퍼짐, 조립이 진행됨)에는 생략 전 상태 → 생략 후 상태와 후속 유지 조건을 [상태·인과·연속성 인계](26-state-causality-continuity.md)의 선택 슬롯으로 넘긴다. 시간 압축이 없는 실시간 편집에는 이 절차를 적용하지 않는다.\r\n\r\n\r\n## 실행 가능한 편집·사운드 큐\r\n\r\n편집 표는 source 구간과 최종 타임라인 구간을 별도로 기록한다. 배속 샷은 `playback_rate`와 원본 구간을 함께 두며, 전환 중첩은 `transition`과 실제 길이로 표기한다. 출처 타임라인을 모르면 정밀한 원본 in/out을 추정하지 않는다. 원본 영상에 접근할 수 없고 사용자가 가상 배분을 요청하지 않았다면 샷별 최종 타임코드·길이를 만들지 말고 비트 순서와 역할만 제안한다. 명시적으로 가상 배분을 요청하면 `proposal / 비실행용`임을 표시하고 측정된 EDL과 분리한다.\r\n\r\n편집·큐 ID는 `project.json`과 실제 에셋 원장에서 이어받는다. 출처에 없는 shot_id/sound_id나 임의 JSON 계약을 만들어 실행 가능한 산출물처럼 제시하지 않는다. 실제 타임라인이나 에셋이 아직 없으면 ID와 source 구간을 비워 두거나, 비정본 제안서에서만 역할명으로 부른다.\r\n\r\n`assets/sound-cues.csv`의 `sound_id`는 `project.json`의 `audio_cues[].id`와 같게 쓴다. `start_s/end_s`는 최종 타임라인의 시작 포함/끝 미포함, `source_in_s/source_out_s`는 음원 파일 구간의 시작 포함/끝 미포함 초다. 샷 간 음악처럼 시퀀스 전체에 걸친 큐는 `shot_id`를 비워 둔다. 추가 실행 메타데이터는 버전이 있는 편집 산출물에 기록하고 `project.json`에서는 artifact/asset ID로 연결한다.\r\n\r\n각 큐에는 레이어, 파일, 적용 gain(dB), fade 길이, 믹스 자동화 메모, 동기 기준점/오프셋, 권리 상태를 연결한다. `sync_offset_s`는 실제 소리 사건 시각에서 화면 기준점 시각을 뺀 값이며, 음향이 먼저면 음수다. 자동화는 `mix_note`에 구간과 목표를 적는다. 단일 혼합 참조 음원은 `mixed_reference` 레이어로 기록하고, 없는 stem을 가정하지 않는다. 권리 상태는 `unknown`, `user_asserted`, `evidence_recorded`, `restricted` 중 실제 근거에 맞춰 쓰고, 증거 위치나 제한은 `mix_note`에 둔다. 표기만으로 권리 허가나 게시 승인을 의미하지 않는다.\r\n\r\n제품 공개·접촉·충격·전환을 음악에 맞출 때는 기준점을 `action_peak`, `reveal`, `cut` 등으로 이름 붙이고 기준 타임코드와 실제 오프셋을 측정한다. 허용 오차는 브리프나 승인된 검수 기준에서 가져오며 보편적인 임의 수치를 적용하지 않는다. 권리 미확인 음원은 검토본에 사용하더라도 상태와 게시 제한을 표시한다.\r\n\r\n비트 기반 그래픽·몽타주에서는 승인된 최종 오디오 마스터의 실제 박/다운비트/드롭 시각을 기준으로 삼고, 해당 파일·버전과 측정 근거를 편집 아티팩트에 연결한다. 초 단위 사건 시각은 타임라인 프레임레이트의 절대 프레임 경계로 변환하며, 반올림한 박 간격을 반복 누적해 드리프트를 만들지 않는다. 마스터나 프레임레이트가 바뀌면 종속 컷·그래픽 타이밍을 다시 계산하고 실시간 재생으로 확인한다. 박 기반 편집이 브리프 요구가 아니면 이 절차를 강제하지 않는다.\r\n\r\n동적 편집 검수는 전체 영상을 실시간으로 소리와 함께 재생하고, 필요한 경우 무음 화면·오디오 단독·전환 경계 프레임을 추가 확인한다. 표본 프레임만 확인했으면 전체 리듬이나 청취 품질을 통과로 판정하지 않는다.\r\n\r\n편집 명세는 실행기에서 해석 가능한 타임라인과 음원 계층을 제공해야 한다. 실제 편집은 별도 요청·승인과 사용 가능한 실행기 확인 뒤 수행하며, 계획표·스크립트 작성만으로 렌더 완료를 주장하지 않는다.\r\n\r\n## 오디오 의도와 실행 경로\r\n\r\n오디오 작업 전에 요청을 분류한다: 무음(`no_audio`) · 대사 없음(`no_dialogue`) · 효과음만 · 음악 제외 · 단일 혼합 참조. `project.json`의 `audio_mode`와 `audio_cues` 레이어를 그대로 재사용하고 새 enum을 만들지 않는다. 세부 의도는 편집 산출물과 큐 레이어로 기록한다:\r\n\r\n- `no_audio` — 오디오 큐를 두지 않는다. 무음 요청에 음악·효과를 추가하지 않는다.\r\n- `no_dialogue` — 말만 없다. 음악·환경·효과 큐는 유지되므로 무음이나 음악 제외로 해석하지 않는다.\r\n- 효과음만(SFX-only) — 대사 유무에 따라 `dialogue`/`no_dialogue`로 기록하되 큐는 SFX 계열 레이어만 둔다. 음악이나 대사를 암묵적으로 추가하지 않고, 생성 결과에 음악·말이 섞여 나오면 실패로 기록한다.\r\n- 음악 제외 — 음악 레이어를 두지 않는다. 지시 문법은 실행자의 실제 지원 제어로 쓴다; 제어가 없는 endpoint에 지원되지 않는 파라미터나 존재하지 않는 stem을 발명하지 않는다.\r\n- 단일 혼합 참조 — `mixed_reference` 레이어 하나로 기록하고 대사/음악/효과 분리를 약속하지 않는다. 분리 stem은 실제 소스가 제공할 때만 그 레이어로 기록한다.\r\n\r\n요청한 제외·구성을 endpoint가 실제 지원하지 않으면 가짜 지시를 넣지 않는다. 대신 영상 생성과 음향을 분리해 조립하는 경로(별도 음성/효과음 패스, 편집 단계 합성)를 비용·승인 범위와 함께 별도 제안하고, 승인 없이 새 음향 작업·분리·과금을 시작하지 않는다. 사용자가 지정한 음향 실행자·소스·방식은 조용히 대체하지 않는다.\r\n\r\n실제 오디오 결과는 요청한 의도와 대조해 청취 검수한다. 듣지 않은 구간은 미검증으로 두고, 청취 확인 없이 구성(말 없음·음악 없음·분리)이 맞다고 보고하지 않는다.\r\n\r\n## 음악·효과음 소싱과 권리\r\n\r\n카탈로그 또는 사용자 제공 파일에서 후보를 고를 때 브리프의 기능·감정·길이·동기 기준점에 맞춰 비교하고 비교한 기준을 남긴다. 실제 길이와 필요한 구간은 파일을 보고 맞춘다.\r\n\r\n선택 항목마다 실제 출처/트랙·파일 ID와 버전, 권리 근거, 확인 시점·위치를 연결한다. 구독·다운로드·접근 가능 URL은 게시 허가가 아니며, 플랜/프로젝트·채널·지역·기간 제한은 해당하는 것만 `mix_note`나 연결된 편집 산출물에 기록한다(`sound-cues.csv` 필드를 늘리지 않는다). `rights_status`는 실제 근거에 맞춰 쓰고 출처 URL만으로 상업적 사용을 통과시키지 않는다. 권리가 제한되거나 불명이면 게시 가능으로 주장하지 않고, 차단되는 범위와 준비 가능한 범위를 나눠 보고한다. 구매·구독 가입·게시는 자동으로 하지 않고 사용자 승인을 받는다.\r\n\r\n선택한 음원은 실제로 들어서 후보 비교가 실제 소리와 맞는지 확인한 뒤 `source_in_s/source_out_s`, fade, gain, `sync_anchor`/`sync_offset_s`를 측정해 기존 편집 표와 `sound-cues.csv` 필드에 맞춘다. 측정하지 않은 구간·동기는 추정으로 표시한다.\r\n\r\n## 후반작업 단계 추적 (영화 라이프사이클 요청 시)\r\n\r\n영화·단편 요청으로 [28](28-film-production-lifecycle.md)의 05 Post-production이 배정됐을 때, 선택된 후반 단계만 단계 표로 추적한다. `assets/film-postproduction-template.md`를 사용하고, 이 표는 `project.json` artifact/dependency/version과 `asset_registry`를 참조하는 인계 문서지 새 원장이 아니다.\r\n\r\n**단계 목록** — 각 단계는 개별 artifact로 버전을 단다: 인제스트/싱크 → 어셈블리 컷 → 러프 컷 → 파인 컷 → 픽처 락 → VFX → ADR → Foley → 사운드 디자인 → 스코어/음악 편집 → 사운드 믹스 → 컬러 그레이드 → 자막/크레딧 → 마스터링 → 최종 QC. 미적용 단계는 N/A와 이유를 적고, 겹치는 단계는 의존 대상의 버전을 남긴다. 순서는 [23](23-finishing-platform.md)의 의존 순서와 맞춘다 — 그레이드와 최종 믹스는 픽처 락 이후, 마스터링은 그 이후다.\r\n\r\n각 행은 다음을 기록한다: 단계 artifact ID·버전, 입력 테이크/미디어의 artifact·asset ID와 버전(잠금 입력의 경우 그 잠금 버전), 상태, 실제 출력 locator, dependencies, 검수 evidence, 미해결 이슈, 미검증 범위.\r\n\r\n**상태 규칙** — `project.json` artifact 상태(draft/reviewed/approved/generated/verified/stale)를 그대로 쓰고 새 enum을 만들지 않는다. 계획·설계는 draft/reviewed로 두고, 실제 출력 파일이 생기기 전에는 generated/verified로 올리지 않는다. 편집 계획·큐 표·믹스 노트만으로 렌더/믹스/마스터 완료를 주장하지 않는다. 픽처 락도 실제 승인된 컷 버전이 있을 때만 기록하고, 계획된 잠금 날짜를 잠금으로 취급하지 않는다.\r\n\r\n**단계별 인계 규칙**\r\n\r\n- 인제스트/싱크: 선택 테이크(촬영 로그·`generation_attempts`의 실제 accept 결과)만 입력으로 연결한다. 실제 파일·asset_registry ID와 동기화 근거(싱크 오프셋·클립·타임코드
