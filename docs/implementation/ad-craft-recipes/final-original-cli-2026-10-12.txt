프로필\r\n`schema_version`은 `1.1`을 사용한다. 이전 `1.0` 입력도 일부 호환되지만 새로운 프로젝트는 v1.1 필드를 작성한다.\r\n\r\n- plan: 필수 제작 정보·시간·참조·상태 기록을 검사한다. 생성 전 자료와 source_duration_status=estimated를 허용한다.\r\n- preproduction: 저장한 현재 시놉과 모든 캐릭터 character_sheet의 정확한 버전에 의존한다. 각 샷/패널에 원문·beat/scene/shot/panel/캐릭터·페르소나/SSOT·카메라·시간·실제 이미지 참조를 통합한다. 각 패널은 해당 beat·가시 캐릭터·audio cue·speech ID를 직접 기록한다.\r\n- 합본 `type=storyboard_sheet` artifact는 보드의 현재 버전에 의존하고 `kind=storyboard_sheet` 이미지 에셋 정확히 하나를 연결한다. PNG의 `storyboard_sheet.panel_traceability` metadata와 표시 캡션은 panel별 ID 매핑을 담는다. 입력 시트/crop은 합본 출력의 대체물이 아니다.\r\n- 이미지 모드의 `storyboard_sheet_artifact_ids`는 이야기 순서로 정렬된 `type=storyboard_sheet` artifact 배열이다. **한 시트에는 최대 8개 패널**만 둔다 — 패널 수·정보 밀도·씬 경계로 장수를 정하고 한 장에 욱여넣지 않는다. 각 시트 artifact는 보드의 현재 버전에 의존하고 `kind=storyboard_sheet` 이미지 에셋 정확히 하나를 연결한다. 각 시트 에셋의 `panel_ids`는 자기 구간의 정본 panels 순서이며, 모든 시트를 순서대로 이어 붙이면 정본 전체 순서와 일치한다(누락·중복 없음). 시트가 두 장 이상이면 각 에셋에 `sheet_index`(1부터)·`sheet_count`를 기록한다. `source_asset_ids`는 그 시트 패널의 실제 픽셀 입력(source_sheet_asset_id가 있으면 그 ID, 없으면 image_asset_id)을 같은 순서로 담고 `source_sha256`는 해당 입력 ID→현재 해시 맵이다.\r\n- `render_storyboard_sheet.py <project.json> --base-dir <root> --output 04_STORYBOARDS/sheets/<새.png> [--font <font.ttf>] [--panels-per-sheet 1..8]`는 clean 패널과 외부 촬영 캡션을 순서 있는 PNG 세트로 조립한다. 각 시트의 실제 path/hash/패널·소스 매핑과 동일 traceability PNG metadata를 반환하며 원장을 쓰지 않는다. 총괄이 모든 시트를 등록하고 실제 합본을 연다.\r\n- 합본을 만든 직후 `split_storyboard.py --sheet <프로젝트-relative 시트>`를 이야기 순서로 반복 지정해 장면 overview와 clean 패널을 추출한다. 실제 JSON manifest를 `kind=storyboard_split_manifest`로 등록하고 `preproduction.storyboard_split_asset_id`에 연결한다. 각 추출 이미지도 실제 경로·SHA-256으로 등록한다. manifest의 `file`은 manifest 폴더 기준, `sheet_path`·`sheets[].path`·`band_sources`는 프로젝트 root 기준 상대 경로다. 원본 패널 입력을 추출 이미지로 바꾸지 않는다.\r\n- preproduction/FINAL은 manifest의 주장만 신뢰하지 않는다. 각 panel/scene의 실제 등록 파일·SHA-256, canonical scene/shot/panel, source asset/version/hash 및 asset pins가 서로 일치해야 하며 다른 패널 파일을 alias한 split은 거부한다.\r\n- `package_production.py --require-final`은 명시적인 현재 FINAL 보드, 완료된 이미지 기반 패키지, 정렬된 현재 시트/hash와 일치하는 split manifest, 전체 scene/panel 이미지의 실제 등록을 요구한다. ZIP의 root `project.json`은 휴대 가능한 파생 스냅샷이며 registry 경로가 실제 패키지 파일을 가리킨다. 표준 폴더 경로는 유지하고, 구형 평면 경로는 asset ID를 포함해 충돌 없이 배치한다. CSV manifest는 정본의 파생물이고 모든 실제 패키지 파일을 열거한다.\r\n- ZIP 재개봉은 asset registry 경로와 split 내부 `file`/`sheet_path`/overview source 참조를 같은 relocation map으로 재투영하고 파생 snapshot hash를 갱신한다. 원본 정본은 변경하지 않으며, 실제 복사 byte stream이 등록 지문과 다르면 게시를 중단한다.\r\n- 모든 필수 실제 파일에는 SHA-256을 기록한다. 이미지 디코딩·현재 종속 버전·전체 커버리지·열린 blocker도 검사한다. reviewed/approved인 preproduction_review 또는 approved인 video_execution_plan에는 plan에서도 이 완결 게이트를 자동 적용하며 이미지 모드를 요구한다. 검토는 시놉·보드·합본을 dependency 그래프로 소비해야 한다.\r\n- 누락 상태는 draft/stale로 보존하고 strict preproduction 검사에서는 준비 미완료로 반환한다. 프롬프트·가상 path·planned 에셋·검사 기록만으로 실제 산출물이라고 표시하지 않는다. 구조 통과 뒤에도 캐릭터 7뷰 정체성, 전체 clean 컷 읽힘, 합본 누락/가독성, 장면 내 제품·빛·그림자·반사 통합을 실제 검수하고 사용자 수락을 별도로 받는다.\r\n\r\n\r\n## 실제 파일과 부가 시간표\r\n- asset_registry: {id, kind, version, path, status, sha256}. 실제 path는 프로젝트 폴더 기준 상대 경로를 권장하며 `--base-dir` 검사에서 resolve한 결과가 그 폴더 밖이면 거부한다(절대 경로/..//symlink 포함). planned는 path=null을 허용한다. available/verified는 실제 경로를 갖고 base-dir가 있으면 파일 존재와 제공된 해시를 확인한다. 최종 파일에는 verified와 SHA-256이 필요하다.\r\n- asset_registry 선택 provenance 필드(있을 때만 채운다): entity_type(character/product/prop/location/wardrobe/look/lighting/graphic/environment), entity_id, authority(authoritative/inferred/derived), source_asset_ids, prompt, provider, model, workflow, result_asset_id. 사용자가 준 SSOT·바이블은 authoritative로 기록하고 임의로 변경하지 않는다. 확인되지 않은 provider/model을 기록하지 않는다.\r\n- source_asset_ids/result_asset_id는 실제 asset_registry ID를 참조한다. entity_id가 있으면 비어 있지 않은 문자열이어야 하고 entity_type=character는 characters의 ID와 일치한다. 캐릭터 Identity Sheet A의 source_asset_ids에는 해당 캐릭터 SSOT artifact의 유일한 Markdown asset ID가 반드시 포함된다. 다른 entity_id는 해당 전문 바이블 locator로서 실제 소스를 인계하며 새 임의 테이블을 강제하지 않는다. shot.claim_ids가 있으면 claims의 실제 ID를 참조한다.\r\n- shot.retry_budget: 최초 생성 이후 허용된 최대 재시도 수(선택, 0 이상 정수). 승인된 video_execution_plan의 상한에서 온다. 0이면 최초 1회만 허용하고 attempt의 최대값은 1+retry_budget이다. 필드 부재는 무제한 실행 허가가 아니다.\r\n- generation_attempts: {id, shot_id, attempt(최초=1, 이후 샷별 중복 없는 양의 정수), route, model?, changes?, observed_failures?, preserve?, result(accept/reject/conditional), result_asset_id?, failure_class?, notes?}. 실제 시도만 기록한다. accept는 available/verified인 실제 결과 에셋 ID를 참조해야 하며 planned 에셋을 성공 결과로 기록하지 않는다. 기록/구조 검사 자체가 실행 승인이나 미디어 품질 검사는 아니다.\r\n- audio_mode: no_audio / no_dialogue / dialogue. audio_cues: {id, start_s, end_s, layer, shot_id?, asset_id?}. 소리는 겹칠 수 있지만 전체 영상 구간을 벗어나지 않는다.\r\n- captions: {id, start_s, end_s, text, shot_id?}. 오디오 음소나 자막 타이밍의 의미 적합성은 실제 재생으로 검사한다.\r\n- issues: {id, severity: blocker/major/minor, status: open/resolved, evidence?, fix?}.\r\n- delivery_spec: {destination, width, height, container, video_codec, caption_mode: none/sidecar/burned_in, final_asset_id, caption_asset_id?}. 기존 소스에서 현재 목적지 규격을 추정하지 않는다.\r\n- delivery_checks: {id, category: playback/timing/visual/audio/captions/continuity/claims, status: pass/fail/unverified/not_applicable, evidence?, reason?}. pass는 실제 검사 위치, N/A는 비적용 이유를 갖는다. 실제 확인하지 않고 pass를 적지 않는다.\r\n\r\n## 버전 변경과 범위\r\n변경된 산출물과 그 하위 인계를 stale로 표시하고 입력 버전을 갱신한 뒤 관련 항목만 재검수한다. 계획 패키지가 완성됐어도 실제 영상이 완성된 것은 아니다. 참고 후보·예산·도구 기능이 미정이면 계획에서 가정으로 남기고 실제 실행 직전에 확인한다.\r\n\r\n## 프리프로덕션 검토와 영상 실행 승인\r\n[프리프로덕션·검토 절차](preproduction-review.md)의 `review.md`는 `type=preproduction_review` artifact로 등록하고 검토 대상의 ID·버전을 dependencies/dependency_versions로 연결한다. 실제 사용자 수락 때만 approved와 approval 근거를 기록한다. 문서·이미지의 generated/verified 상태는 사용자 수락을 뜻하지 않는다.\r\n\r\n별도 `type=video_execution_plan` artifact는 승인된 검토 패키지 버전과 명시적 샷·모델/endpoint·실행/재시도/비용 상한을 참조한다. 실제 사용자 실행 승인 뒤에만 approved로 기록한다. 프리프로덕션 중 모델/가격 미정은 허용하지만 실행자 기본값으로 보충하지 않는다. 변경된 에셋의 종속 검토/실행 계획은 stale로 표시하고 새 버전에 이전 승인을 재사용하지 않는다. 사용자 승인과 파일 존재/구조 검사는 별개의 증거다.\r\napproved 영상 실행 계획은 dependency 그래프에 현재 approved인 preproduction_review를 반드시 포함한다. 이 구조 검사는 실제 사용자 권한·비용·음성/이미지의 품질을 인증하지 않는다.\r\n\r\n프리뷰와 최종은 별도 허가다. `video_execution_plan`의 승인 범위에 프리뷰 단계가 포함되면 승인된 프리뷰 입력 버전·설정·샷/출력 수·상한을 그대로 기록하고, 프리뷰 승인만으로 최종 생성·추가 과금을 허가하지 않는다. 프리뷰 실제 출력·검수 결과·수락 근거는 연결된 artifact(result_asset_id, generated/verified, evidence)로 남기고, 승인된 최종 계획은 프리뷰 판정과 최종 승격 경로를 dependencies로 참조한다. 프리뷰와 최종 범위를 하나의 plan 버전으로 함께 승인한 경우에만 최종이 같은 승인 안에서 현재 입력 버전·조건·상한으로 진행되며, 그렇지 않으면 현재 버전의 별도 최종 승인이 필요하다. 같은 seed·입력의 재생성은 같은 동작·정체성을 보장하지 않으므로 최종본은 다시 검수한다.\r\n\r\n## 선택적 상세 스토리보드 확장\r\n제작용/상세 콘티와 전체 보드 시트에는 [완전한 스토리보드 계약](storyboard-contract.md) §8의 `storyboard` 객체와 shot 기술 필드를 정본 `project.json`에 추가한다. 기존 schema_version=1.1 및 일반 plan/delivery 프로필은 유지한다. 별도 `validate_storyboard.py`는 전체 비트/씬/샷/패널 연결과 제작 슬롯을 검사하며 실제 이미지에는 `--require-images --base-dir`를 적용한다. 합본 crop/clean 컷은 `split_storyboard.py`의 파생 결과를 asset_registry에 등록하고 같은 ID로 연결한다. CSV/시트/분할 manifest는 조회·등록용 투영이며 별도 원장이 아니다. 의미 검수·권리·사용자 수락을 파일 검사로 대체하지 않는다.\r\n\r\n## v5.1 프로덕션 무결성 (LOOK·에셋 게이트·계보·provenance·패키지)\r\n\r\n선택 확장이 아니라 전체 이미지 기반 패키지와 그 다운스트림(씬 상태·보드·생성 명세·애니매틱)에 적용한다. 기존 schema_version=1.1을 유지하고 아래 필드는 모두 선택이지만, `final`을 선언하는 순간 해당 게이트는 강제다.\r\n\r\n### 활성 LOOK과 스타일/월드 바이블\r\n- `look_asset_id`는 루트 필드로, `entity_type=look`(또는 미분류)의 asset_registry 에셋을 가리킨다. LOOK은 **하나만 활성**으로 둔다 — 프로젝트 전체 시각 문법(매체·리얼리즘·비율·팔레트·조명 철학·카메라 문법·스타일 드리프트 금지)을 버전으로 잠근다. 바이블 문서에는 `assets/style-world-bible-template.md`를 쓴다.\r\n- 모든 시각 생성 에셋은 활성 LOOK 버전을 참조한다. LOOK 에셋의 내용이 바뀌면 버전을 올리고 종속물을 stale 처리한다. 패널이 활성 바이블에 없는 새 시각 스타일을 발명하지 않는다.\r\n\r\n### 마스터·파생 에셋 계보\r\n- `asset_registry` 선택 필드 `role: master|derivative`와 `master_asset_ref: {asset_id, version}`을 둔다. 반복 정체성 에셋(캐릭터 마스터·장소 마스터·소품 마스터)은 한 번만 master로 등록하고, 씬별 상태(젖음·파손·의상·조명·배치)는 derivative로 등록해 마스터 ID와 **정확한 버전**을 핀한다. 여러 씬 폴더에 같은 마스터의 편집 가능한 사본을 두지 않는다.\r\n- 마스터 버전이 올라가면 그것을 핀하는 derivative는 자동으로 stale가 되고(재핀하기 전까지), 이 계보를 따라 이어지는 derivative도 연쇄로 stale가 된다. 비stale 에셋이 옛 버전을 핀하거나 stale 마스터에서 파생되면 검사가 거부한다.\r\n- 캐릭터 마스터는 7뷰 정체성 시트 외에 서사 관련 표정·의상(WD ID)·DO-NOT-CHANGE 락을 포함한다. 장소 마스터는 생산상 중요한 장소에 4공간뷰(establishing/reverse/lateral/top-down)와 출입·창·장애물·광원 앵커를 둔다 — 수치는 추정이면 `ESTIMATED`로 명시한다. 소품/도구/제품은 연속성이 문제가 될 때만 전/후/측/3/4·상태 변형·스케일 참조를 둔다. 장식 보드를 위해 에셋을 만들지 않는다.\r\n\r\n### 에셋 게이트: preliminary vs final\r\n- artifact 선택 필드 `finality: preliminary|final`과 `required_asset_versions: {asset_id: version}`을 둔다. finality를 생략하면 preliminary다.\r\n- `final` 선언은 **생성 전 잠금 게이트**다: 참조 에셋이 전부 등록돼 있고 status가 **`verified`**(v5.1의 LOCKED/APPROVED/VERIFIED_REFERENCE에 해당 — `available`은 파일이 존재할 뿐 에셋 QA 잠금이 아니므로 final을 차단한다)이며 핀 버전이 현재와 같아야 한다. final 시각 산출물(type storyboard/storyboard_sheet)은 추가로 **활성 `look_asset_id`가 등록된 style_world_bible/look 에셋이고 verified이며 해당 board의 `required_asset_versions`에 현재 버전으로 핀**돼 있어야 한다. stale이거나 draft인 artifact는 final이 될 수 없고, final은 의존 체인 어디에도 누락/draft/stale/버전 드리프트를 가질 수 없다. 실행 시점 게이트는 `scripts/asset_gate.py`의 `check_asset_gate(project, artifact_ids=None)`다 — `artifact_ids`로 특정 final 범위만 검사할 수 있고, 반환 blocker 목록이 비어 있어야 최종 생성·납품으로 진행한다. `--profile 장소·광원·세팅으로 촬영 순서를 묶고 이야기 순서와 구분한다.\r\n9. 패널에서 핵심 행동의 실루엣, 인물·소품 겹침, 주목점·시선 유도, 필요한 깊이·대비 및 최종 출력 크기에서의 판독성을 확인한다. 필수 정보가 읽히지 않으면 구도·스테이징·시점 또는 패널 분할을 고친다.\r\n10. 동작 중심 비트의 start/action_peak/end 이미지는 실제 시간 상태 차이를 보여야 한다. 인접 패널에 자세·행동·손-제품 접촉·시선·공간 관계의 변화가 없으면 키프레임을 다시 스테이징한다. 제공된 인물/제품 reference를 완성된 컷아웃으로 붙이지 않고, 제품이 장면의 원근·광원·접촉 안에서 읽히는지 확인한다.\r\n11. 스토리보드가 텍스트 설명뿐이면 이미지가 완성됐다고 말하지 않는다. 실제 그림/프리비즈가 있으면 카메라와 블로킹을 비교한다.\r\n\r\n### 정보 단위와 POV/반응 인계\r\n\r\n하나의 scene에 여러 shot이 있을 수 있고, 한 shot도 여러 action-phase를 포함할 수 있다. 장면에서 actor/camera/action 변화가 없다면 event detector나 시각 grain마다 새 shot을 만들지 않는다. 반대로 POV 이동과 상대의 reaction은 서로 다른 정보/관점을 전달할 때 각각 목적·진입/종료 상태가 보이는 shot으로 분리한다. 같은 continuous shot에서 양쪽을 실제로 볼 수 있으면 한 shot 안의 phase로 적고, 관찰되지 않은 reverse/cut을 가정하지 않는다.\r\n\r\n특히 상대의 표정을 보여 주는 host/reverse shot에서 guest의 POV 전환·후속 이동을 같은 shot에 연속 서술하지 않는다. host reaction은 그 shot에 보이는 host/구도에 한정한다. guest의 시선·POV·복귀 동작은 별도의 shot 또는 같은 프레임에서 양쪽을 실제로 볼 수 있도록 의도한 구도로 계획하고, 그 연결이 불명확하면 06의 shot ID/time/blocking/관점·공개 필드를 분리해 09의 컷 순서와 잇는다. shot 한 행/ID에 여러 관점이 들어가도 관객에게 실제로 함께 보이는 근거가 있어야 한다.\r\n\r\n각 shot에는 초점 대상, 새 정보, 행동의 주체·상대, reaction cue, 종료 상태를 기존 shot/beat/cue 필드에 기록한다. 핵심 반응이나 product handoff가 앞 shot의 자극에 의존하면 cut order와 cue를 [09-edit](09-edit.md)에 연결한다. 캐릭터 목표/실행 가능한 action은 [04-performance](04-performance.md), 지속 상태와 가림 뒤 재등장은 해당할 때만 [26-state-causality-continuity](26-state-causality-continuity.md)로 넘긴다. Copy가 행동을 약속하면 텍스트 상태와 행동을 맞추되 shot count나 endcard/CTA를 새로 의무화하지 않는다.\r\n\r\n위계/스케일 농담에서 아동과 성인의 대상/역할을 마주 놓을 때, 두 인물·시간·관계가 같은지 브리프에서 정하고 storyboard의 기존 character/shot identity를 맞춘다. 명시된 허구가 아니면 아동이 실제 차량을 운전하거나 위험한 행동을 하는 것처럼 staging하지 않는다. copy가 한 뜻에서 다른 뜻으로 바뀌면 두 화면 상태와 각각의 대상/행동을 별도로 적는다; 연결점이 불분명하면 단순 cut 또는 copy 변경을 비교한다.\r\n\r\n목격자/대상 반응 사다리가 필요할 때만 사건→개별 시선→집단 반응→원인 대상/역방향 정보→문구 순서를 계획한다. 각 반응을 독립 cut으로 강제하지 않고, 같은 scene의 여러 phase일 수 있는지 검토한다. 확인 가능한 eyeline과 공간 관계를 맞추고 표정만으로 목격, 말, 동의, 동일 사건을 추정하지 않는다. 관련 장르 기대/closure는 실제 comedy brief일 때만 [17-genre-comedy](17-genre-comedy.md)에서 판단한다.\r\n\r\n숙박/서비스/장소를 따라가는 브리프에는 입구→경로→문턱→기준 landmark→목적지와 복귀를 scene/shot fields의 공간 기준으로 선언한다. 프레임/POV가 바뀌어도 landmark·방향·소품 소유 관계를 유지한다. 미니어처/portal scale break는 ordinary space와 분리된 fantasy view 및 복귀 shot/phase를 표시한다; 가림·wipe만으로 실제 floorplan이나 이동 거리를 증명하지 않는다. 수치 spatial/camera 요청은 기존 `$camera-spatial-design` handoff를 사용한다.\r\n\r\n화면 안 화면·인셋이 관객 시선을 나눌 때만 main/secondary 정보, 공개 순서, 기준 anchor, 각 창의 시간·공간·출처가 같은지/다른지 기록한다. 동시 inset이면 동시 동작을 보이는지, 과거/별도 세계의 insert면 그 시간·공간 전환이 읽히는지 명시한다. 실제 출력 크기와 크롭에서 각 창의 대상·행동·타이포를 검사한다; flash나 detector event 수만으로 리듬/beat를 만들거나 동시성을 주장하지 않는다.\r\n\r\n## 산출물 목적 구분 — 스토리보드·샷리스트·애니매틱·프리비즈\r\n\r\n같은 샷 ID를 공유해도 네 산출물은 목적이 다르며 하나가 다른 하나를 대체하지 않는다. 영화 라이프사이클에서는 [영화 제작 라이프사이클](28-film-production-lifecycle.md)의 03 Pre-production 라우팅을 따른다.\r\n\r\n- **스토리보드**: 이야기·정보 공개를 설명하는 시각 설명물. 검정 구간이나 로고 초기화는 실제 확인한 타임라인의 화면 상태로 적는다. 자동 캡션/ASR는 음성 큐나 발화 시각의 근거가 아니며 원본 컷 시간을 새 카피 싱크로 복사하지 않는다.\r\n\r\n## 완료 조건\r\n컷이 감정 또는 정보를 바꾸는가? 대사가 명료한가? 전체 길이와 컷 간 방향성이 맞는가?\r\n\r\n## 근거와 적용 범위\r\n자료 ID: 04,09,10,11,12. `sources.md`에서 파일 상태와 탐색 위치를 확인한다. 절차와 템플릿은 여러 자료의 개념을 결합한 독자 설계다. 저자의 규칙을 그대로 재현한 요약이나 공식 인증된 방법론으로 표현하지 않는다.\r\n\r\n## 출력 템플릿\r\n`assets/09-edit-template.md`를 복사해 채운다. 영화 라이프사이클의 후반 단계 추적에는 `assets/film-postproduction-template.md`를 함께 쓴다.\r\n\r\n## 배속과 원본\r\n배속·슬로모션 샷은 source_in_s와 playback_rate를 적고 실제 원본 길이와 최종 구간을 구분한다. 디졸브·오디오 중첩은 별도 레이어로 표현하며 기본 JSON 샷 구간은 최종 영상의 대표 구간을 겹치지 않게 배정한다. 실제 전환 프레임은 편집 타임라인에서 재검수한다.\r\n\r\n## 시간 압축·생략의 획득 방식과 상태\r\n\r\n시간을 줄이는 편집은 획득 방식을 먼저 구분한다 — 같은 \"4시간 → 8초\"라도 기록해야 할 근거가 다르다.\r\n\r\n- **연속 소스 배속**: 연속 녹화의 한 구간을 재생 속도로 압축. `playback_rate`와 source 구간에 실제 측정값을 적는다.\r\n- **인터벌 획득(타임랩스)**: 간격 샘플링으로 촬영. 실제 촬영 구간·프레임 간격·중단/공백의 근거(촬영 로그·파일 타임스탬프·사용자 제공 메타데이터)를 적고, 화면 내 단서(시계·조명 변화)와 제공 메타데이터를 구분한다.\r\n- **단계 몽타주**: 과정의 선택 단계를 별도 컷으로 배열. 각 컷이 실제로 커버하는 단계와 그 사이에 생략된 단계를 적는다.\r\n- **의도적 생략(elision)**: 중간 과정을 보여주지 않고 생략 전 상태 → 생략 후 상태로 자른다. 생략 양쪽의 관찰 가능한 상태를 각각 적고, 생략으로 생긴 결과가 다음 컷에서 유지돼야 하면 그 유지 조건(다시 리셋되는 조건 포함)을 인계한다.\r\n\r\n실제 경과시간·촬영 구간·간격·공백은 확인 가능한 근거가 있을 때만 적고 없으면 `미확인`으로 둔다. 원본 길이와 출력 길이의 비율(예: \"4시간 / 8초\")만으로 실제 playback_rate·촬영 간격·획득 방식을 확정하지 않는다 — 그 비율이 촬영 샘플링·편집 배속·구간 선택 중 무엇의 결과인지 구분할 수 없기 때문이다. 획득 방식이 미확인이면 최종 출력 구간과 생략 전후 상태만 기록하고 방식별 근거는 비워 둔다.\r\n\r\n상태가 바뀌는 압축·생략(재료가 익음, 액체가 퍼짐, 조립이 진행됨)에는 생략 전 상태 → 생략 후 상태와 후속 유지 조건을 [상태·인과·연속성 인계](26-state-causality-continuity.md)의 선택 슬롯으로 넘긴다. 시간 압축이 없는 실시간 편집에는 이 절차를 적용하지 않는다.\r\n\r\n\r\n## 실행 가능한 편집·사운드 큐\r\n\r\n편집 표는 source 구간과 최종 타임라인 구간을 별도로 기록한다. 배속 샷은 `playback_rate`와 원본 구간을 함께 두며, 전환 중첩은 `transition`과 실제 길이로 표기한다. 출처 타임라인을 모르면 정밀한 원본 in/out을 추정하지 않는다. 원본 영상에 접근할 수 없고 사용자가 가상 배분을 요청하지 않았다면 샷별 최종 타임코드·길이를 만들지 말고 비트 순서와 역할만 제안한다. 명시적으로 가상 배분을 요청하면 `proposal / 비실행용`임을 표시하고 측정된 EDL과 분리한다.\r\n\r\n편집·큐 ID는 `project.json`과 실제 에셋 원장에서 이어받는다. 출처에 없는 shot_id/sound_id나 임의 JSON 계약을 만들어 실행 가능한 산출물처럼 제시하지 않는다. 실제 타임라인이나 에셋이 아직 없으면 ID와 source 구간을 비워 두거나, 비정본 제안서에서만 역할명으로 부른다.\r\n\r\n`assets/sound-cues.csv`의 `sound_id`는 `project.json`의 `audio_cues[].id`와 같게 쓴다. `start_s/end_s`는 최종 타임라인의 시작 포함/끝 미포함, `source_in_s/source_out_s`는 음원 파일 구간의 시작 포함/끝 미포함 초다. 샷 간 음악처럼 시퀀스 전체에 걸친 큐는 `shot_id`를 비워 둔다. 추가 실행 메타데이터는 버전이 있는 편집 산출물에 기록하고 `project.json`에서는 artifact/asset ID로 연결한다.\r\n\r\n각 큐에는 레이어, 파일, 적용 gain(dB), fade 길이, 믹스 자동화 메모, 동기 기준점/오프셋, 권리 상태를 연결한다. `sync_offset_s`는 실제 소리 사건 시각에서 화면 기준점 시각을 뺀 값이며, 음향이 먼저면 음수다. 자동화는 `mix_note`에 구간과 목표를 적는다. 단일 혼합 참조 음원은 `mixed_reference` 레이어로 기록하고, 없는 stem을 가정하지 않는다. 권리 상태는 `unknown`, `user_asserted`, `evidence_recorded`, `restricted` 중 실제 근거에 맞춰 쓰고, 증거 위치나 제한은 `mix_note`에 둔다. 표기만으로 권리 허가나 게시 승인을 의미하지 않는다.\r\n\r\n제품 공개·접촉·충격·전환을 음악에 맞출 때는 기준점을 `action_peak`, `reveal`, `cut` 등으로 이름 붙이고 기준 타임코드와 실제 오프셋을 측정한다. 허용 오차는 브리프나 승인된 검수 기준에서 가져오며 보편적인 임의 수치를 적용하지 않는다. 권리 미확인 음원은 검토본에 사용하더라도 상태와 게시 제한을 표시한다.\r\n\r\n비트 기반 그래픽·몽타주에서는 승인된 최종 오디오 마스터의 실제 박/다운비트/드롭 시각을 기준으로 삼고, 해당 파일·버전과 측정 근거를 편집 아티팩트에 연결한다. 초 단위 사건 시각은 타임라인 프레임레이트의 절대 프레임 경계로 변환하며, 반올림한 박 간격을 반복 누적해 드리프트를 만들지 않는다. 마스터나 프레임레이트가 바뀌면 종속 컷·그래픽 타이밍을 다시 계산하고 실시간 재생으로 확인한다. 박 기반 편집이 브리프 요구가 아니면 이 절차를 강제하지 않는다.\r\n\r\n동적 편집 검수는 전체 영상을 실시간으로 소리와 함께 재생하고, 필요한 경우 무음 화면·오디오 단독·전환 경계 프레임을 추가 확인한다. 표본 프레임만 확인했으면 전체 리듬이나 청취 품질을 통과로 판정하지 않는다.\r\n\r\n편집 명세는 실행기에서 해석 가능한 타임라인과 음원 계층을 제공해야 한다. 실제 편집은 별도 요청·승인과 사용 가능한 실행기 확인 뒤 수행하며, 계획표·스크립트 작성만으로 렌더 완료를 주장하지 않는다.\r\n\r\n## 오디오 의도와 실행 경로\r\n\r\n오디오 작업 전에 요청을 분류한다: 무음(`no_audio`) · 대사 없음(`no_dialogue`) · 효과음만 · 음악 제외 · 단일 혼합 참조. `project.json`의 `audio_mode`와 `audio_cues` 레이어를 그대로 재사용하고 새 enum을 만들지 않는다. 세부 의도는 편집 산출물과 큐 레이어로 기록한다:\r\n\r\n- `no_audio` — 오디오 큐를 두지 않는다. 무음 요청에 음악·효과를 추가하지 않는다.\r\n- `no_dialogue` — 말만 없다. 음악·환경·효과 큐는 유지되므로 무음이나 음악 제외로 해석하지 않는다.\r\n- 효과음만(SFX-only) — 대사 유무에 따라 `dialogue`/`no_dialogue`로 기록하되 큐는 SFX 계열 레이어만 둔다. 음악이나 대사를 암묵적으로 추가하지 않고, 생성 결과에 음악·말이 섞여 나오면 실패로 기록한다.\r\n- 음악 제외 — 음악 레이어를 두지 않는다. 지시 문법은 실행자의 실제 지원 제어로 쓴다; 제어가 없는 endpoint에 지원되지 않는 파라미터나 존재하지 않는 stem을 발명하지 않는다.\r\n- 단일 혼합 참조 — `mixed_reference` 레이어 하나로 기록하고 대사/음악/효과 분리를 약속하지 않는다. 분리 stem은 실제 소스가 제공할 때만 그 레이어로 기록한다.\r\n\r\n요청한 제외·구성을 endpoint가 실제 지원하지 않으면 가짜 지시를 넣지 않는다. 대신 영상 생성과 음향을 분리해 조립하는 경로(별도 음성/효과음 패스, 편집 단계 합성)를 비용·승인 범위와 함께 별도 제안하고, 승인 없이 새 음향 작업·분리·과금을 시작하지 않는다. 사용자가 지정한 음향 실행자·소스·방식은 조용히 대체하지 않는다.\r\n\r\n실제 오디오 결과는 요청한 의도와 대조해 청취 검수한다. 듣지 않은 구간은 미검증으로 두고, 청취 확인 없이 구성(말 없음·음악 없음·분리)이 맞다고 보고하지 않는다.\r\n\r\n## 음악·효과음 소싱과 권리\r\n\r\n카탈로그 또는 사용자 제공 파일에서 후보를 고를 때 브리프의 기능·감정·길이·동기 기준점에 맞춰 비교하고 비교한 기준을 남긴다. 실제 길이와 필요한 구간은 파일을 보고 맞춘다.\r\n\r\n선택 항목마다 실제 출처/트랙·파일 ID와 버전, 권리 근거, 확인 시점·위치를 연결한다. 구독·다운로드·접근 가능 URL은 게시 허가가 아니며, 플랜/프로젝트·채널·지역·기간 제한은 해당하는 것만 `mix_note`나 연결된 편집 산출물에 기록한다(`sound-cues.csv` 필드를 늘리지 않는다). `rights_status`는 실제 근거에 맞춰 쓰고 출처 URL만으로 상업적 사용을 통과시키지 않는다. 권리가 제한되거나 불명이면 게시 가능으로 주장하지 않고, 차단되는 범위와 준비 가능한 범위를 나눠 보고한다. 구매·구독 가입·게시는 자동으로 하지 않고 사용자 승인을 받는다.\r\n\r\n선택한 음원은 실제로 들어서 후보 비교가 실제 소리와 맞는지 확인한 뒤 `source_in_s/source_out_s`, fade, gain, `sync_anchor`/`sync_offset_s`를 측정해 기존 편집 표와 `sound-cues.csv` 필드에 맞춘다. 측정하지 않은 구간·동기는 추정으로 표시한다.\r\n\r\n## 후반작업 단계 추적 (영화 라이프사이클 요청 시)\r\n\r\n영화·단편 요청으로 [28](28-film-production-lifecycle.md)의 05 Post-production이 배정됐을 때, 선택된 후반 단계만 단계 표로 추적한다. `assets/film-postproduction-template.md`를 사용하고, 이 표는 `project.json` artifact/dependency/version과 `asset_registry`를 참조하는 인계 문서지 새 원장이 아니다.\r\n\r\n**단계 목록** — 각 단계는 개별 artifact로 버전을 단다: 인제스트/싱크 → 어셈블리 컷 → 러프 컷 → 파인 컷 → 픽처 락 → VFX → ADR → Foley → 사운드 디자인 → 스코어/음악 편집 → 사운드 믹스 → 컬러 그레이드 → 자막/크레딧 → 마스터링 → 최종 QC. 미적용 단계는 N/A와 이유를 적고, 겹치는 단계는 의존 대상의 버전을 남긴다. 순서는 [23](23-finishing-platform.md)의 의존 순서와 맞춘다 — 그레이드와 최종 믹스는 픽처 락 이후, 마스터링은 그 이후다.\r\n\r\n각 행은 다음을 기록한다: 단계 artifact ID·버전, 입력 테이크/미디어의 artifact·asset ID와 버전(잠금 입력의 경우 그 잠금 버전), 상태, 실제 출력 locator, dependencies, 검수 evidence, 미해결 이슈, 미검증 범위.\r\n\r\n**상태 규칙** — `project.json` artifact 상태(draft/reviewed/approved/generated/verified/stale)를 그대로 쓰고 새 enum을 만들지 않는다. 계획·설계는 draft/reviewed로 두고, 실제 출력 파일이 생기기 전에는 generated/verified로 올리지 않는다. 편집 계획·큐 표·믹스 노트만으로 렌더/믹스/마스터 완료를 주장하지 않는다. 픽처 락도 실제 승인된 컷 버전이 있을 때만 기록하고, 계획된 잠금 날짜를 잠금으로 취급하지 않는다.\r\n\r\n**단계별 인계 규칙**\r\n\r\n- 인제스트/싱크: 선택 테이크(촬영 로그·`generation_attempts`의 실제 accept 결과)만 입력으로 연결한다. 실제 파일·asset_registry ID와 동기화 근거(싱크 오프셋·클립·타임코드 일치)를 검수 evidence로 남기고, 싱크를 확인하지 않은 클립은 unverified로 둔다. 계획되거나 기대된 테이크를 인제스트된 입력으로 섞지 않는다.\r\n- 어셈블리/러프/파인 컷: 각 컷은 별도 버전의 artifact다. 입력은 이전 컷 버전과 해당 테이크 버전이며, 상위 입력 변경 시 실제 의존 후속 컷만 stale로 표시한다.\r\n- VFX: [21](21-generated-video-qa-retry.md)의 VFX·합성 수퍼비전 절차를 사용하고 레이어/소스 버전·실제 comp 결과물을 기록한다. VFX 작업을 자동 실행하거나 플레이스홀더를 완성물로 보고하지 않는다.\r\n- ADR/립싱크: [22](22-dialogue-lipsync.md)의 보이스 선택·청취·립싱크 절차를 사용하고 실제 생성/녹음 음성의 ID·버전·청취 결과를 연결한다. 듣지 않은 음성은 미검증으로 인계한다.\r\n- Foley·사운드 디자인·스코어/음악 편집: 위 `sound-cues.csv`와 오디오 의도 절차로 큐를 기록한다. 소싱은 \"음악·효과음 소싱과 권리\"의 근거 절차를 거치며 권리 미확인 음원을 게시 가능으로 주장하지 않는다.\r\n- 사운드 믹스·컬러 그레이드·자막/크레딧·마스터링: [23](23-finishing-platform.md)의 피니싱 의존 순서와 [15](15-delivery.md)의 자막·규격 절차를 따른다. 실제 믹스/그레이드/마스터 출력 파일 locator와 버전을 기록하고, 계획 단계에서는 해당 출력을 빈 칸·미완으로 둔다.\r\n- 최종 QC: QC 체크리스트는 계획 단계에서도 만들 수 있지만, 실제 pass는 해당 파일이 생기고 재생·청취·규격 검사를 거친 뒤에만 [12](12-qa.md)·[15](15-delivery.md)의 delivery_checks 근거로 기록한다. 체크리스트 존재를 검사 통과와 혼동하지 않는다.\r\n\r\n이 추적은 후반 단계의 계획·버전·검증 상태를 정리하는 것이며, 자동으로 VFX를 합성하거나 ADR·음악을 생성하거나 익스포트·업로드를 수행하지 않는다. 실제 매체 작업은 별도 승인·실행자 확인 뒤에만 수행한다.\r\n\r\n## 심화 참조\r\n구간별 유지 지도·컷 대체(유지 진단)는 [콘셉트·감정·유지](16-concept-emotion-retention.md) §3, 소리의 서사 기능과 피니싱 믹스 순서는 [피니싱·플랫폼](23-finishing-platform.md).\r\n\r\n\r\n## 소리의 서사 기능\r\n소리는 장식이 아니라 내러티브 정보다. 큐마다 최소 하나에 답한다: 어떤 정보를 더하는가 · 어떤 감정을 만드는가 · 어떤 전환을 동기화하는가.\r\n- 공개 전 화면 밖 원인을 알린다.\r\n- 컷을 가로지르는 공간 연속성을 만든다.\r\n- 인물의 몸/마음으로 관점을 좁힌다.\r\n- 모티프로 기억이나 반복 아이디어를 신호한다.\r\n- 아이러니나 불안을 위해 화면과 모순된다.\r\n- 컷을 숨기거나 전환을 동기화한다.\r\n- 추가가 아니라 제거로 임팩트를 만든다.\r\n- 샷 길이와 독립적으로 체감 속도를 통제한다.\r\n- Foley로 재질 질감을 세운다.\r\n- 구체적 앰비언스로 장소를 믿게 한다.\r\n\r\n레이어(대사 · 핵심 효과 · Foley · 앰비언스 · 음악 · 침묵)를 쌓되 모든 층을 계속 채우지 않는다. 침묵을 이벤트로 만들려면 먼저 소리를 세운 뒤 뺀다. 음악은 매 문장이 아니라 감정 전환을 점수화하고, 중요 장면은 음악을 꺼서 시험한다. 큐 지도는 타이밍 의도를 적고 저작권 곡의 모사를 요구하지 않는다.\r\n\r\n=== 10-evidence ===\r\n# 광고·설명·데이터 영상 근거\r\n\r\n## 입력과 산출물\r\n입력: 실제 데이터·자료, 관객의 질문, 영상 주장\r\n\r\n산출물: 주장 원장, 증거 샷, 차트 지시, 브리프가 요구하는 경우 CTA/고지\r\n\r\n## 실행 절차\r\n1. 주장·관찰·해석·가정·창작을 분리한다. 수치의 기간·모집단·분모·단위·출처 위치를 기록한다.\r\n2. 데이터→비교 정보→상황 해석→가능한 행동으로 연결한다. 상관관계를 인과관계로 표현하지 않는다.\r\n3. 비교는 막대, 시간 변화는 선 등 질문에 맞는 정확한 시각화를 사용한다. 축 절단·기간 선택·불확실성이 결론을 왜곡하는지 검토한다.\r\n4. 자료가 없으면 필요한 자료와 임시 문구를 제시한다. 가짜 차트·후기·인터뷰로 빈칸을 채우지 않는다.\r\n5. 시각 은유와 감정적 사례는 이해를 돕는 수단으로 사용한다. 일부 첨부 서적의 뇌과학·기억 효과 숫자를 검증된 과학 주장으로 재사용하지 않는다.\r\n6. 발화·차트·자막 및 요청된 CTA/고지에 같은 claim_id를 연결하고 단서가 잘리거나 발화보다 늦게 나타나지 않는지 검수한다. CTA는 요청된 목표 행동과 목적지가 있을 때만 추가한다.\r\n\r\n### 광고의 시각 은유·문구·근거 분리\r\n\r\n은유·카테고리 농담·창작 문구는 `claim-ledger.csv`의 기존 `statement`/`kind`/`limitations` 필드로 사실 주장과 구별한다. 새 claim class/enum은 만들지 않는다. 병원처럼 보이는 배경, 포장 문구, 원재료의 시각 여정은 효능·원산지·이력·실제 제품 사용을 증명하지 않는다. 원료→표기→운송→수령의 화면 순서는 창작 이야기로 제안할 수 있지만 원산지·식품 안전·규제 품질 표현에는 그 시각 순서와 별개인 근거가 필요하다.\r\n\r\n레퍼런스 영상에서 직접 읽은 화면 문구와 새로 계획한 카피를 구분한다. 화면 문구는 `OBSERVED`와 원본 locator, 제작자 설명은 `DECLARED_UPLOADER_CLAIM`, 자동 캡션은 `CAPTION_TEXT_AUTO_UNTIMED`, ASR 결과는 `ASR_RUN / HYPOTHESIS_UNVERIFIED`로 기록한다. 어느 유형도 미청취 발화의 시각·부재, 주장의 증명, 재사용 권리로 바꾸지 않는다. 자세한 근거 등급은 [25 레퍼런스 영상 분해](25-reference-video-analysis.md)를 따른다. 프레임을 읽는 검수와 음성 청취는 별도다.\r\n\r\n인물·장소가 실제 서비스·고객·후기로 읽힐 수 있으면 허구와 실재, 주장, 대상 관객, 사용 허가를 나눠 검토한다. 생활양식 장면은 위치·평면도·서비스 품질·점유율의 증거가 아니다. 아동이 실제로 등장하면 보호자 동의·복지·연령에 맞는 관객/맥락을 검토하되, 아동 옆의 건강 관련 범주 로고만으로 성행위·제품 사용이나 자동 차단 사유를 추론하지 않는다. 구체적인 권리·안전 위반은 기존 검토/중단 절차에 따른다.\r\n\r\nCTA는 브리프에 목표 행동과 목적지가 있을 때만 주장 수신자와 연결한다. 필수 고지나 주장 제한 문구가 있으면 최종 화면에서 읽히는지 검수하고, 이를 가리는 엔드카드/후속 장면을 수정한다.\r\n\r\n## 완료 조건\r\n각 주장에 확인 가능한 근거가 있는가? 수치·단위·자막·해석이 일치하는가?\r\n\r\n## 근거와 적용 범위\r\n자료 ID: 24,26,27,28,29,30,32,34,35. `sources.md`에서 파일 상태와 탐색 위치를 확인한다. 절차와 템플릿은 여러 자료의 개념을 결합한 독자 설계다. 저자의 규칙을 그대로 재현한 요약이나 공식 인증된 방법론으로 표현하지 않는다.\r\n\r\n## 출력 템플릿\r\n`assets/10-evidence-template.md`를 복사해 채운다.\r\n\r\n=== 19-brand-product-integration ===\r\n# 스폰서·제품 통합 (온디맨드 심화)\r\n\r\n모듈 13(아이디어·브랜드)과 10(근거·주장 원장)의 심화. 드라마·코미디 시리즈·스킷·크리에이터 영상 안에 광고를 자연스럽게 넣거나, 제품 자체가 정확하게 보여야 하는 영상에 연다.\r\n\r\n## 1. 스토리 네이티브 광고 통합\r\n\r\n제품이 이야기에 원주민처럼 느껴지게 한다. 브리프가 명시적으로 단절형 광고를 원하지 않으면 죽은 광고 블록을 붙이지 않는다.\r\n\r\n1. 스폰서 요구를 추출한다: 제품/서비스명·필수 주장과 금지 주장·필수 노출 비주얼·CTA/고지 요구·톤 제약. 필수/금지 주장은 모듈 10의 claim 원장에 claim_id로 연결한다.\r\n2. 이야기 체계를 추출한다: 인물·진행 중인 갈등·감정 판돈·장르 톤·세계 논리.\r\n3. 이야기 호환 제품 기능을 찾는다: 제품이 현재 상황을 해결하거나·복잡하게 하거나·드러내거나·유혹하거나·상징적으로 반영한다.\r\n4. 통합 모드를 고른다:\r\n   - 플롯 장치: 제품이 다음 사건을 일으키거나 현재 장애를 해결한다.\r\n   - 인물 의식: 인물이 반복 맥락에서 자연스럽게 쓰는 제품.\r\n   - 공개 도구: 제품이 숨은 정보·정체성·감정을 드러낸다.\r\n   - 코믹 해결사: 우스운 문제에 대한 지나치게 진지한 해결책.\r\n   - 브랜디드 우회: 세계가 자의식적으로 광고 개그를 위해 멈췄다가 복귀한다. 자의식적 단절이 해당 콘텐츠 문법일 때만 사용한다.\r\n5. 진입 순서를 쓴다: 선행 문제/질문 → 제품의 자연스러운 도착 → 사용/시연 비트 → 브랜드 보상 → 본편 복귀 전환.\r\n6. 인물 진실을 지킨다. 진지한 전사가 갑자기 영업 멘트를 하지 않는다 — 그 단절 자체가 의도된 개그일 때만 예외.\r\n7. 고지는 정책·신뢰와 양립하는 최소 손상 위치에 넣는다. 불편하다고 고지를 삭제하지 않는다.\r\n8. 정확한 제품 비주얼·패키지 요구는 아래 제품 SSOT 절차로 보낸다.\r\n9. 분리 테스트: 제품을 빼 본다. 장면이 완전히 붕괴하면 통합이 과의존, 아무 변화가 없으면 통합이 너무 약하다.\r\n\r\n### 통합 점검 목록\r\n\r\n- 인물이 스폰서 없이도 이 말/행동을 할 수 있는가?\r\n- 제품 도착이 장면 안에서 성립하는가?\r\n- 스폰서 이점이 한 번의 시청으로 읽히는가?\r\n- 고지가 존재하는가?\r\n- 이후 본편이 매끄럽게 재개되는가?\r\n\r\n### 규칙\r\n\r\n- 의료·법률·성능 주장을 지어내지 않는다. 확인된 주장만 claim 원장에 verified로 둔다.\r\n- 이야기를 멈추고 살균된 기능 나열을 하지 않는다 — 명시 요청 시만.\r\n- 일반 시연 문구보다 인물 특유의 사용법을 우선한다.\r\n- 제품이 코미디를 만들 수는 있지만 광고가 시청자를 굴욕시키지 않는다.\r\n\r\n## 2. 제품 비주얼 디렉팅\r\n\r\n제품을 일반 소품이 아니라 통제된 주인공 에셋으로 다룬다.\r\n\r\n1. 제품 SSOT를 만든다: `assets/product-ssot-template.md`. 치수/비율·실루엣·로고·라벨 배치·캡/마개·재질·색·표면 마감·투명도·내용물 질감·사용자가 제공한 법적 필수 표기.\r\n2. 정확한 제품 표현과 개념적 성분/효능 시각화를 분리한다. 뒷받침되지 않은 효능을 암시하지 않는다.\r\n3. 샷 기능을 고른다: 도입 → 촉감 클로즈업 → 추상 매크로 → 제품 히어로 → 사용/결과 → 정확한 팩샷 → CTA/엔드카드. 브리프가 요구하는 기능만 쓰며 CTA/구매 경로는 명시적으로 필요할 때만 둔다.\r\n4. 재질별 조명을 설계한다:\r\n   - 유광: 통제된 긴 하이라이트와 깨끗한 반사.\r\n   - 반투명: 배후/가장자리 조명과 내부 밀도.\r\n   - 크림/액체: 점성·표면 장력·질감·접촉.\r\n   - 금속: 반사 환경 자체가 겉모습이다.\r\n   - 반사 제품(거울·유리·금속): 무엇이 반사되는지, 제품 회전/카메라 이동 중 반사 띠가 어떻게 이동하는지, 라벨·로고의 읽기 영역을 먼저 정한다. 정확한 artwork는 제품 면의 불변 레이어로 잠그고, 반사 패스가 문자를 복제·뒤집어 가짜 라벨을 만들지 않도록 가림/보호 영역을 둔다. 관찰 프레임에서 반사 방식이 확인되지 않으면 실제 반사광으로 추정하지 말고 graphic/reflection design으로 표시한다. 전·중·후와 실제 크롭에서 표시/실패를 확인한다.\r\n   - 피부: 질감이 믿을 만해야 하며 의도적 스타일화가 아니면 플라스틱 스무딩을 피한다.\r\n5. 생성 모델의 텍스트/로고 충실도가 불안정하면 승인된 패키지 아트워크를 정확히 맞는 제품 면에 합성하거나 제품을 별도 레이어로 만든다. 합성은 허용되지만 action scene에서 source packshot 전체를 배경 위에 평면으로 얹지 않는다. 원근·면 방향·스케일·광원·반사·접촉 그림자·가림을 통합해 실제 공간의 물체로 읽혀야 한다. 제품을 쥐거나 열거나 도포하는 컷은 손과의 접촉/소유 상태 변화를 보여준다. 정면 packshot 합성은 계획된 frontal hold에 한해 사용하며 정확한 로고·법적 문구는 승인 아트워크로 보존한다.\r\n6. 손/피부/도포의 접촉은 [생성 영상 QA·재시도](21-generated-video-qa-retry.md)의 모션 절차, 모델 연속성은 [비주얼 모드·SSOT](20-visual-mode-ssot.md)로 라우팅한다.\r\n\r\n7. 액체 튐·물방울·성분 세계·불가능한 매크로 전환은 레이어 합성 계획으로 분리한다.\r\n8. QA: 실루엣·캡 형상·로고 위치·라벨 문구·재질·내용물 수위·색·손 접촉·최종 팩샷.\r\n\r\n### 분리형 부품의 상태·소유 인계\r\n\r\n제품을 열거나 캡 등 분리형 부품을 떼어 내는 경우, 제품 SSOT의 `캡/마개`와 불변 속성은 제품 아이덴티티를 고정하는 데 쓰고, 상태 전이는 기존 26 템플릿 행으로 기록한다. 실제 템플릿의 `대상 ID`, `시작 상태와 근거`, `끝 상태와 근거`, `후속 유지 범위 / 리셋 조건`, `동작 → 대상 변화 → 잔류 결과`, `검사한 동작/접촉 구간`을 연결하고, 샷/컷에서 어느 손이 제품과 분리 부품을 지지·소유하는지, 내려놓기/넘김이 어디서 일어나는지를 기존 `인물 블로킹`과 shot-local cue에 명시한다. 부품이 분리되면 명시적으로 놓거나 넘기기 전까지 소유 손에 남는다. 컷이나 화면 밖에서 부품/손의 상태가 저절로 바뀐 것으로 전제하지 않는다. 오프스크린 처리가 제품 물성에 영향을 주면 위치/후속 소유 상태는 `미확인`으로 두고 모순되는 샷 계획을 내지 않는다.\r\n\r\n제품 내용물·사용 뒤 피부/표면 잔류가 브리프나 승인된 자료에 특정되지 않으면 액적·광택·잔류를 사실/효능으로 만들지 않는다. brief가 창작된 시각 흔적을 요청하면 제안으로 표시하고 위치·시작/끝 상태·가림 뒤 유지 또는 명시적 reset을 기존 26 템플릿 행에 연결한다; 속성이 정해지지 않으면 `미확인`/`N/A`로 남긴다.\r\n\r\n### 형태·환경 은유를 제품 공개로 연결할 때\r\n\r\n제품을 늦게 드러내는 재료/풍경 순서는 필요할 때만 설계한다. 와이드 환경→가까운 표면/질감→일부 실루엣→제품·라벨에 서로 다른 정보 역할을 주고, 제안한 연결이 실제 컷·연속 이동·합성 중 무엇인지는 확인 전까지 단정하지 않는다. 제품 등장 뒤에는 SSOT의 실루엣·면·표식을 다시 회수한다. 풍경·반사·물방울은 방수/향/원산지/성능 증거가 아니다.\r\n\r\n제품과 세계의 형태를 맞출 때 **표면 대응**(원·곡선·색·질감)과 **의미 해석**(예: 힘·속도·향)을 따로 적는다. A03식 구체 대응이 필요하면 `assets/06-shots-template.md`의 기존 `공개 정보`, `관점·감정/구도 의도`, `카메라 동작`, `종료 프레임`에 양쪽 대상의 화면 위치·크기·방향·가림·질감 anchor, 대응 근거와 공개 시점을 기록한다. 시간상 대응에는 템플릿의 cue timeline을 쓰고, 별도 상태라면 기존 shot/panel row를 쓴다. 제안 전·중·후 frame에서 실제 변화가 읽히는지 계획/검수 상태를 구분해 확인하고, hard cut/dissolve/morph/mask 중 무엇을 쓸지와 대안을 비교한다. 전자는 화면 관계, 후자는 새 해석 제안이며 둘 다 주장을 증명하지 않는다. 시각 대응이 제품을 왜곡하거나 표식/라벨을 덮으면 단순 cut, 고정 하이라이트, 승인된 그래픽 레이어를 대안으로 검토한다.\r\n\r\n브리프에 불가능한 스펙터클이 있을 때만 그 진입·환상 범위·복귀를 정하고, 뒤 제품 히어로에서 승인된 스케일/라벨/조명/정체성을 재확립한다. 불·물·차량·섭취 등 위험하거나 불가능한 장면을 실제 사용법·안전성·제품 성능으로 오인시키지 않는다. 환상 신호가 충분하지 않으면 스펙터클을 제거하거나 비기능적 그래픽/애니메이션으로 바꾼다. 각 사례는 실제 관객·에셋·안전/권리 조건에 맞게 검토한다.\r\n\r\n산출물: 스폰서 요구 요약, 통합 모드, 이야기 호환 사용 사례, 광고 비트 맵, 필수 주장/비주얼 체크리스트, 고지 계획, 본편 복귀, 톤/신뢰 위험. 제품 영상은 추가로 제품 SSOT·시각 시퀀스·히어로 조명 계획·매크로/도포 통합한다.\r\n6. 반사와 그림자는 실제 표면과 움직임을 따른다. 일반적인 뜬 드롭 섀도를 피한다.\r\n7. 텍스트·로고·정확한 패키지는 생성 충실도가 부족하면 통제된 그래픽/제품 레이어로 유지한다.\r\n\r\n### 매칭 순서와 경고 신호\r\n\r\n형상 → 모션 → 조명 → 접촉 → 깊이 → 색 → 질감/그레인 → 광택. 경고: 떠 있는 피사체·흐린 플레이트 위 선명한 전경·불일치 셔터/모션 블러·다른 그레인 주파수·어울리지 않는 블랙 레벨·잘못된 광원 측·그림자 방향 불일치·틀린 환경 반사·안개 낀 장면의 완벽한 컷아웃 가장자리.\r\n\r\n전체 프레임과 클로즈 줌 둘로 검수한다: 가장자리 헤일로·불일치 블랙·불일치 그레인·틀린 블러·뜬 발·빠진 접촉 그림자·원근 불일치·불가능한 반사.\r\n\r\n## 3. 생성 매체 QA\r\n\r\n실제 매체를 판정하고 프롬프트를 판정하지 않는다. 파일이나 필요한 프레임/오디오가 없으면 해당 항목을 unverified로 남긴다.\r\n\r\n### 검사 순서\r\n\r\n실제 매체를 이 순서로 본다 — 부합(요청한 대상/행동/의도가 실제로 나왔는가) → 모션(접촉·균형·시간 안정) → 정체성(SSOT·제품 정확도) → 카메라(프레이밍·방향·공간) → 오디오(입·목소리·소리 원근) → 기술 규격(길이·화면비·해상도·프레임 무결성·필요 시 오디오 존재). 앞 단계의 blocker가 보이면 뒤 패스의 세부 미학 판정으로 넘어가지 않는다.\r\n\r\n### 검사 패스 (여러 모드로 본다)\r\n\r\n1. 정속 시청(소리 포함) 2. 정속 무음 3. 의심 구간 슬로/스텝 4. 시작·핵심 접촉·끝의 정지 프레임 비교 5. 샷 간 연속성 비교 6. 대사/소리가 중요하면 오디오만 듣기.\r\n\r\n- 정체성 패스: 승인 SSOT와 인접 샷에 대해 얼굴/몸/머리/털/의상/액세서리 비교.\r\n- 사물/제품 패스: 실루엣·비율·캡/부품·라벨·로고·스케일·손 접촉·반사·텍스트 가독성.\r\n- 모션 패스: 발과 손부터 본다. 예비·접촉·체중 이동·후속·충돌·미끄러짐·튐·해부 초과/결손·사물 영속성.\r\n- 시간 패스: 플리커·모핑·질감 기어감·불안정 그림자·사라지는 디테일·배경 호흡·서사와 무관한 조명 변화.\r\n- 카메라/공간 패스: 지평선·렌즈 느낌·원근·프레이밍·시선·화면 방향·동기 있는 움직임·편집이 요구한 시작/끝 상태.\r\n- 합성 패스: 가장자리·깊이 순서·접촉 그림자·광원 방향·그레인/노이즈·모션 블러·심도·블랙/화이트 레벨·대기 통합·반사 논리.\r\n- 연기/오디오 패스: 시선·표정 전환·반응 타이밍·대사 의도·입 타이밍·숨·멈춤·노이즈·클리핑·소리 원근과 화면 일치.\r\n\r\n### 판정\r\n\r\n이슈마다 `타임코드 → 관찰 → 관객 영향 → 심각도 → 추정 원인 → 권장 경로 → 재검수 기준`으로 기록한다. 심각도와 판정은 모듈 12의 blocker/major/minor와 pass/pass_with_notes/needs_revision을 사용한다. 생성 결함은 아래 재시도 절차로, 창작/서사 실패는 상위 모듈로, 정확한 그래픽과 레이어 통합은 합성 절차로 되돌린다. `assets/generated-qa-report-template.md` 사용.\r\n\r\n실제 매체를 검사하지 않고 가상의 품질 점수를 매기지 않는다. 사용자 제공 루브릭과 실제 검사가 있을 때만 점수를 쓴다.\r\n\r\n### 프리뷰 판정과 최종 검수\r\n\r\n실제 출력만 판정한다: 짧은 프리뷰는 뒤 구간의 동작·접촉·연속성을 증명하지 않으므로 보이지 않은 대상을 통과로 쓰지 않는다. 수락/수정/경로 변경은 [생성 경로·비용 라우팅](24-production-execution.md) §5의 프리뷰 계획 대상과 승격 경로로 되돌린다. 프리뷰 수락은 최종 승인이 아니며, 최종본의 동작·정체성·오디오·기술 규격은 다시 검수한다 — 같은 seed·입력의 재생성은 같은 동작을 보장하지 않는다.\r\n\r\n### 상태·인과 검수 (선택적)\r\n\r\n직접 또는 앞선 샷에서 이어받은 [상태·인과 슬롯](26-state-causality-continuity.md)이 있는 샷에 적용한다. 판정 enum과 실패 분류는 그대로이며, 여기서는 근거 위치와 미검증 구분만 추가한다.\r\n\r\n- **구간 검사**: 시작·끝 프레임이 달라 보이는 것만으로 원인 동작이 성립했다고 판정하지 않는다. 접촉/변화가 진행되는 구간을 실제로 본다. 구간을 보지 못했으면 전이를 unverified로 남긴다.\r\n- **후속 경계**: 선언한 유지 범위 안의 모든 해당 후속 컷 경계·재등장 상태를 문서화된 리셋까지 대조한다. 중간 정지 컷·가림도 의무를 지우지 않으며 의도적 리셋과 상태 리셋 오류를 구분한다.\r\n- **가림**: 가려진 동안 안 보인 특징을 상태 역전·삭제로 판정하지 않는다. 가림 전 관측과 재등장 관측을 비교하고, 재등장이 없으면 미확인으로 둔다.\r\n- **결합 응답**: 인계된 대상쌍이 있으면 양쪽의 응답을 각각 본다. 응답 구간을 검사할 수 없으면 unverified로 남기고, 검사했는데 요구된 응답이 실제로 빠져 있으면 모션/물리 실패로 분류해 needs_revision으로 되돌린다.\r\n- **생략**: 승인된 서사 생략은 전후 상태와 관객이 읽는 인과가 브리프를 충족할 때만 허용한다. 생략 표기만으로 필수 시연을 면제하거나 보이지 않은 동작을 증명하지 않는다. 생략된 동작 자체는 unverified로 남기고, 관찰된 필수 행동 누락은 needs_revision으로 되돌린다. 경계·인과 누락을 빠른 컷이나 음악으로 감추지 않는다.\r\n- 새 활성 조건과 상속된 유지 의무가 모두 없는 `N/A` 샷에만 이 패스를 적용하지 않는다.\r\n\r\n### 실행·상태 수명 주기\r\n\r\n선택 실행자의 실제 호출 계약(API·CLI·연결 도구 중 실제 것)으로만 승인된 범위를 제출한다. 비동기 작업은 그 도구의 대기/폴링 규칙을 따르고 실제 요청·작업·결과 ID와 대기 상태를 연결된 실행 산출물에 기록한다. 상태가 불명이면 먼저 그 도구의 상태 확인으로 결정하고, 실패·부분 성공을 그대로 보고한다 — 제출 성공 여부를 확인할 수 없을 때 다시 호출해 중복 실행·과금을 만들지 않는다. 실제 결과 파일을 받아 검사한 뒤에만 성공으로 기록한다. 자신의 검사와 사용자의 관찰 보고를 구분하고, 수정은 성공 속성을 보존한 채 한 번에 한 주요 변수만 바꿔 §5에 기록한다. 과거 시도 기록은 보존하며 입력 버전 변경 시 영향받는 종속 산출물·승인만 stale로 표시한다; 시도에 별도 stale 상태를 만들지 않는다.\r\n\r\n## 4. 완성 시퀀스의 모션·리듬·오디오 QA\r\n\r\n클립별 생성 QA를 통과한 것만으로 광고/몽타주의 역동성이나 편집 싱크를 승인하지 않는다. 완성 타임라인에서 확인한다.\r\n\r\n1. 편집본·오디오·타임라인의 artifact ID와 버전을 고정한다. 검사 범위(전체 재생, 표본 프레임, 오디오 단독)를 각각 기록한다.\r\n2. 역동성 요청이면 샷마다 실제 피사체 동작, 카메라 동작, 제품/정보 공개, 정지/정착 중 무엇이 시간에 따라 바뀌는지 적는다. 컷 속도나 디졸브만으로 모션을 대체했다고 판단하지 않는다.\r\n3. 실제 편집본을 정상 속도와 최종 믹스로 재생해 전체 페이싱·전환을 확인한다. 중요한 접촉·충격·제품 공개는 프레임/타임코드와 오디오 동기 기준점을 대조한다. 무음·오디오 단독 검수는 요청과 문제 유형에 맞게 추가한다.\r\n4. 샘플 프레임만 검사했으면 모션의 중간 프레임, 전환의 실제 길이, 전체 음악 적합성은 미검증으로 둔다. 청취하지 않은 음원의 품질이나 싱크를 통과로 쓰지 않는다.\r\n5. 오디오가 참조 영상의 단일 혼합 트랙이면 분리 BGM/SFX stem이 없음을 기록한다. 분석 도구가 찾은 파형 피크는 청취 판정이 아니며, 음원 권리는 별도 확인한다.\r\n6. 정지/거의 정지된 원본은 요청된 비트가 실제 움직임을 요구하는지 먼저 판단한다. 의도된 제품 히어로 홀드로서 화면 내용·가독성·타이밍이 이를 뒷받침할 때만 보존한다. 정지 상태라는 이유만으로 보조 컷이나 엔드카드 역할을 추정하지 않는다. 동작이 필요한 비트가 성립하지 않으면 더 강한 실제 동작 구간을 선택하거나 샷 교체안을 낸다. 확대/전환 효과만으로 움직임을 꾸며내지 않는다. 새 생성·유료 실행은 별도 승인과 기존 비용/재시도 상한을 따른다.\r\n\r\n보고에는 타임라인 범위·실제 검사 모드·도구/파일·관찰된 타임코드·미검증 항목·재검수 기준을 포함한다. `assets/generated-qa-report-template.md`를 사용한다.\r\n\r\n## 5. 인과 재시도 제어\r\n\r\n실패한 생성은 진단 문제다. 매번 전부 다시 쓰지 말고 가장 이른 통제 가능 원인을 고친다.\r\n\r\n### 실패 분류\r\n\r\n- 정체성: 얼굴 표류·신체 비율 변화·의상/액세서리 표류·종/연령 변화.\r\n- 제품/그래픽: 형태 표류·캡/라벨 변화·로고/텍스트 손상·재질 불일치·틀린 스케일.\r\n- 모션/물리: 초과 사지·발 미끄러짐·깨진 접촉·텔레포트·불가능한 균형·사물 관통·이상한 유체.\r\n- 시간: 플리커·모핑·질감 기어감·사라지는 사물·불안정 배경·불연속 조명.\r\n- 카메라/구도: 틀린 프레이밍·의도 없는 줌/팬·피사체 이탈·지평선/원근 불일치·시선/화면 방향 단절.\r\n- 연기: 틀린 감정·늦은 반응·입 불일치·죽은 눈·의도와 다른 제스처.\r\n- 합성: 나쁜 가장자리·빠진 접촉 그림자·틀린 깊이·불일치 블러/노이즈/색·스케일/원근 불일치.\r\n- 창작: 불명확 아이디어·약한 보상·중복 샷·낮은 감정 가치. 맹목적 재생성 대신 상위로 보낸다.\r\n\r\n### 실패 → 수정 매핑\r\n\r\n| 관찰된 실패 | 첫 수정 | 상승 경로 |\r\n|---|---|---|\r\n| 부합 불일치(요청한 대상/행동이 아님) | 프롬프트를 요청 의도·주 행동·끝 상태로 다듬기 | 샷 분할 → 모델 재라우팅 |\r\n| 모핑/시간 불안정·플리커 | 구간 단축·행동 단순화·참조 강화 | 세그먼트 분할 → 합성 |\r\n| 정확한 텍스트/로고 손상 | 반복 생성 중단, 승인 아트워크 합성 레이어 | 합성 경로 확정 |\r\n| 물리/접촉 붕괴 | 동시 행동 축소·접촉 분해·초기/끝 상태 명시 | 샷 분할 → 레이어 합성 모호 · 약한 참조 제어 · 과도한 행동 복잡성 · 모델 능력 불일치 · 나쁜 초기 프레임 · 연속성 의존 · 합성 필요 · 확률적 분산.\r\n4. 고칠 가능성이 큰 가장 작은 개입을 고른다. 실용적으로 한 번에 한 주요 변수만 바꾼다.\r\n5. 재시도 시 성공한 속성을 명시적으로 보존한다.\r\n6. 반복 실패 시 무차별 재시도 대신 상승한다: 행동 단순화 → 샷 분할 → 레이어 분리 → 모델/워크플로 변경 → 더 나은 참조 에셋 → 정확한 요소 합성 → 서사 목적을 유지한 샷 재설계.\r\n7. 재시도 예산을 지킨다. 다음 생성의 기대 가치가 전략 전환보다 낮으면 멈춘다.\r\n8. 성공 설정이 재사용되도록 매 시도를 `project.json`의 `generation_attempts`에 기록한다(계약 v1.1). 샷 `retry_budget`은 승인된 `video_execution_plan`의 상한에서 온다.\r\n\r\n### 재시도 사다리\r\n\r\n프롬프트 명료화 → 참조/첫 프레임 교정 → 행동 단순화 → 길이/타이밍 조정 → 샷 분할 → 모델/워크플로 재라우팅 → 레이어 분리/합성 → 서사 목적 유지 샷 재설계.\r\n\r\n### 규칙\r\n\r\n- 한 번에 한 변수: 재시도마다 하나의 주요 변수만 바꾸고 변경 내용을 generation_attempts.changes에 남긴다. seed는 재현 힌트일 뿐 정체성·품질 보장 수단이 아니며, seed만 고정한 재시도를 원인 수정으로 세지 않는다.\r\n- 경계 있는 재시도: 샷 retry_budget과 승인된 실행 계획의 비용·시간 상한 안에서만 시도한다. 상한 초과 전에 전략 전환(분할/재라우팅/합성) 또는 unverified 보고로 닫는다.\r\n- 관객이 인지하는 연속성 실패를 빠른 편집으로 숨기지 않는다.\r\n- 정체성 표류를 수십 개 형용사로 고치지 않는다: 정규 참조를 강화하고 상충 지시를 줄인다.\r\n- 정확한 텍스트/로고는 반복 생성보다 합성을 우선한다.\r\n- 접촉 중심 물리는 동시 행동을 줄이고 초기/접촉/끝 상태를 정의한다.\r\n- 생성 실패와 창작 실패를 구분한다. 완벽히 렌더링된 지루한 샷은 재시도가 아니라 콘셉트/편집으로 돌아간다.\r\n\r\n=== video-production-assets/references/25-reference-video-analysis.md ===\r\n# 레퍼런스 영상 분해 (온디맨드 심화)\r\n\r\n모듈 01·05·06·09의 공통 심화. 사용자가 단일 영상·클립·광고·릴스·숏·영화 장면·시각 레퍼런스의 제작 원리를 추출해 달라고 하거나, 여러 비디오가 있는 폴더/아카이브를 전부 분석해 포트폴리오 패턴·스킬 커버리지·갭을 비교해 달라고 할 때 연다. 보호된 표현의 복제가 아니라 이전 가능한 제작 원리를 추출한다.\r\n\r\n## 레퍼런스 발견과 선택\r\n\r\n\"레퍼런스를 찾아 달라\"는 요청에는 후보 제안과 상세 분석을 분리한다. 상세 분석은 사용자가 후보를 선택·승인한 뒤에만 시작한다.\r\n\r\n1. 후보마다 셋을 적는다: 확인 가능한 만큼의 식별자/출처(제목·채널·링크), 해당 채널·관객과의 적합성, 이 브리프에 이전 가능한 구체적 요소 하나.\r\n2. 후보 단계에서는 후보를 제시할 만큼의 공개 메타데이터·미리보기만 본다. 선택되지 않은 자료를 전체 시청하거나 상세 분석하지 않는다.\r\n3. 사용자가 영상·링크·폴더·아카이브를 직접 제공하고 분석을 요청한 경우 이미 선택된 것으로 보고, 별도 승인 없이 바로 분석한다.\r\n4. 선택된 자료를 분석하는 읽기와 재사용·외부 업로드·유료 분석·생성 권한을 구분한다. 분석 요청만으로 외부 전송이나 과금을 승인받았다고 보지 않고, 해당 단계는 기존 승인 범위가 있을 때만 수행한다.\r\n\r\n## 절차\r\n\r\n1. 형식·길이·화면비·장르·관객·목적을 파악하고 실제로 검사한 소스 버전/구간을 기록한다. 영상 전체를 보지 못했으면 분석 범위와 표본 구간을 먼저 밝힌다.\r\n2. 샷 또는 의미 있는 시각 비트로 분절한다. 실제 컷 시점은 측정하고, 측정할 수 없으면 근사치로 표시한다.\r\n3. 비트마다 피사체·행동의 시작/끝 상태·주요 동작 정점(접촉·충격·제품 공개 등)·프레이밍/스케일·카메라 무빙·조명·팔레트·연기·전환·연속성을 기록한다. 프레임이나 타임코드로 관찰할 수 없는 내용은 추정으로 둔다.\r\n4. 같은 타임라인에 컷 지점·전환 종류와 길이·음악/효과 큐를 놓는다. 화면 변화와 소리의 동기점은 실제 시각·타임코드로 적고, 확인할 수 없는 정밀도는 만들지 않는다.\r\n5. 참조 음원이 분리 stem인지 단일 믹스인지 구분한다. 혼합 음원만 있으면 음악과 효과음을 분리해 들었다고 표현하지 않고, 재사용 권리는 별도 미확인으로 기록한다.\r\n6. **표면 스타일**(의상·팔레트·질감·세트 장식)과 **구조 논리**(정보 공개 순서·스케일 변화·동작/카메라 동기·감정 전환·컷 리듬)를 분리한다. 역동성은 컷 수나 전환 효과가 아니라 실제 피사체/카메라의 시간적 변화와 그 배열로 설명한다.\r\n7. 발견을 재사용 가능한 제작 레시피로 변환한다. 원리는 보존하고, 사용자가 소유하거나 재사용을 허가하지 않은 캐릭터·사건·브랜드 에셋·장소·대사·특정 보호 디자인은 바꾼다. 전문 문제는 아래 경로로 라우팅한다.\r\n### 원본 위치·경계·분석 ID의 증거 수준\r\n\r\n아카이브 감사에서는 `archive_id`를 source의 안정된 identity로 사용하고, 원본 장·분석에서 쓰는 locator를 프로젝트의 `scene_id`, `shot_id`, `panel_id`로 승격하지 않는다. `C##`는 detector candidate/neighborhood, `B##`는 관찰 블록, `G##/SG##`는 장면 해석, `S##.P##`는 source shot 안의 action phase를 나타낼 수 있다. 숫자와 접두어만으로 종류를 추정하지 말고 해당 source의 legend를 따른다.\r\n\r\n검출 점수나 프레임 차이는 `DETECTOR_CANDIDATE`다. 후보 하나, contact sheet, 1fps/native sample, 성공한 전체 decode도 컷 경계 검증이 아니다. `SH###`는 경계 양쪽의 원본 증거로 컷을 실제 확인했을 때만 사용하고, 표본 사이의 경계는 bracketed `ESTIMATED` 또는 `UNKNOWN`으로 남긴다. Scene, shot/cut, 한 shot 안의 여러 action phase를 따로 세며 dissolve/morph/wipe가 미확정이면 transition candidate라 한다.\r\n\r\n각 locator에는 요청 시각(`requested_s`)과 실제 source frame PTS(`source_pts_s`)를 구분해 기록한다. PTS는 샘플 프레임 위치이지 정확한 cut time이나 action onset이 아니다. 같은 시각의 화면 텍스트는 `OBSERVED`로 쓸 수 있지만 실제 speech timing/부재는 청취가 필요하다. Uploader pipeline/tool credits는 `DECLARED_UPLOADER_CLAIM`; 자동 캡션은 `CAPTION_TEXT_AUTO_UNTIMED`; ASR는 `ASR_RUN / HYPOTHESIS_UNVERIFIED`; 미청취 오디오·미검사 구간은 `UNKNOWN`이다. Frame review ≠ continuous playback; stream metadata ≠ listening.\r\n\r\n새 브리프에 옮길 때는 관찰한 source locator와 새 계획의 proposed timing/IDs를 다른 열에 둔다. `assets/shot-dna-template.md`의 source scope, observed/estimated/unknown, transfer chain, reusable mechanism fields를 쓰고, 확인할 실제 생성/렌더/재생은 담당 모듈에 넘긴다. 분석은 컷 전체 인증·제작 경로/권리·효능·성과 승인이 아니다.\r\n\r\n### 제작 레시피 연계\r\n\r\n레퍼런스의 메커니즘은 새 브리프에만 적용한다. 순서 · 샷/구도/카메라 · 비주얼 스타일 · 사운드 · 서사/감정 효과. 축마다 **관찰**(직접 확인한 프레임·재생·청취 또는 출처를 밝힌 사용자 관찰 기록), **해석/추정**(관찰에서 유도한 의도·기능), **미확인**(범위 밖·권리·성과)을 분리한다. 사용자 기록을 직접 검사로 표현하지 않는다. 확인할 수 없는 타임코드·오디오 내용·재사용 권리·성과 수치를 만들지 않고, 점수나 자동 합격 판정을 붙이지 않는다.\r\n\r\n## Shot DNA 필드 (중요한 것만 채운다)\r\n\r\nshot_id/근사 또는 측정 시간 · 서사 기능 · 피사체/행동의 시작-정점-끝 · 샷 크기/앵글 · 카메라 무빙/동기 · 조명/색 · 컷/전환 · 음악/효과 큐와 동기점 · 연속성 · 관찰/추정 구분 · 시점(앞/뒤/측면, 다른 각도·거리)에서 보여주거나, 브리프가 특정 구도·공간·광학 느낌의 정확한 재현을 요구할 때만 적용한다. 해당하지 않으면 `N/A`로 닫고 분위기 참조만으로 이 절차를 채우지 않는다.\r\n\r\n**같은 특징의 시점 대응.** 시점 사이에서 같은 특징만 짝짓는다 — 같은 얼굴·면·바느질·개구부·접촉점처럼 대응이 성립하는 특징을 연결하고 각 쌍에 `관찰 / 가림 / 미확인`을 표시한다. 가려져서 안 보이는 특징을 없다고 단정하거나 형상 변화·복원으로 해석하지 않는다. 가림 전 마지막 관측과 재등장 시점의 관측을 구분해 기록하고, 재등장하지 않으면 미확인으로 남긴다. 가림 때문에 안 보이는 면의 특징을 다른 시점 관찰 없이 만들지 않는다.\r\n\r\n**광학 역추정(정확한 재현 요구 시).** 역추정의 입력은 픽셀 수치가 아니라 화면 정규화 기준점이다: 소실점·지평선 높이·피사체의 화면 대비 크기·보이는 면의 수·가장자리 왜곡·상대 크기 관계처럼 해상도와 무관하게 관찰되는 것을 적는다. 알려진 크롭·출력 화면비는 추정 입력이 아니라 제약으로 기록하고, 크롭 여부가 미확인이면 그 사실을 명시한다. 각 항목을 **관찰**(프레임에서 직접 읽은 값)/**추정**(관찰에서 유도한 가설)/**미확인**(스케일·기기·위치 정보 부재)으로 분리한다.\r\n\r\n한 프레임과 물체 크기 미상 조건에서 카메라 해는 단일이 아니다 — 여러 초점거리·거리·크롭 조합이 같은 화면을 만들 수 있다. 물리 렌즈·센서·거리의 확정값을 만들지 않고, 관측과 양립하는 **후보 범위**와 그 근거를 적는다(예: 압축된 원근은 긴 초점거리+먼 거리 조합과 크롭 모두와 양립). 후보 사이를 실제로 가르는 관측이 무엇인지(민감도)와 반증·확정에 필요한 추가 증거(다른 시점 프레임·파랄랙스·EXIF/제작 기록·알려진 크기의 기준 물체)를 함께 기록한다. 새 제작으로 넘기는 목표는 확정 카메라 값이 아니라 관찰된 화면 특성(원근 압축·심도·왜곡·피사체 화면 대비)이다.\r\n\r\n수치 카메라·공간 명세의 설계와 실행은 `$camera-spatial-design`이 담당한다 — 여기서는 역추정의 근거와 불확실성만 기록해 넘긴다. 대응표와 역추정 제약은 [상태·인과·연속성 인계](26-state-causality-continuity.md)의 시점 대응·역추정 근거 슬롯으로 이어 줄 수 있다.\r\n\r\n\r\n## 아카이브 일괄 분석\r\n\r\n폴더/아카이브의 전수 영상 분석 또는 포트폴리오 갭 검토는 단일 레퍼런스 분석과 구분한다. 요청된 영상 범위만 읽고, 요청이 분석이면 원본 수정·외부 업로드·생성·게시 없이 분석한다.\r\n\r\n1. 영상 파일을 전부 열거하고 사용자 제공 게시물 ID/캡션과 파일을 연결한다. 발견·요청·실제 분석한 개수를 분리하고, 열 수 없는 파일은 미분석으로 남긴다. 게시물 캡션은 영상 프레임의 관찰로 취급하지 않는다.\r\n2. 각 영상을 개별 항목으로 다룬다. 길이·프레임 크기·화면비·알려진 스트림 메타데이터와 실제 확인한 시각/구간을 `assets/archive-audit-template.md`에 기록한다. 아카이브 요청이면 템플릿의 source별 analysis라 하지 않는다. 의미 있는 비트는 `assets/shot-dna-template.md`에 연결한다.\r\n3. 각 영상별 직접 관찰·사용자/게시 메타데이터·해석·미확인을 구분한다. 표본 프레임만 본 경우 전체 순서·컷 리듬·모션을 확정하지 않는다. 오디오 스트림 정보만으로 실제 대사·음악·효과음·품질을 주장하지 않는다.\r\n4. 영상별 분해가 끝난 뒤 반복·대조 패턴을 집계한다. 해당 패턴을 뒷받침하는 파일 수와 실제 확인 범위를 함께 적고, 조회수·유지율·전환 데이터가 없으면 성과 판단으로 확장하지 않는다.\r\n5. 각 갭 후보를 현재 스킬의 정확한 참조/절차와 대조해 `이미 커버`, `부분 커버`, `갭 후보`, `증거 부족`으로 분류한다. 누락된 키워드만으로 기능이 없다고 판단하지 않는다.\r\n6. 실제 갭만 수정 후보로 제안하고 기존 절차의 중복 복사를 피한다. 미확인 영상에서의 부재·캡션 불일치·권리 문제를 확정하지 않는다.\r\n\r\n## 재사용 규칙 추출\r\n\r\n\"정확히 이 산과 의상을 쓴다\"보다 \"얼굴 클로즈업에서 극와이드로 잘라 규모를 드러낸다\" 같은 규칙을 우선한다. 오프닝 문법·에스컬레이션 패턴·보상
