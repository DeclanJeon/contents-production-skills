video-production-assets\\references\\contract.md\r\n# 공통 제작 계약 v1.1\r\n\r\n## ID와 단위\r\n- project_id는 프로젝트 내 고유값으로 정한다. scene_id S01, beat_id B01, shot_id SH01, character_id CH01, claim_id CL01, sound_id AU01, artifact_id A01 형식을 권장하되 기존 체계를 우선한다.\r\n- 시간은 초 단위 숫자로 기록한다. 최종 타임라인은 start_s 포함 / end_s 미포함이다. fps는 초당 프레임 수다. 프레임 범위는 시작 포함 / 끝 미포함이며 길이는 (end-start)/fps다.\r\n- 생성/촬영 원본 길이 source_duration_s와 최종 편집 구간 길이를 구분한다. final 구간은 겹치지 않는다. 전환과 오디오 중첩은 별도 레이어 큐로 표현한다.\r\n- 기본 계약의 최종 영상 구간은 0초부터 target_duration_s까지 연속으로 덮는다. 블랙·정지·타이틀도 하나의 shot으로 기록한다.\r\n\r\n## 상태와 버전\r\n- artifact 상태: draft / reviewed / approved / generated / verified / stale.\r\n- approved는 실제 사용자 또는 위임된 승인 사실이 있을 때만 기록한다. generated는 실제 파일이 생성됐을 때, verified는 해당 파일을 검사했을 때만 기록한다.\r\n- 버전과 dependency를 기록한다. 상위 각본이 바뀌면 영향을 받는 샷과 계획을 stale로 표시한다.\r\n- `assets/project-template.json`의 빈 배열과 null은 작성 시작 상태다. 검사 통과 예제가 아니다.\r\n\r\n## JSON 구조\r\n필수: project_id, version, target_duration_s, fps, aspect_ratio, scenes, characters, shots, claims, artifacts.\r\nscenes: id, purpose. characters: id, locked_traits.\r\nshots: id, scene_id, character_ids, start_s, end_s, source_duration_s, purpose, start_state, end_state.\r\nclaims: id, statement, kind(fact/inference/fiction), source(실제 문서/데이터 위치), status(unverified/verified/fiction).\r\nartifacts: id, type, version, status, dependencies(artifact id 배열), evidence(검수 위치; verified 상태 필수).\r\n\r\n## 인계 최소값\r\n각 산출물에 입력 ID와 버전, 생성한 항목 ID, 가정, 실제 검증 결과, 다음 단계 미해결 사항을 붙인다. 재생성에는 바뀐 변수와 실패 타임코드를 남긴다. 같은 정보를 복사해 여러 문서에서 따로 변경하지 말고 공통 원장을 기준으로 조회한다.\r\n\r\n## Worker handoff and single writer\r\n\r\n현재 단계에 필요한 조각만 인계한다. 이 패킷은 일시적 실행 문맥이며 새 원장/스케줄러가 아니다. 단독 채팅 산출물은 project.json·프로젝트/산출물 ID를 새로 요구하지 않는다. 기존 프로젝트라면 선택된 `<project-root>/project.json`이 정본이고, 설치된 skill/support 폴더에는 제작 데이터를 쓰지 않는다.\r\n\r\n**입력 패킷:** 실제 project_root/project_id/project version(존재할 때), 한 개의 assigned stage와 requested output, 담당 artifact/entity/scene/shot/beat/panel/cue ID와 수정 범위, 소비하는 artifact ID→version, 필요한 소스/범위, 잠근 사실·연속성·제외 조건, 관련 승인 근거, 미해결 입력. 이미 확정된 값을 재질문하지 않고 다른 단계의 상세 문서를 미리 읽지 않는다. 별도 원장 없이 필요한 필드만 조회한다.\r\nsource/character/beat/provider ID는 artifact ID가 아니다. dependencies/dependency_versions/input_versions에는 **정본에 등록된 artifact ID만** 넣는다. 등록 여부를 확인하지 못한 입력은 source locator 또는 등록 제안으로 반환하며 실제 dependency라고 꾸미지 않는다.\r\n\r\n**워커 반환:** 담당 output ID와 output version, dependencies/dependency_versions 제안, 바뀐 레코드 제안, 실제 파일/공급자 locator와 관찰 상태·검수 근거/한계, 가정과 blocker. ID는 배정된 값 또는 명시적 신규 등록 제안으로 구분한다. 부족한 공간/음성/참조 입력은 scene/shot/beat ID별 요구 패킷 한 개로 반환한다. 워커가 총괄을 재호출하거나 현재 범위를 넓히지 않는다.\r\n\r\n**총괄만 작성:** 저장·변경이 허용된 기존 프로젝트에서 현재 입력 버전을 다시 읽고 stale 결과를 거부한다. 담당 변경과 해당 소유 artifact 버전만 반영하고 종속 승인만 stale로 표시한다. 저장 후 다시 읽어 검사하고 다음 배정 단계에 넘긴다. 워커는 project.json을 동시 수정하지 않는다. 텍스트만/저장 금지 요청은 반환 제안에서 끝난다. 초기 프로젝트 선택·초안 작성은 기존 프리프로덕션 절차이며, 아래 도구는 자동 생성/자동 실행 엔진이 아니다.\r\n\r\n- `python scripts/project_index.py <project-root>/project.json --shot SH06` 또는 `--artifact A01`: 정본에서 현재 샷의 scene/character/beat/panel/voice/audio/claim/asset와 provenance·artifact dependency를 읽는 **읽기 전용 조회**. 샷/산출물을 지정하지 않으면 전체 원장을 자동 로드하지 않는다. 결과는 전체 브리프나 실행 승인 대신 사용할 수 없다.\r\n- focused `project_index.py` 전달에는 panel pins, `required_asset_versions`, `master_asset_ref` 전체 계보, 활성 `look_asset_id`와 해당 에셋을 포함하고 무관한 샷/산출물은 제외한다.\r\n- `python scripts/update_project.py <project-root>/project.json --update update.json`: **총괄 전용**, 구조가 유효한 기존 원장의 upsert 도구. 입력은 `{project_id, base_version, version, input_versions, owner_artifact_ids?, changes, storyboard?, preproduction?}`. changes는 기존 테이블 이름→부분 레코드 배열이며 기존 ID의 미변경 필드는 보존한다. storyboard는 synopsis_artifact_id와 beats/panels upsert, preproduction은 아래 패키지 포인터의 부분 갱신만 지원한다. 생성/삭제·프로젝트 선택·그 밖의 헤더 설계·승인 추론은 하지 않는다.\r\n- 내용 레코드(씬/인물/샷/주장/에셋/오디오/자막/보드)를 바꾸면 패킷에서 배정한 `owner_artifact_ids`와 신규/증가한 소유 artifact 버전을 함께 준다. 상태·증거만 갱신할 때 내용 버전을 억지로 바꾸지 않는다. 소유 관계와 사용자 권한은 총괄이 실제 문맥에서 판단한다; 도구가 진위를 인증하지 않는다.\r\n- 업데이트 도구는 base/input 버전, 레코드 참조/시간, 파일 루트, 후보 전체 구조를 확인한 뒤 같은 폴더 임시 파일→원자 교체한다. 협력 작성자 lock과 교체 전 원본 재확인으로 오래된 결과·중복 작성·관찰된 외부 수정을 거부한다. 기존 lock을 자동 제거하거나 재시도하지 않는다. 비협력 편집기의 마지막 순간 경합/정전 내구성까지 보장하는 DB는 아니다.\r\n- 상위 버전 변경은 실제 dependency 그래프를 따라 stale을 전파한다. stale artifact는 **이전 입력 버전**을 보존할 수 있으나 현재 승인/실행에 쓰지 않는다. 현재 버전으로 다시 만든 레코드는 명시적으로 등록하고 재검수한다. 독립 승인과 정상 컷은 보존한다.\r\n- `storyboard.panels[].asset_version_refs`의 버전 변경은 해당 에셋이 `required_asset_versions`에 없어도 보드 artifact의 입력 변경이다. 그 보드와 실제 종속 downstream만 stale 처리하고 과거 핀은 그대로 보존한다. 무관한 분기는 현재 상태를 유지한다.\r\n\r\n공급자 upload/job/Soul/site/folder ID와 URL은 외부 locator이며 canonical asset ID가 아니다. 실제 파일을 얻고 등록한 available/verified asset만 result_asset_id로 쓴다. Brandkit 상태·blocks.json·camera_spec.json·분할 manifest는 각각 domain authority/파생 adapter로 연결하고 project.json과 경쟁하는 전역 원장을 만들지 않는다.\r\n- `python scripts/package_production.py <project-root>/project.json --base-dir <project-root> --output <새-출력> [--zip] [--require-final]`: 원장과 실제 파일에서 v5.1 패키지 트리/ZIP를 조립하는 **파생 출력 도구**. 원장을 쓰지 않고 출력 경로를 덮어쓰지 않으며, 매니페스트는 정본에서 재생성한다.\r\n\r\n## v1.1 구조와 검사 프로필\r\n`schema_version`은 `1.1`을 사용한다. 이전 `1.0` 입력도 일부 호환되지만 새로운 프로젝트는 v1.1 필드를 작성한다.\r\n\r\n- plan: 필수 제작 정보·시간·참조·상태 기록을 검사한다. 생성 전 자료와 source_duration_status=estimated를 허용한다.\r\n- preproduction: 저장한 전체 패키지의 필수 산출물·실제 Markdown/이미지·전체 보드·인물 페르소나/SSOT·참조와 해시를 검사한다. `--base-dir` 필수, 이미지 모드에는 Pillow 필요. 예술성·동일 얼굴·권리·사용자 승인 진위를 인증하지 않는다. plan 성공은 이 준비 완료 판정을 대신하지 않는다.\r\n- delivery: plan 검사에 실제 파일 존재·해시·측정 시간·열린 blocker·납품 검사 기록을 추가한다. `--base-dir`을 프로젝트 폴더로 지정한다. 파일 재생, 디코딩, 음량 측정, 사실의 진위나 동의의 진위는 이 코드가 확인하지 않는다.\r\n- 필수 테이블 scenes/shots/artifacts는 비어 있으면 안 된다. 등장인물이 없는 영상은 characters=[]를 허용한다.\r\n- scene.purpose는 장면 기능, character.locked_traits는 문자열 또는 비어 있지 않은 목록/객체로 기록한다.\r\n- target_duration_s와 shot.start_s/end_s는 fps 기준 프레임 경계에 맞춘다. 초는 실수로 허용하고 반올림 오차를 제한한다.\r\n- shot.source_duration_status: estimated/measured. 계획의 원본 길이는 추정이며 실제 생성/촬영 후 측정한다.\r\n- shot.source_in_s는 선택 테이크의 소스 시작 초, playback_rate는 소스 초/최종 초(기본 1). 배속·슬로모션에서 필요한 소스 길이는 source_in_s+(end_s-start_s)*playback_rate다.\r\n- shot.asset_ids는 asset_registry의 선택된 참조 ID 목록이다. 프롬프트의 경로·룩·의상·소품은 CSV 연속성 원장과 맞춘다.\r\n- artifact.dependencies는 ID 목록이고 dependency_versions는 **정확히 그 ID들**의 {artifact_id: 입력 버전} 객체다. 선언되지 않은 키는 오류다. 현재 산출물은 상위 버전과 일치해야 하고, stale 산출물만 과거 입력 버전을 보존할 수 있다.\r\n- approved artifact는 approval={by, at, evidence}를 기록한다. 승인자·시간·근거는 실제 기록을 사용한다. 생성/검증 산출물에는 asset_ids, verified에는 evidence가 필요하다.\r\n\r\n## 전체 프리프로덕션 패키지\r\n\r\n단일 텍스트/프롬프트 요청은 이 확장을 요구하지 않는다. 전체 이미지 기반 제작은 **시놉 MD, 인물별 페르소나·SSOT MD와 실제 한 장짜리 Identity Sheet A, 통합 기술 콘티 MD, 모든 패널을 이야기 순서로 덮는 합본 스토리보드 이미지 세트(시트당 최대 8패널, 순서 있는 1장 이상)**를 인계한다. 캐릭터 없는 작품은 인물 산출물만 비적용이다. 텍스트 전용 전체 설계는 이미지 제출/파일/지출을 추가하지 않는다.\r\n\r\n- `preproduction={mode:text|image_backed,synopsis_artifact_id,storyboard_artifact_id,storyboard_sheet_artifact_ids,storyboard_split_asset_id}`를 기존 project.json에 둔다. 이미지 모드에는 합본 시트 artifact ID의 **정렬된 배열**이 필수다. 한 장도 배열로 기록하며 기존 단수 선언은 같은 ID의 한 항목 배열로 이전한다. 시놉 type은 synopsis, 보드 type은 storyboard이며 각각 정확히 한 실제 `.md` 에셋을 연결한다.\r\n- 전체 패키지의 각 `characters[]`에는 `persona={role,personality,observable_behavior,speech}`, `ssot_artifact_id`를 둔다. 네 페르소나 값은 구체적인 비지 않은 문자열이며 무대사에는 이유를 적는다. character_sheet artifact는 시놉 입력 ID/버전과 실제 SSOT MD 에셋 하나를 연결한다. 공급된 캐릭터는 원본을 보존하고 시놉 적용 범위의 인계 시트를 버전으로 연결한다.\r\n- 이미지 모드의 `identity_sheet_asset_id`는 kind=character_identity_sheet, entity_type=character, 해당 entity_id의 실제 이미지다. 전신 정면/3·4/측면/후면 + 얼굴 정면/3·4/측면의 7뷰를 한 장에 구성하고 각 뷰의 고정 앵커를 실제 검사한다. 장면 초상 하나는 대체물이 아니다. 해당 에셋의 `source_asset_ids`에는 그 캐릭터 SSOT artifact가 가리키는 실제 Markdown asset ID가 포함돼야 하며, 검사기가 연결을 확인한다. 인물이 등장하는 모든 샷의 asset_ids에 이 정본을 연결한다.\r\n- storyboard artifact는 현재 시놉과 모든 캐릭터 character_sheet의 정확한 버전에 의존한다. 각 샷/패널에 원문·beat/scene/shot/panel/캐릭터·페르소나/SSOT·카메라·시간·실제 이미지 참조를 통합한다. 각 패널은 해당 beat·가시 캐릭터·audio cue·speech ID를 직접 기록한다.\r\n- 합본 `type=storyboard_sheet` artifact는 보드의 현재 버전에 의존하고 `kind=storyboard_sheet` 이미지 에셋 정확히 하나를 연결한다. PNG의 `storyboard_sheet.panel_traceability` metadata와 표시 캡션은 panel별 ID 매핑을 담는다. 입력 시트/crop은 합본 출력의 대체물이 아니다.\r\n- 이미지 모드의 `storyboard_sheet_artifact_ids`는 이야기 순서로 정렬된 `type=storyboard_sheet` artifact 배열이다. **한 시트에는 최대 8개 패널**만 둔다 — 패널 수·정보 밀도·씬 경계로 장수를 정하고 한 장에 욱여넣지 않는다. 각 시트 artifact는 보드의 현재 버전에 의존하고 `kind=storyboard_sheet` 이미지 에셋 정확히 하나를 연결한다. 각 시트 에셋의 `panel_ids`는 자기 구간의 정본 panels 순서이며, 모든 시트를 순서대로 이어 붙이면 정본 전체 순서와 일치한다(누락·중복 없음). 시트가 두 장 이상이면 각 에셋에 `sheet_index`(1부터)·`sheet_count`를 기록한다. `source_asset_ids`는 그 시트 패널의 실제 픽셀 입력(source_sheet_asset_id가 있으면 그 ID, 없으면 image_asset_id)을 같은 순서로 담고 `source_sha256`는 해당 입력 ID→현재 해시 맵이다.\r\n- `render_storyboard_sheet.py <project.json> --base-dir <root> --output 04_STORYBOARDS/sheets/<새.png> [--font <font.ttf>] [--panels-per-sheet 1..8]`는 clean 패널과 외부 촬영 캡션을 순서 있는 PNG 세트로 조립한다. 각 시트의 실제 path/hash/패널·소스 매핑과 동일 traceability PNG metadata를 반환하며 원장을 쓰지 않는다. 총괄이 모든 시트를 등록하고 실제 합본을 연다.\r\n- 합본을 만든 직후 `split_storyboard.py --sheet <프로젝트-relative 시트>`를 이야기 순서로 반복 지정해 장면 overview와 clean 패널을 추출한다. 실제 JSON manifest를 `kind=storyboard_split_manifest`로 등록하고 `preproduction.storyboard_split_asset_id`에 연결한다. 각 추출 이미지도 실제 경로·SHA-256으로 등록한다. manifest의 `file`은 manifest 폴더 기준, `sheet_path`·`sheets[].path`·`band_sources`는 프로젝트 root 기준 상대 경로다. 원본 패널 입력을 추출 이미지로 바꾸지 않는다.\r\n- preproduction/FINAL은 manifest의 주장만 신뢰하지 않는다. 각 panel/scene의 실제 등록 파일·SHA-256, canonical scene/shot/panel, source asset/version/hash 및 asset pins가 서로 일치해야 하며 다른 패널 파일을 alias한 split은 거부한다.\r\n- `package_production.py --require-final`은 명시적인 현재 FINAL 보드, 완료된 이미지 기반 패키지, 정렬된 현재 시트/hash와 일치하는 split manifest, 전체 scene/panel 이미지의 실제 등록을 요구한다. ZIP의 root `project.json`은 휴대 가능한 파생 스냅샷이며 registry 경로가 실제 패키지 파일을 가리킨다. 표준 폴더 경로는 유지하고, 구형 평면 경로는 asset ID를 포함해 충돌 없이 배치한다. CSV manifest는 정본의 파생물이고 모든 실제 패키지 파일을 열거한다.\r\n- ZIP 재개봉은 asset registry 경로와 split 내부 `file`/`sheet_path`/overview source 참조를 같은 relocation map으로 재투영하고 파생 snapshot hash를 갱신한다. 원본 정본은 변경하지 않으며, 실제 복사 byte stream이 등록 지문과 다르면 게시를 중단한다.\r\n- 모든 필수 실제 파일에는 SHA-256을 기록한다. 이미지 디코딩·현재 종속 버전·전체 커버리지·열린 blocker도 검사한다. reviewed/approved인 preproduction_review 또는 approved인 video_execution_plan에는 plan에서도 이 완결 게이트를 자동 적용하며 이미지 모드를 요구한다. 검토는 시놉·보드·합본을 dependency 그래프로 소비해야 한다.\r\n- 누락 상태는 draft/stale로 보존하고 strict preproduction 검사에서는 준비 미완료로 반환한다. 프롬프트·가상 path·planned 에셋·검사 기록만으로 실제 산출물이라고 표시하지 않는다. 구조 통과 뒤에도 캐릭터 7뷰 정체성, 전체 clean 컷 읽힘, 합본 누락/가독성, 장면 내 제품·빛·그림자·반사 통합을 실제 검수하고 사용자 수락을 별도로 받는다.\r\n\r\n\r\n## 실제 파일과 부가 시간표\r\n- asset_registry: {id, kind, version, path, status, sha256}. 실제 path는 프로젝트 폴더 기준 상대 경로를 권장하며 `--base-dir` 검사에서 resolve한 결과가 그 폴더 밖이면 거부한다(절대 경로/..//symlink 포함). planned는 path=null을 허용한다. available/verified는 실제 경로를 갖고 base-dir가 있으면 파일 존재와 제공된 해시를 확인한다. 최종 파일에는 verified와 SHA-256이 필요하다.\r\n- asset_registry 선택 provenance 필드(있을 때만 채운다): entity_type(character/product/prop/location/wardrobe/look/lighting/graphic/environment), entity_id, authority(authoritative/inferred/derived), source_asset_ids, prompt, provider, model, workflow, result_asset_id. 사용자가 준 SSOT·바이블은 authoritative로 기록하고 임의로 변경하지 않는다. 확인되지 않은 provider/model을 기록하지 않는다.\r\n- source_asset_ids/result_asset_id는 실제 asset_registry ID를 참조한다. entity_id가 있으면 비어 있지 않은 문자열이어야 하고 entity_type=character는 characters의 ID와 일치한다. 캐릭터 Identity Sheet A의 source_asset_ids에는 해당 캐릭터 SSOT artifact의 유일한 Markdown asset ID가 반드시 포함된다. 다른 entity_id는 해당 전문 바이블 locator로서 실제 소스를 인계하며 새 임의 테이블을 강제하지 않는다. shot.claim_ids가 있으면 claims의 실제 ID를 참조한다.\r\n- shot.retry_budget: 최초 생성 이후 허용된 최대 재시도 수(선택, 0 이상 정수). 승인된 video_execution_plan의 상한에서 온다. 0이면 최초 1회만 허용하고 attempt의 최대값은 1+retry_budget이다. 필드 부재는 무제한 실행 허가가 아니다.\r\n- generation_attempts: {id, shot_id, attempt(최초=1, 이후 샷별 중복 없는 양의 정수), route, model?, changes?, observed_failures?, preserve?, result(accept/reject/conditional), result_asset_id?, failure_class?, notes?}. 실제 시도만 기록한다. accept는 available/verified인 실제 결과 에셋 ID를 참조해야 하며 planned 에셋을 성공 결과로 기록하지 않는다. 기록/구조 검사 자체가 실행 승인이나 미디어 품질 검사는 아니다.\r\n- audio_mode: no_audio / no_dialogue / dialogue. audio_cues: {id, start_s, end_s, layer, shot_id?, asset_id?}. 소리는 겹칠 수 있지만 전체 영상 구간을 벗어나지 않는다.\r\n- captions: {id, start_s, end_s, text, shot_id?}. 오디오 음소나 자막 타이밍의 의미 적합성은 실제 재생으로 검사한다.\r\n- issues: {id, severity: blocker/major/minor, status: open/resolved, evidence?, fix?}.\r\n- delivery_spec: {destination, width, height, container, video_codec, caption_mode: none/sidecar/burned_in, final_asset_id, caption_asset_id?}. 기존 소스에서 현재 목적지 규격을 추정하지 않는다.\r\n- delivery_checks: {id, category: playback/timing/visual/audio/captions/continuity/claims, status: pass/fail/unverified/not_applicable, evidence?, reason?}. pass는 실제 검사 위치, N/A는 비적용 이유를 갖는다. 실제 확인하지 않고 pass를 적지 않는다.\r\n\r\n## 버전 변경과 범위\r\n변경된 산출물과 그 하위 인계를 stale로 표시하고 입력 버전을 갱신한 뒤 관련 항목만 재검수한다. 계획 패키지가 완성됐어도 실제 영상이 완성된 것은 아니다. 참고 후보·예산·도구 기능이 미정이면 계획에서 가정으로 남기고 실제 실행 직전에 확인한다.\r\n\r\n## 프리프로덕션 검토와 영상 실행 승인\r\n[프리프로덕션·검토 절차](preproduction-review.md)의 `review.md`는 `type=preproduction_review` artifact로 등록하고 검토 대상의 ID·버전을 dependencies/dependency_versions로 연결한다. 실제 사용자 수락 때만 approved와 approval 근거를 기록한다. 문서·이미지의 generated/verified 상태는 사용자 수락을 뜻하지 않는다.\r\n\r\n별도 `type=video_execution_plan` artifact는 승인된 검토 패키지 버전과 명시적 샷·모델/endpoint·실행/재시도/비용 상한을 참조한다. 실제 사용자 실행 승인 뒤에만 approved로 기록한다. 프리프로덕션 중 모델/가격 미정은 허용하지만 실행자 기본값으로 보충하지 않는다. 변경된 에셋의 종속 검토/실행 계획은 stale로 표시하고 새 버전에 이전 승인을 재사용하지 않는다. 사용자 승인과 파일 존재/구조 검사는 별개의 증거다.\r\napproved 영상 실행 계획은 dependency 그래프에 현재 approved인 preproduction_review를 반드시 포함한다. 이 구조 검사는 실제 사용자 권한·비용·음성/이미지의 품질을 인증하지 않는다.\r\n\r\n프리뷰와 최종은 별도 허가다. `video_execution_plan`의 승인 범위에 프리뷰 단계가 포함되면 승인된 프리뷰 입력 버전·설정·샷/출력 수·상한을 그대로 기록하고, 프리뷰 승인만으로 최종 생성·추가 과금을 허가하지 않는다. 프리뷰 실제 출력·검수 결과·수락 근거는 연결된 artifact(result_asset_id, generated/verified, evidence)로 남기고, 승인된 최종 계획은 프리뷰 판정과 최종 승격 경로를 dependencies로 참조한다. 프리뷰와 최종 범위를 하나의 plan 버전으로 함께 승인한 경우에만 최종이 같은 승인 안에서 현재 입력 버전·조건·상한으로 진행되며, 그렇지 않으면 현재 버전의 별도 최종 승인이 필요하다. 같은 seed·입력의 재생성은 같은 동작·정체성을 보장하지 않으므로 최종본은 다시 검수한다.\r\n\r\n## 선택적 상세 스토리보드 확장\r\n제작용/상세 콘티와 전체 보드 시트에는 [완전한 스토리보드 계약](storyboard-contract.md) §8의 `storyboard` 객체와 shot 기술 필드를 정본 `project.json`에 추가한다. 기존 schema_version=1.1 및 일반 plan/delivery 프로필은 유지한다. 별도 `validate_storyboard.py`는 전체 비트/씬/샷/패널 연결과 제작 슬롯을 검사하며 실제 이미지에는 `--require-images --base-dir`를 적용한다. 합본 crop/clean 컷은 `split_storyboard.py`의 파생 결과를 asset_registry에 등록하고 같은 ID로 연결한다. CSV/시트/분할 manifest는 조회·등록용 투영이며 별도 원장이 아니다. 의미 검수·권리·사용자 수락을 파일 검사로 대체하지 않는다.\r\n\r\n## v5.1 프로덕션 무결성 (LOOK·에셋 게이트·계보·provenance·패키지)\r\n\r\n선택 확장이 아니라 전체 이미지 기반 패키지와 그 다운스트림(씬 상태·보드·생성 명세·애니매틱)에 적용한다. 기존 schema_version=1.1을 유지하고 아래 필드는 모두 선택이지만, `final`을 선언하는 순간 해당 게이트는 강제다.\r\n\r\n### 활성 LOOK과 스타일/월드 바이블\r\n- `look_asset_id`는 루트 필드로, `entity_type=look`(또는 미분류)의 asset_registry 에셋을 가리킨다. LOOK은 **하나만 활성**으로 둔다 — 프로젝트 전체 시각 문법(매체·리얼리즘·비율·팔레트·조명 철학·카메라 문법·스타일 드리프트 금지)을 버전으로 잠근다. 바이블 문서에는 `assets/style-world-bible-template.md`를 쓴다.\r\n- 모든 시각 생성 에셋은 활성 LOOK 버전을 참조한다. LOOK 에셋의 내용이 바뀌면 버전을 올리고 종속물을 stale 처리한다. 패널이 활성 바이블에 없는 새 시각 스타일을 발명하지 않는다.\r\n\r\n### 마스터·파생 에셋 계보\r\n- `asset_registry` 선택 필드 `role: master|derivative`와 `master_asset_ref: {asset_id, version}`을 둔다. 반복 정체성 에셋(캐릭터 마스터·장소 마스터·소품 마스터)은 한 번만 master로 등록하고, 씬별 상태(젖음·파손·의상·조명·배치)는 derivative로 등록해 마스터 ID와 **정확한 버전**을 핀한다. 여러 씬 폴더에 같은 마스터의 편집 가능한 사본을 두지 않는다.\r\n- 마스터 버전이 올라가면 그것을 핀하는 derivative는 자동으로 stale가 되고(재핀하기 전까지), 이 계보를 따라 이어지는 derivative도 연쇄로 stale가 된다. 비stale 에셋이 옛 버전을 핀하거나 stale 마스터에서 파생되면 검사가 거부한다.\r\n- 캐릭터 마스터는 7뷰 정체성 시트 외에 서사 관련 표정·의상(WD ID)·DO-NOT-CHANGE 락을 포함한다. 장소 마스터는 생산상 중요한 장소에 4공간뷰(establishing/reverse/lateral/top-down)와 출입·창·장애물·광원 앵커를 둔다 — 수치는 추정이면 `ESTIMATED`로 명시한다. 소품/도구/제품은 연속성이 문제가 될 때만 전/후/측/3/4·상태 변형·스케일 참조를 둔다. 장식 보드를 위해 에셋을 만들지 않는다.\r\n\r\n### 에셋 게이트: preliminary vs final\r\n- artifact 선택 필드 `finality: preliminary|final`과 `required_asset_versions: {asset_id: version}`을 둔다. finality를 생략하면 preliminary다.\r\n- `final` 선언은 **생성 전 잠금 게이트**다: 참조 에셋이 전부 등록돼 있고 status가 **`verified`**(v5.1의 LOCKED/APPROVED/VERIFIED_REFERENCE에 해당 — `available`은 파일이 존재할 뿐 에셋 QA 잠금이 아니므로 final을 차단한다)이며 핀 버전이 현재와 같아야 한다. final 시각 산출물(type storyboard/storyboard_sheet)은 추가로 **활성 시점(앞/뒤/측면, 다른 각도·거리)에서 보여주거나, 브리프가 특정 구도·공간·광학 느낌의 정확한 재현을 요구할 때만 적용한다. 해당하지 않으면 `N/A`로 닫고 분위기 참조만으로 이 절차를 채우지 않는다.\r\n\r\n**같은 특징의 시점 대응.** 시점 사이에서 같은 특징만 짝짓는다 — 같은 얼굴·면·바느질·개구부·접촉점처럼 대응이 성립하는 특징을 연결하고 각 쌍에 `관찰 / 가림 / 미확인`을 표시한다. 가려져서 안 보이는 특징을 없다고 단정하거나 형상 변화·복원으로 해석하지 않는다. 가림 전 마지막 관측과 재등장 시점의 관측을 구분해 기록하고, 재등장하지 않으면 미확인으로 남긴다. 가림 때문에 안 보이는 면의 특징을 다른 시점 관찰 없이 만들지 않는다.\r\n\r\n**광학 역추정(정확한 재현 압축된 원근은 긴 초점거리+먼 거리 조합과 크롭 모두와 양립). 후보 사이를 실제로 가르는 관측이 무엇인지(민감도)와 반증·확정에 필요한 추가 증거(다른 시점 프레임·파랄랙스·EXIF/제작 기록·알려진 크기의 기준 물체)를 함께 기록한다. 새 제작으로 넘기는 목표는 확정 카메라 값이 아니라 관찰된 화면 특성(원근 압축·심도·왜곡·피사체 화면 SSOT와 효능 claim을 따로 검사한다.\r\n\r\n문구가 시각적으로 변형될 때는 어떤 뜻이 먼저 읽히고 무엇이 다음 상태에서 달라지는지 명시한다. 각 상태의 실제 읽기 구간과 전환은 [09-edit](09-edit.md)에 넘긴다. 짧은 보상 뒤에 post-card/coda가 유익한지 검토할 수 있지만, 구매 CTA나 coda는 브리프가 요구/허용할 때만 둔다. 문구가 보이는 것만으로 claim proof, 음성 발화, 구매 목적지를 성립시키지 않는다. 리허설 QA는 행동이 카피의 주장을 재현하는지, 다른 말장난/광고 해석이 더 자연스러운지 확인한다.\r\n\r\n카피가 특정 행동을 약속하거나 그 행동에 기대는 경우, 승인된 문구를 실제 보이는 사건/행동에 연결해 `06-shots-template`의 주체·행동·공개·cue 시간과 `09-edit-template`의 final start/end 및 행동 cue에 함께 기록한다. 카피의 시작·정착·읽기 홀드·퇴장/전환은 그 사건의 제안 시간과 비교해 근거 있게 배치한다; shot-local cue와 final timeline 시간을 혼합하지 않는다. 의미 대응이 은유적이면 채택한 은유와 시각 앵커를 적고, 무관한 제품 미장센만으로 문구를 실현한 척하지 않는다. brief에 없는 문자 그대로의 행동/소품/claim은 만들지 않는다.\r\n\r\n### 기대 위반·목격자 반응 (세계 규칙을 실제로 깨는 아이디어일 때)\r\n\r\n관객이 먼저 알아볼 기대/장소 단서를 두고, 그 규칙이 깨지는 사건, 사건을 본 인물의 관찰 가능한 반응, 새 정보/복귀를 순서대로 설계한다. 행동 원인과 reaction cue가 인접해 읽히도록 [04-performance](04-performance.md) 및 [06-shots](06-shots.md)의 주체·상대·시선·cut slot으로 인계한다. 필요하지 않으면 목격자/반응 shot을 추가하지 않는다; 한 shot의 action phase도 가능하다.\r\n\r\n실제 frame/eyeline·공간 관계로 그 인물이 해당 사건을 볼 수 있는지 확인한다. 표정만으로 사건 인지, 동의, 만족, audience persuasion을 주장하지 않는다. 코미디라면 genre promise와 punchline을 [17-genre-comedy](17-genre-comedy.md)에서만 판단하고, 17을 출연자 인물설정/연기 목표 계약으로 쓰지 않는다. 이 recipe는 설계 가설이며 관객 반응/성과 증거가 아니다.\r\n\r\n## 2. 감정과 기억 설계\r\n\r\n관객이 감정적으로 거주할 수 있는 경험을 설계한다. 대사·내레이션으로 감정 이름을 붙이는 것으로 대신하지 않는다.\r\n\r\n1. 목표 감정 여정을 하나의 분위기가 아니라 순서로 정한다: 예) 호기심→따뜻함→걱정→안도→씁쓸한 여운.\r\n2. 관객이 누구의 시점에 감정적으로 들어가는지, 그 대상이 지금 무엇을 원하는지 정한다.\r\n3. 관찰 가능한 취약점을 찾는다: 행동·망설임·의식·희생·실수·은폐·선택.\r\n4. 의미·관계·기대·판돈을 바꾸는 감정 전환을 요청한 길이와 이야기 비트에 맞게 설계한다. 수량을 채우기 위한 전환은 추가하지 않는다.\r\n5. 핵심 감정에 감각적·시각적 앵커 하나를 배정한다: 사물·소리·제스처·색 관계·장소 디테일·반복 행동.\r\n6. 대비를 쓴다: 가까움/거리, 소음/침묵, 군중/고독, 속도/정지, 희망/상실.\r\n7. 명시적 설명은 관객이 느끼거나 추론할 근거가 충분해진 뒤로 미룬다.\r\n8. 결말은 앞선 이미지·소리·문구·행동을 변형하거나 재맥락화해 닫는다. 기억되는 결말은 ①무엇이 변했는지 ②그 변화를 담는 이미지 ③왜 중요한지를 연결한다.\r\n\r\n### 감정 구조 패턴\r\n\r\n- 재인식: \"이 느낌을 안다\" → 구체성 → 공유된 인간성.\r\n- 보호적 공감: 유능한 겉모습 → 작은 취약점 → 의미 있는 선택.\r\n- 재맥락화: 중립 모티프 → 새 정보 → 감정적 무게를 얻은 모티프의 귀환.\r\n- 축적: 작은 행동의 반복이 변주를 통해 의미를 얻는다.\r\n- 부재: 일상을 세운 뒤 요소 하나를 빼서 빈자리가 감정을 운반하게 한다.\r\n- 정당한 해방: 장애로 압력을 쌓은 뒤 최대 멜로드라마가 아니라 작고 믿을 수 있는 해방을 준다.\r\n- 혼합 감정: 안도+상실, 기쁨+불확실, 자부+대가. 혼합 상태는 단일 감정보다 오래 남는 경우가 많다.\r\n\r\n행동이 형용사보다 우선이고, 구체적 판돈이 일반적 비극보다 우선이다.\r\n\r\n### 감정 정직성 점검\r\n\r\n뒷받침되지 않은 비극·가짜 증언·지어낸 사실·굴욕·강요·이야기 증거를 대신하는 조작적 음악으로 눈물을 만들지 않는다.\r\n- 그 감정은 관찰된 사건에서 얻은 것인가?\r\n- 음악을 꺼도 장면이 작동하는가?\r\n- 대상이 존엄과 행위성을 유지하는가?\r\n- 관객에게 느낄 것을 말하는 대신 추론할 여지가 있는가?\r\n- 보상이 확립된 인물·세계와 일치하는가?\r\n\r\n## 3. 시청 유지 설계\r\n\r\n주의를 지키되 매 초를 소음으로 만들지 않는다. 유지율은 계속 볼 이유의 연속이다.\r\n\r\n1. 제목·썸네일·전제·오프닝 이미지가 만든 관객 기대를 적는다. 미끼-뒤바꾸기는 하지 않는다.\r\n2. 계속 볼 첫 구체적 이유를 즉시 준다: 특이한 이미지·미해결 행동·모순·급한 목표·감정적으로 충전된 질문.\r\n3. 각본 전에 유지 지도를 만든다. 구간마다 열린 질문·새 정보·변화·약속된 보상을 적는다.\r\n4. 설정 없이 이해되는 가장 강한 증거·갈등·이미지·놀라움은 앞으로 이동한다.\r\n5. 압축과 숨 고르기를 번갈아 쓴다. 반복 설명·예비 잡담·중복 establishing·관객이 이미 도달한 결론은 제거한다.\r\n6. 패턴 변화는 동기가 있을 때만 쓴다: 샷 크기·장소·화자·시각 모드·소리·템포·그래픽·행동·정보 상태.\r\n7. 작은 고리는 닫으면서 더 큰 고리를 연다. 모든 보상을 무한히 미루지 않는다.\r\n8. 감사 주기: 장편은 10~30초마다, 단편은 비트마다 \"무엇이 변했는가?\"를 묻고 변화가 없으면 압축하거나 삭제한다.\r\n\r\n### 유지 아키텍처\r\n\r\n단편(피드 우선) 기본 비트 — 증거가 설명보다 먼저:\r\n- 진입: 이상·결과·가장 읽기 쉬운 행동을 보여준다.\r\n- 방위: 누가/무엇/목표를 빠르게 설명한다.\r\n- 복잡화: 마찰이나 모순 도입.\r\n- 에스컬레이션: 결과나 놀라움 증가.\r\n- 전환: 해석이나 전략 변화.\r\n- 보상: 원래 약속 충족.\r\n- 애프터비트(선택): 콜백·함축·루프 가능한 마지막 이미지.\r\n\r\n장편은 중첩 고리:\r\n- 거시 질문: 왜 전체를 보는가.\r\n- 구간 질문: 왜 다음 2~5분을 보는가.\r\n- 비트 질문: 왜 다음 10~30초를 보는가.\r\n\r\n약력·브랜딩·채널 잡무·첫 강렬 사건 뒤에 이해해도 되는 맥락으로 시작하지 않는다.\r\n\r\n### 유지율 진단 (실제 분석 데이터가 있을 때)\r\n\r\n- 하락: 하락 직전 순간을 검사한다. 흔한 원인은 약속 불일치·반복·혼란스러운 설명·낮은 판돈·예측 가능한 전환·약한 시각 변화·늦은 증거·긴 설정이다.\r\n- 상승: 강한 순간·재시청 디테일·공유할 비트·재생이 필요한 혼란 모두 가능하다. 댓글·맥락으로 확인한 뒤 패턴을 복사한다. 모든 스파이크를 긍정으로 해석하지 않는다.\r\n- 오프닝보다 뒤 구간이 명백히 강하면 보상을 망치지 않는 범위에서 일부를 미리 보여주거나 앞으로 옮기는 것을 시험한다.\r\n\r\n## 관련 모듈\r\n\r\n- 선택된 콘셉트의 브리프 고정: 모듈 01.\r\n- 감정 곡선의 인과 비트화: 모듈 02, 각본화는 03.\r\n- 유지 지도의 컷·길이 반영: 모듈 09, 플랫폼 적응은 [피니싱·플랫폼](23-finishing-platform.md).\r\n\r\n### 19-brand-product-integration.md\r\n# 스폰서·제품 통합 (온디맨드 심화)\r\n\r\n모듈 13(아이디어·브랜드)과 10(근거·주장 원장)의 심화. 드라마·코미디 시리즈·스킷·크리에이터 영상 안에 광고를 자연스럽게 넣거나, 제품 자체가 정확하게 보여야 하는 영상에 연다.\r\n\r\n## 1. 스토리 네이티브 광고 통합\r\n\r\n제품이 이야기에 원주민처럼 느껴지게 한다. 브리프가 명시적으로 단절형 광고를 원하지 않으면 죽은 광고 블록을 붙이지 않는다.\r\n\r\n1. 스폰서 요구를 추출한다: 제품/서비스명·필수 주장과 금지 주장·필수 노출 비주얼·CTA/고지 요구·톤 제약. 필수/금지 주장은 모듈 10의 claim 원장에 claim_id로 연결한다.\r\n2. 이야기 체계를 추출한다: 인물·진행 중인 갈등·감정 판돈·장르 톤·세계 논리.\r\n3. 이야기 호환 제품 기능을 찾는다: 제품이 현재 상황을 해결하거나·복잡하게 하거나·드러내거나·유혹하거나·상징적으로 반영한다.\r\n4. 통합 모드를 고른다:\r\n   - 플롯 장치: 제품이 다음 사건을 일으키거나 현재 장애를 해결한다.\r\n   - 인물 의식: 인물이 반복 맥락에서 자연스럽게 쓰는 제품.\r\n   - 공개 도구: 제품이 숨은 정보·정체성·감정을 드러낸다.\r\n   - 코믹 해결사: 우스운 문제에 대한 지나치게 진지한 해결책.\r\n   - 브랜디드 우회: 세계가 자의식적으로 광고 개그를 위해 멈췄다가 복귀한다. 자의식적 단절이 해당 콘텐츠 문법일 때만 사용한다.\r\n5. 진입 순서를 쓴다: 선행 문제/질문 → 제품의 자연스러운 도착 → 사용/시연 비트 → 브랜드 보상 → 본편 복귀 전환.\r\n6. 인물 진실을 지킨다. 진지한 전사가 갑자기 영업 멘트를 하지 않는다 — 그 단절 자체가 의도된 개그일 때만 예외.\r\n7. 고지는 정책·신뢰와 양립하는 최소 손상 위치에 넣는다. 불편하다고 고지를 삭제하지 않는다.\r\n8. 정확한 제품 비주얼·패키지 요구는 아래 제품 SSOT 절차로 보낸다.\r\n9. 분리 테스트: 제품을 빼 본다. 장면이 완전히 붕괴하면 통합이 과의존, 아무 변화가 없으면 통합이 너무 약하다.\r\n\r\n### 통합 점검 목록\r\n\r\n- 인물이 스폰서 없이도 이 말/행동을 할 수 있는가?\r\n- 제품 도착이 장면 안에서 성립하는가?\r\n- 스폰서 이점이 한 번의 시청으로 읽히는가?\r\n- 고지가 존재하는가?\r\n- 이후 본편이 매끄럽게 재개되는가?\r\n\r\n### 규칙\r\n\r\n- 의료·법률·성능 주장을 지어내지 않는다. 확인된 주장만 claim 원장에 verified로 둔다.\r\n- 이야기를 멈추고 살균된 기능 나열을 하지 않는다 — 명시 요청 시만.\r\n- 일반 시연 문구보다 인물 특유의 사용법을 우선한다.\r\n- 제품이 코미디를 만들 수는 있지만 광고가 시청자를 굴욕시키지 않는다.\r\n\r\n## 2. 제품 비주얼 디렉팅\r\n\r\n제품을 일반 소품이 아니라 통제된 주인공 에셋으로 다룬다.\r\n\r\n1. 제품 SSOT를 만든다: `assets/product-ssot-template.md`. 치수/비율·실루엣·로고·라벨 배치·캡/마개·재질·색·표면 마감·투명도·내용물 질감·사용자가 제공한 법적 필수 표기.\r\n2. 정확한 제품 표현과 개념적 성분/효능 시각화를 분리한다. 뒷받침되지 않은 효능을 암시하지 않는다.\r\n3. 샷 기능을 고른다: 도입 → 촉감 클로즈업 → 추상 매크로 → 제품 히어로 → 사용/결과 → 정확한 팩샷 → CTA/엔드카드. 브리프가 요구하는 기능만 쓰며 CTA/구매 경로는 명시적으로 필요할 때만 둔다.\r\n4. 재질별 조명을 설계한다:\r\n   - 유광: 통제된 긴 하이라이트와 깨끗한 반사.\r\n   - 반투명: 배후/가장자리 조명과 내부 밀도.\r\n   - 크림/액체: 점성·표면 장력·질감·접촉.\r\n   - 금속: 반사 환경 자체가 겉모습이다.\r\n   - 반사 제품(거울·유리·금속): 무엇이 반사되는지, 제품 회전/카메라 이동 중 반사 띠가 어떻게 이동하는지, 라벨·로고의 읽기 영역을 먼저 정한다. 정확한 artwork는 제품 면의 불변 레이어로 잠그고, 반사 패스가 문자를 복제·뒤집어 가짜 라벨을 만들지 않도록 가림/보호 영역을 둔다. 관찰 프레임에서 반사 방식이 확인되지 않으면 실제 반사광으로 추정하지 말고 graphic/reflection design으로 표시한다. 전·중·후와 실제 크롭에서 표시/실패를 확인한다.\r\n   - 피부: 질감이 믿을 만해야 하며 의도적 스타일화가 아니면 플라스틱 스무딩을 피한다.\r\n5. 생성 모델의 텍스트/로고 충실도가 불안정하면 승인된 패키지 아트워크를 정확히 맞는 제품 면에 합성하거나 제품을 별도 레이어로 만든다. 합성은 허용되지만 action scene에서 source packshot 전체를 배경 위에 평면으로 얹지 않는다. 원근·면 방향·스케일·광원·반사·접촉 그림자·가림을 통합해 실제 공간의 물체로 읽혀야 한다. 제품을 쥐거나 열거나 도포하는 컷은 손과의 접촉/소유 상태 변화를 보여준다. 정면 packshot 합성은 계획된 frontal hold에 한해 사용하며 정확한 로고·법적 문구는 승인 아트워크로 보존한다.\r\n6. 손/피부/도포의 접촉은 [생성 영상 QA·재시도](21-generated-video-qa-retry.md)의 모션 절차, 모델 연속성은 [비주얼 모드·SSOT](20-visual-mode-ssot.md)로 라우팅한다.\r\n\r\n7. 액체 튐·물방울·성분 세계·불가능한 매크로 전환은 레이어 합성 계획으로 분리한다.\r\n8. QA: 실루엣·캡 형상·로고 위치·라벨 문구·재질·내용물 수위·색·손 접촉·최종 팩샷.\r\n\r\n### 분리형 부품의 상태·소유 인계\r\n\r\n제품을 열거나 캡 등 분리형 부품을 떼어 내는 경우, 제품 SSOT의 `캡/마개`와 불변 속성은 제품 아이덴티티를 고정하는 데 쓰고, 상태 전이는 기존 26 템플릿 행으로 기록한다. 실제 템플릿의 `대상 ID`, `시작 상태와 근거`, `끝 상태와 근거`, `후속 유지 범위 / 리셋 조건`, `동작 → 대상 변화 → 잔류 결과`, `검사한 동작/접촉 구간`을 연결하고, 샷/컷에서 어느 손이 제품과 분리 부품을 지지·소유하는지, 내려놓기/넘김이 어디서 일어나는지를 기존 `인물 블로킹`과 shot-local cue에 명시한다. 부품이 분리되면 명시적으로 놓거나 넘기기 전까지 소유 손에 남는다. 컷이나 화면 밖에서 부품/손의 상태가 저절로 바뀐 것으로 전제하지 않는다. 오프스크린 처리가 제품 물성에 영향을 주면 위치/후속 소유 상태는 `미확인`으로 두고 모순되는 샷 계획을 내지 않는다.\r\n\r\n제품 내용물·사용 뒤 피부/표면 잔류가 브리프나 승인된 자료에 특정되지 않으면 액적·광택·잔류를 사실/효능으로 만들지 않는다. brief가 창작된 시각 흔적을 요청하면 제안으로 표시하고 위치·시작/끝 상태·가림 뒤 유지 또는 명시적 reset을 기존 26 템플릿 행에 연결한다; 속성이 정해지지 않으면 `미확인`/`N/A`로 남긴다.\r\n\r\n### 형태·환경 은유를 제품 공개로 연결할 때\r\n\r\n제품을 늦게 드러내는 재료/풍경 순서는 필요할 때만 설계한다. 와이드 환경→가까운 표면/질감→일부 실루엣→제품·라벨에 서로 다른 정보 역할을 주고, 제안한 연결이 실제 컷·연속 이동·합성 중 무엇인지는 확인 전까지 단정하지 않는다. 제품 등장 뒤에는 SSOT의 실루엣·면·표식을 다시 회수한다. 풍경·반사·물방울은 방수/향/원산지/성능 증거가 아니다.\r\n\r\n제품과 세계의 형태를 맞출 때 **표면 대응**(원·곡선·색·질감)과 **의미 해석**(예: 힘·속도·향)을 따로 적는다. A03식 구체 대응이 필요하면 `assets/06-shots-template.md`의 기존 `공개 정보`, `관점·감정/구도 의도`, `카메라 동작`, `종료 프레임`에 양쪽 대상의 화면 위치·크기·방향·가림·질감 anchor, 대응 근거와 공개 시점을 기록한다. 시간상 대응에는 템플릿의 cue timeline을 쓰고, 별도 상태라면 기존 shot/panel row를 쓴다. 제안 전·중·후 frame에서 실제 변화가 읽히는지 계획/검수 상태를 구분해 확인하고, hard cut/dissolve/morph/mask 중 무엇을 쓸지와 대안을 비교한다. 전자는 화면 관계, 후자는 새 해석 제안이며 둘 다 주장을 증명하지 않는다. 시각 대응이 제품을 왜곡하거나 표식/라벨을 덮으면 단순 cut, 고정 하이라이트, 승인된 그래픽 레이어를 대안으로 검토한다.\r\n\r\n브리프에 불가능한 스펙터클이 있을 때만 그 진입·환상 범위·복귀를 정하고, 뒤 제품 히어로에서 승인된 스케일/라벨/조명/정체성을 재확립한다. 불·물·차량·섭취 등 위험하거나 불가능한 장면을 실제 사용법·안전성·제품 성능으로 오인시키지 않는다. 환상 신호가 충분하지 않으면 스펙터클을 제거하거나 비기능적 그래픽/애니메이션으로 바꾼다. 각 사례는 실제 관객·에셋·안전/권리 조건에 맞게 검토한다.\r\n\r\n산출물: 스폰서 요구 요약, 통합 모드, 이야기 호환 사용 사례, 광고 비트 맵, 필수 주장/비주얼 체크리스트, 고지 계획, 본편 복귀, 톤/신뢰 위험. 제품 영상은 추가로 제품 SSOT·시각 시퀀스·히어로 조명 계획·매크로/도포 계획·VFX 분리·팩샷 QA.\r\n\r\n### 20-visual-mode-ssot.md\r\n# 비주얼 모드·SSOT 티어·연속성 (온디맨드 심화)\r\n\r\n모듈 05(시각 구조), 11(AI 인계), 14(에셋 운영)의 심화. 반복 인물/제품/세계가 여러 샷·회차·생성에 걸쳐 정체성을 유지해야 할 때 연다. 사용자가 제공한 SSOT·바이블은 authoritative로 보존하고, 빈 필드는 명시적 창작 위임이 있을 때만 `proposal` 라벨로 채운다 — 실존 인물의 문서화되지 않은 사실은 추론으로 만들지 않는다.\r\n\r\n## 1. 비주얼 모드 선택\r\n\r\n캐릭터 시트·제작 이미지 생성 전에 표현 체계를 정한다. 스타일은 장식이 아니라 SSOT 요구·모션 기대·조명·질감·카메라 언어·모델 라우팅을 바꾼다.\r\n\r\n1. 브리프·레퍼런스·플랫폼·장르·반복/예산 여유·정체성 연속성 요구를 읽는다.\r\n2. 사용자의 명시 선택은 authoritative다.\r\n3. 미지정이면 브리프에 맞는 서로 다른 표현 방향과 추천 이유를 제시한다. 후보 수는 요청과 필요한 비교 폭으로 정한다. 중요한 방향은 사용자 수락 또는 명시적 창작 위임 뒤에 잠그며, 위임받은 경우 선택 이유를 기록해 계속한다. 정지/영상 생성 승인은 별도다.\r\n4. 비주얼 모드 ID를 잠그고 시각 규칙(룩 바이블)에 기록한다.\r\n5. 렌더링 차원을 정의한다: 표현(실사/스타일라이즈드 실사/2D/3D/스톱모션/일러스트/혼합)·리얼리즘 수준·인물 비율·재질/질감 논리·조명 논리·렌즈/카메라 리얼리즘·모션 리얼리즘·색 체계·선/렌더 처리.\r\n6. 이미지 생성·영상 생성·피니싱 전 구간에서 유지해야 할 것을 정한다.\r\n7. 모드별 SSOT 요구는 아래 참조 팩 표, 생성 요구는 [프로덕션 실행·비용 라우팅](24-production-execution.md)으로 보낸다.\r\n\r\n### 선택 메뉴 (선택이 유용할 때)\r\n\r\n- A. 실사 — 믿을 수 있는 피부·광학·재질·물리 조명.\r\n- B. 스타일라이즈드 실사 — 사실적 해부 + 의도적 아트 디렉션.\r\n- C. 2D 애니메이션 — 그래픽 형태·선/색 일관성·포즈 가독성.\r\n- D. 3D 애니메이션 — 안정된 볼륨·재질·모델 시트 턴어라운드·통제 조명.\r\n- E. 스톱모션/미니어처 — 촉각 재질·수제 불완전성·연출 조명.\r\n- F. 일러스트/그림책 — 회화적·그래픽적 정지 이미지 우선 서사.\r\n- G. 하이브리드 — 어떤 레이어가 어떤 표현을 쓰는지 명시 정의.\r\n- AUTO — 레퍼런스와 콘텐츠 목표에서 추론.\r\n\r\n### 모드별 고정 사항\r\n\r\n- 실사: 정체성 충실도·피부/머리카락·의상 재질·렌즈 거동·물리적 조명·표정 참조. 중립 정체성 참조에 극단적 그레이딩을 입히지 않는다.\r\n- 스타일라이즈드 실사: 해부 과장·얼굴 비율·질감 선명도·팔레트·스타일화 강도를 잠근다. 샷마다 일반 실사나 카툰으로 표류하지 않게 한다.\r\n- 2D: 모델 시트 비율·실루엣·선 굵기·팔레트·명암 단순화·눈/입 구조·포즈 언어. 턴어라운드와 표정 시트가 실사 질감보다 중요하다.\r\n- 3D: 볼륨·재질 반응·표면 거칠기/반사·헤어/털 처리·리그 친화 비율·중립 스튜디오 조명. 앞/옆/뒤/3/4 뷰가 중요하다.\r\n- 스톱모션/미니어처: 재질 스케일 단서·수제 표면·미니어처 심도 논리·실물 조명 느낌·프레임 간 촉각 일관성.\r\n- 일러스트: 붓/선 처리·형태 언어·팔레트·원근 단순화·반복 모티프 처리. 모션 생성은 통제된 image-first 워크플로가 필요할 수 있다.\r\n- 하이브리드: 레이어/시퀀스마다 표현 모드와 전환 규칙을 선언한다. 모델 표류로 우발적 혼합을 만들지 않는다.\r\n\r\n규칙: 생존 작가 이름만으로 스타일을 지정하지 말고 시각 속성으로 기술한다. 레퍼런스 영상은 페이싱·카메라 문법만 제공하고 같은 렌더링 스타일을 강제하지 않는다.\r\n\r\n## 2. 캐릭터 SSOT 티어\r\n\r\n연속성을 지킬 만큼만 SSOT를 만들고 그 이상은 만들지 않는다.\r\n\r\n- Tier A — Full SSOT: 주인공·반복 리드·반복 적대자·반복 연애 상대·시그니처 마스코트·여러 씬/회차의 정체성 핵심 인물.\r\n- Tier B — Lite SSOT: 여러 샷에 정체성이 필요한 명명된 조연·단일 회차 인물.\r\n- Tier C — 아키타입 엑스트라: 고유 SSOT 대신 재사용 캐스팅 카드(궁중 시녀·직장인·마을 사람·파티 손님).\r\n- Tier D — 군중 규칙: 개인 시트 없이 인구 구성·의상 범위·행동 군집·팔레트·배제 규칙을 정의한다.\r\n- Tier별 텍스트 깊이는 같이 간다: `designing-video-character-sheets`의 전체 canonical `CHARACTER SSOT`(섹션 0–33, [`designing-video-character-sheets/references/character-ssot-master-prompt.md`](../../designing-video-character-sheets/references/character-ssot-master-prompt.md))는 Tier A와 명시적 전체 SSOT 요청에 쓰고, Tier B/C는 `assets/character-ssot-template.md`의 필요 필드만 채운다.\r\n- **이미지 기반 전체 패키지의 필수 이미지:** 정의된 인물마다 Sheet A — 한 장의 중립 스튜디오 정체성 시트(전신 정면·3/4 전면·측면·후면 + 얼굴 정면·3/4·측면, 7뷰, 동일 인물, 중립 표정·조명, 장면 서사 없음)가 실제 파일로 필요하다. B/C/D(표정·의상·액션)는 프롬프트 스펙일 뿐 추가 생성·과금을 승인하지 않는다. 텍스트 전용/독립 작업은 파일·이미지 없이 끝난다. 글래머 초상은 실제 시트 대체가 안 된다.\r\n\r\n### 승격 기준과 절차\r\n\r\n1. 이야기/회차/시리즈의 캐스트 목록을 파싱한다.\r\n2. 정체성 핵심 반복 인물을 먼저 센다.\r\n3. 하나 이상 해당하면 Full로 승격: 회차 반복·감정 중심·즉시 재인식 필요·시그니처 의상/소품/제품 상호작용·여러 샷이 정확한 얼굴/신체 연속성에 의존.\r\n4. 짧지만 여러 샷의 명명 역은 Lite.\r\n5. 교환 가능한 배경 역은 아키타입/군중 규칙으로 묶는다.\r\n6. 티어별 정확한 수와 이유를 보고한 뒤에 참조 이미지를 만든다.\r\n7. 시리즈는 영속 레지스트리를 유지하고 새 반복 정체성이 생길 때만 SSOT를 추가한다 — `project.json`의 characters와 asset_registry를 쓰고 별도 DB를 만들지 않는다.\r\n\r\n### 참조 팩 (샷 필요에 맞게 조정)\r\n\r\n- Full SSOT — 실사/스타일라이즈드: 정면 중립 · 3/4 중립 · 측면(옆 샷이 있으면) · 전신 중립 · 주 의상 전신 · 서사 핵심 표정열 · 반복 소품 상호작용 · 후면(뒷모습 샷이 있으면).\r\n- Lite SSOT — 실사/스타일라이즈드: 정면 또는 3/4 정체성 · 전신/의상 · 필요시 표정/행동 참조 1종.\r\n- Full SSOT — 2D: 필요한 턴어라운드(앞/3/4/옆/뒤) · 전신 모델 시트 · 표정 시트 · 플롯상 중요한 손/소품 디테일 · 팔레트와 선/명암 규칙.\r\n- Full SSOT — 3D: 앞/옆/뒤/3/4 · 전신 중립 · 재질 노트 · 표정 목표 · 중요 시 헤어/털/재질 클로즈업.\r\n- 스톱모션/미니어처: 앞/옆/뒤 물리 형태 · 재질/질감 매크로 · 의상/소품 스케일 참조.\r\n- 크리처/비인간: 해부도·이동 논리·스케일 참조·실루엣 불변을 추가.\r\n- 엑스트라/군중: 개별 SSOT 대신 아키타입 보드나 군중 규칙 — 배경 인물이 서사상 중요해지면 그때 승격.\r\n\r\n규칙: 배경 엑스트라마다 Full SSOT를 만들지 않는다. 반복 인물을 글래머 초상 하나에 의존하지 않는다. 정체성 앵커와 샷별 조명/포즈/스타일 참조를 분리한다. 실존 인물의 용모가 필요한데 쓸 이미지가 없으면 정체성 정확도를 주장하기 전에 필요한 입력을 요청한다.\r\n\r\n### 정본 레코드 매핑 (이미지 기반 전체 패키지)\r\n\r\n캐릭터 SSOT 출력은 정본 `project.json`에 이렇게 연결된다(조정자가 기록, 워커는 패킷으로 제안):\r\n\r\n| 정본 필드 | 내용 |\r\n|---|---|\r\n| `characters[].persona` | `{role, personality, observable_behavior, speech}` — 모두 비어 있지 않은 문자열; 무언·해당 없음은 이유가 적힌 `N/A` |\r\n| `characters[].ssot_artifact_id` | `type=character_sheet` artifact — 실제 SSOT Markdown 에셋, synopsis artifact·버전에 의존 |\r\n| `characters[].identity_sheet_asset_id` | `mode=image_backed` 전용 — `kind=character_identity_sheet`, `entity_type=character`, `entity_id`=character_id; 인물당 실제 Sheet A 이미지 1장 |\r\n| `preproduction` | `{mode: text|image_backed, synopsis_artifact_id, storyboard_artifact_id, storyboard_sheet_artifact_ids, storyboard_split_asset_id}` — 시트 artifact ID는 한 장도 이야기 순서 배열(시트당 최대 8패널), split pointer는 실제 장면/패널 추출 manifest asset. text는 이미지 요구가 없고 image_backed 검토·실행은 text로 우회하지 않는다 |\r\n\r\n추적 체인은 synopsis artifact·버전·소스 locator → `character_sheet` artifact·버전 → 단일 `character_identity_sheet` 에셋 → 샷/패널 참조 입력이다. `mode=image_backed`에서 캐릭터를 이름으로 호출하는 샷은 그 인물의 정체성 이미지 에셋을 소비한다. 실제 이미지 검수는 시트의 각 뷰와 선언 앵커를 직접 비교한다 — 프롬프트가 생성된 시트를 뜻하지 않고, 공급자 성공은 정체성 QA가 아니다.\r\n\r\n## 3. 캐릭터 연속성 운용\r\n\r\n연속성은 프롬프트 형용사가 아니라 에셋 관리 문제다.\r\n\r\n1. 반복 인물마다 안정된 `character_id`(CH01 형식)를 부여한다.\r\n2. 많은 샷 생성 전에 SSOT를 만든다: `assets/character-ssot-template.md`. 불변 정체성과 씬 가변 상태를 분리한다.\r\n   - 불변: 얼굴 비율·눈 위치·코/입 형태·피부/털 무늬·연령대·신체 비율·키 관계·머리/털 실루엣·식별 표지·시그니처 액세서리·기준 의상 형상·관련 시 목소리 정체성.\r\n   - 가변: 표정·포즈·임시 머리 상태·먼지·땀·젖음·멍·피·의상 여밈·탈착 레이어·소지품·손상·조명 반응.\r\n3. 승인된 참조 뷰를 정의한다(위 참조 팩).\r\n4. 씬 상태는 별도로 기록한다: 오염·젖음·부상·머리 변화·소지물·의상 손상·분장·감정 상태.\r\n5. 샷마다 SSOT를 상속하고 명시된 상태 델타만 바꾼다. 샷마다 전체 정체성을 다르게 다시 쓰지 않는다.\r\n6. 연속성 앵커: 얼굴 형상·머리 실루엣·신체 비율·시그니처 액세서리·의상 형상·색/재질·소품 손.\r\n7. 인접 샷을 비교한다: 정체성 표류·의상 표류·연령 표류·좌우 반전·빠진 액세서리·설명 없는 상태 리셋.\r\n8. 생성기가 참조/캐릭터 컨디셔닝을 지원하면 승인된 참조를 쓴다. seed만으로 정체성이 보장된다고 주장하지 않는다.\r\n9. 표류가 생기면 가장 작은 영향 단위를 재생성하고 한 번에 한 변수만 바꾼다 — 재시도 절차는 [생성 영상 QA·재시도](21-generated-video-qa-retry.md).\r\n\r\n### 연속성 함정\r\n\r\n손 개수/형태 변화, 액세서리가 쪽을 옮김, 머리 길이 표류, 신체 스케일 표류, 얼굴 연령 변화, 의상 무늬 변이, 눈 색 표류, 소품 손 바뀜, 설명 없는 깨끗/더러움 리셋, 비대칭 표지의 거울 반전.\r\n\r\n연속성 검사는 `assets/continuity-ledger.csv`(shot_id·character_id·의상·소품/손·시선·화면 방향·광원 방향·진입/이탈 상태·예외 이유)로 기록한다. 생성 전에는 텍스트 원장, 생성 후에는 실제 매체와 대조한다.\r\n\r\n## 4. 군중·스펙터클\r\n\r\n지각된 규모는 \"수천 명\" 요청이 아니라 위계로 만든다.\r\n\r\n1. 히어로 이벤트와 규모 이야기를 정한다: 무엇이 무엇에 비해 커 보여야 하는가.\r\n2. 깊이 밴드를 만든다: 전경 앵커 · 중경 군집 · 배경 질량 · 환경 규모 단서 · 하늘/건축/지형.\r\n3. 군중 행동을 서로 다른 미세 행동의 군집으로 나눈다: 보기·촬영·대화·걷기·환호·대기·뒤돌기·앉기·보안/스태프·고립된 이질 존재. 안무가 의도된 게 아니면 동기화된 동작을 피한다. 개인을 모두 독립 랜덤화하지 말고 군집은 공유 맥락을 갖는다.\r\n4. 구도·빛·동작 대비·고도·깊이로 히어로 대상이 질량 위에서 읽히게 한다.\r\n5. 군중 흐름과 안전한 공간 논리를 설계한다: 출입구·동선·무대·장벽·차량·항공기·시선 방향.\r\n6. 컷 구조로 규모를 판다: 디테일/반응 → 중간 군집 → 극와이드 → 히어로 반응. 불가능한 마스터 샷 하나에 의존하지 않는다.\r\n7. 매우 큰 수는 생성 플레이트·복제/절차적 레이어·대기 효과·합성을 결합한다. `assets/crowd-map-template.md` 사용.\r\n8. QA: 반복 얼굴·복제 포즈·불가능한 밀도·떠 있는 사람·스케일 점프·차량 관통·일률적 시선·전경 깊이 부재.\r\n\r\n규모 단서: 알려진 크기의 사람/차량·겹침 깊이·대기 원근·변주된 반복 구조·시차·고각 공개·소리 밀도·지연 공개·전경 가림.\r\n\r\n## 5. 장면 공간 앵커와 선언된 세계 변형\r\n\r\n여러 샷이 같은 공간을 이어받거나 portal/불가능한 스케일을 사용할 때만 적용한다. 기존 location/world SSOT에 입구·문턱·landmark·방위·가구/소품 관계와 카메라 쪽 이동을 고정하고, 이동 전후 관객이 재정위할 화면 anchor를 지정한다. 컷/POV 변경·가림은 공간 이동이나 reset이 아니다. 유지되는 위치/소품은 [26 상태 인계](26-state-causality-continuity.md)에서 후속 상태로 잇는다.\r\n\r\n세계 규칙을 의도적으로 깨면 어느 shot/layer에서 바뀌고 ordinary space로 어떻게 돌아오는지 brief에 표시한다. portal 전후의 frame/eyeline, 방향, scale 단계와 복귀 view를 정한다. cut/dissolve/graphic wipe/composite를 비교하고 단순 cut이 더 명확하면 억지 morph를 하지 않는다. 경계 전 anchor→fantasy insert→회복 anchor를 storyboard/shot cue에 보이고, scale/방위 변화가 실제 평면도·서비스·장소 claim처럼 읽히지 않는지 inspect한다.\r\n\r\n수치 카메라·경로·3D geometry가 필요하면 `$camera-spatial-design`으로 넘긴다; 실제 장면 geometry가 필요할 때만 해당 3D review/runtime 절차를 따른다. 단일 reference frame에서 주소·지리·실제 건축·camera solve를 역산하지 않는다. 실행 가능한 공간/카메라 근거는 계획 텍스트와 구분한다.\r\n\r\n### 21-generated-video-qa-retry.md\r\n# 모션·합성·생성 영상 QA·인과 재시도 (온디맨드 심화)\r\n\r\n모듈 11(AI 인계)과 12(제작 검수)의 심화. 실제 생성/합성 매체가 있거나 복잡한 동작·접촉·VFX를 계획할 때 연다. 계획 단계에서는 설계 절차만 적용하고 실제 매체 없이 검수 통과를 주장하지 않는다.\r\n\r\n## 1. AI 모션·물리 디렉팅\r\n\r\n복잡한 동작을 통제 가능한 물리 비트로 나눈다. 걷기·달리기·무술·춤·잡기·붓기·제품 접촉·운반·충격·점프·동물의 물리 행동·천/머리카락·액체처럼 접촉·균형·무게·충돌·타이밍·동시 다발 행동 때문에 실패하기 쉬운 샷에 적용한다.\r\n\r\n1. 초기 포즈·지지점·무게중심·접촉 사물·최종 포즈를 정한다.\r\n2. 샷을 하나의 주 행동으로 표현한다. 독립 행동이 여럿이거나 변형이 끼면 샷이나 순차 생성 구간으로 나눈다.\r\n3. 해당하면 예비 → 시작 → 이동 → 접촉/충격 → 체중 이동 → 후속 → 정착으로 쪼갠다.\r\n4. 붙어 있어야 할 것을 명시한다: 발·발바닥·손·좌석·도구·제품·바닥·벽·상대.\r\n5. 동사가 아니라 궤적과 상대 운동을 기술한다: 방향·속도 변화·호·정지 조건.\r\n6. 접촉 순간의 해부·사물 무결성을 지킨다. 장식적 2차 동작보다 믿을 수 있는 접촉을 우선한다.\r\n7. 2차 동작은 주 행동이 읽힌 뒤에만 추가한다: 머리카락·천·귀·꼬리·느슨한 사물·튐·먼지.\r\n8. 액체·군중·파괴·복잡 충돌은 한 번의 생성에 요구하지 말고 합성으로 라우팅한다.\r\n\r\n### 접촉 우선순위\r\n\r\n지지와 중력 → 주 접촉 → 사물 무결성 → 신체 역학 → 2차 동작 → 장식 파티클. 낮은 우선순위 동작이 높은 항목을 해치면 제거한다.\r\n\r\n### 샷 분할 트리거\r\n\r\n중요한 접촉이 3개 이상 · 변형+이동 동시 · 여러 인물의 사물 교환 · 큰 카메라 무빙+복잡 동작 · 정밀 제품 다루기+액체 시뮬레이션.\r\n\r\n### QA와 산출물\r\n\r\n9. QA: 발 미끄러짐·떠 있는 사물·관통·불가능한 균형·손 변형·텔레포트 소품·비일관 관성·이른 동작 리셋을 검수한다. `assets/motion-beat-template.md`로 비트 시트를 만든다.\r\n### 차량 접촉 — 물리 계약이 있을 때만\r\n\r\n브리프가 물리적으로 일관된 굴림/착지를 요구할 때만 no-slip 및 지면 접촉 검사를 활성화한다. wheel radius·속도·회전 관계가 승인된 입력에 있으면 그 관계를 연속 구간에서 확인하고, 없으면 invented 수치나 정확한 구름 조건을 QA 기준으로 만들지 않는다. 스타일화·드리프트·의도적 공중부양처럼 접촉이 끊기는 구간에는 no-slip을 강제하지 않는다; 공중 구간은 contact=N/A로 두고 지지점이 돌아오는 착지부터 다시 검사한다.\r\n\r\n한 프레임의 정지/역회전 spokes는 rolling failure 증명이 아니다. 여러 연속 프레임에서 wheel/hub의 화면 위치뿐 아니라 ground texture, contact patch, 차체 높이·이동, camera tracking, shadow/reflection을 함께 비교한다. Temporal aliasing/shutter sampling이나 compositing을 대안으로 남기고, 실제 프레임 연속성에서 회전·지면 이동이 양립하지 않는 interval을 찾았을 때만 failure로 기록한다. 결과 레이어의 splash/wake/residue도 원인 위치·방향·후속 지속 또는 명시된 reset에 연결한다.\r\n\r\n## 2. VFX·합성 수퍼비전\r\n\r\n어려운 샷을 한 번의 생성에 억지로 넣지 않는다. 레이어 구성이 더 통제 가능할 때 분해한다.\r\n\r\n1. 샷을 단일 플레이트로 생성할지 레이어로 분해할지 정한다.\r\n2. 레이어 스택을 정한다: 배경 · 중경 · 히어로 피사체 · 제품/소품 · 그림자 · 반사 · 대기 · 파티클 · 타이포/UI · 전경 가림. `assets/vfx-layer-stack-template.md` 사용.\r\n3. 색보다 카메라 형상을 먼저 맞춘다: 지평선·원근·스케일·렌즈 느낌·심도·모션.\r\n4. 조명을 맞춘다: 키 방향·부드러움·강도 관계·색온도·림·바운스·접촉 그림자·반사광.\r\n5. 가림·대기 깊이·모션 블러·디포커스·그레인/노이즈·정당할 때만 라이트 랩으로 가장자리를 통합한다.\r\n6. 반사와 그림자는 실제 표면과 움직임을 따른다. 일반적인 뜬 드롭 섀도를 피한다.\r\n7. 텍스트·로고·정확한 패키지는 생성 충실도가 부족하면 통제된 그래픽/제품 레이어로 유지한다.\r\n\r\n### 매칭 순서와 경고 신호\r\n\r\n형상 → 모션 → 조명 → 접촉 → 깊이 → 색 → 질감/그레인 → 광택. 경고: 떠 있는 피사체·흐린 플레이트 위 선명한 전경·불일치 셔터/모션 블러·다른 그레인 주파수·어울리지 않는 블랙 레벨·잘못된 광원 측·그림자 방향 불일치·틀린 환경 반사·안개 낀 장면의 완벽한 컷아웃 가장자리.\r\n\r\n전체 프레임과 클로즈 줌 둘로 검수한다: 가장자리 헤일로·불일치 블랙·불일치 그레인·틀린 블러·뜬 발·빠진 접촉 그림자·원근 불일치·불가능한 반사.\r\n\r\n## 3. 생성 매체 QA\r\n\r\n실제 매체를 판정하고 프롬프트를 판정하지 않는다. 파일이나 필요한 프레임/오디오가 없으면 해당 항목을 unverified로 남긴다.\r\n\r\n### 검사 순서\r\n\r\n실제 매체를 이 순서로 본다 — 부합(요청한 대상/행동/의도가 실제로 나왔는가) → 모션(접촉·균형·시간 안정) → 정체성(SSOT·제품 정확도) → 카메라(프레이밍·방향·공간) → 오디오(입·목소리·소리 원근) → 기술 규격(길이·화면비·해상도·프레임 무결성·필요 시 오디오 존재). 앞 단계의 blocker가 보이면 뒤 패스의 세부 미학 판정으로 넘어가지 않는다.\r\n\r\n### 검사 패스 (여러 모드로 본다)\r\n\r\n1. 정속 시청(소리 포함) 2. 정속 무음 3. 의심 구간 슬로/스텝 4. 시작·핵심 접촉·끝의 정지 프레임 비교 5. 샷 간 연속성 비교 6. 대사/소리가 중요하면 오디오만 듣기.\r\n\r\n- 정체성 패스: 승인 SSOT와 인접 샷에 대해 얼굴/몸/머리/털/의상/액세서리 비교.\r\n- 사물/제품 패스: 실루엣·비율·캡/부품·라벨·로고·스케일·손 접촉·반사·텍스트 가독성.\r\n- 모션 패스: 발과 손부터 본다. 예비·접촉·체중 이동·후속·충돌·미끄러짐·튐·해부 초과/결손·사물 영속성.\r\n- 시간 패스: 플리커·모핑·질감 기어감·불안정 그림자·사라지는 디테일·배경 호흡·서사와 무관한 조명 변화.\r\n- 카메라/공간 패스: 지평선·렌즈 느낌·원근·프레이밍·시선·화면 방향·동기 있는 움직임·편집이 요구한 시작/끝 상태.\r\n- 합성 패스: 가장자리·깊이 순서·접촉 그림자·광원 방향·그레인/노이즈·모션 블러·심도·블랙/화이트 레벨·대기 통합·반사 논리.\r\n- 연기/오디오 패스: 시선·표정 전환·반응 타이밍·대사 의도·입 타이밍·숨·멈춤·노이즈·클리핑·소리 원근과 화면 일치.\r\n\r\n### 판정\r\n\r\n이슈마다 `타임코드 → 관찰 → 관객 영향 → 심각도 → 추정 원인 → 권장 경로 → 재검수 기준`으로 기록한다. 심각도와 판정은 모듈 12의 blocker/major/minor와 pass/pass_with_notes/needs_revision을 사용한다. 생성 결함은 아래 재시도 절차로, 창작/서사 실패는 상위 모듈로, 정확한 그래픽과 레이어 통합은 합성 절차로 되돌린다. `assets/generated-qa-report-template.md` 사용.\r\n\r\n실제 매체를 검사하지 않고 가상의 품질 점수를 매기지 않는다. 사용자 제공 루브릭과 실제 검사가 있을 때만 점수를 쓴다.\r\n\r\n### 프리뷰 판정과 최종 검수\r\n\r\n실제 출력만 판정한다: 짧은 프리뷰는 뒤 구간의 동작·접촉·연속성을 증명하지 않으므로 보이지 않은 대상을 통과로 쓰지 않는다. 수락/수정/경로 변경은 [생성 경로·비용 라우팅](24-production-execution.md) §5의 프리뷰 계획 대상과 승격 경로로 되돌린다. 프리뷰 수락은 최종 승인이 아니며, 최종본의 동작·정체성·오디오·기술 규격은 다시 검수한다 — 같은 seed·입력의 재생성은 같은 동작을 보장하지 않는다.\r\n\r\n### 상태·인과 검수 (선택적)\r\n\r\n직접 또는 앞선 샷에서 이어받은 [상태·인과 슬롯](26-state-causality-continuity.md)이 있는 샷에 적용한다. 판정 enum과 실패 분류는 그대로이며, 여기서는 근거 위치와 미검증 구분만 추가한다.\r\n\r\n- **구간 검사**: 시작·끝 프레임이 달라 보이는 것만으로 원인 동작이 성립했다고 판정하지 않는다. 접촉/변화가 진행되는 구간을 실제로 본다. 구간을 보지 못했으면 전이를 unverified로 남긴다.\r\n- **후속 경계**: 선언한 유지 범위 안의 모든 해당 후속 컷 경계·재등장 상태를 문서화된 리셋까지 대조한다. 중간 정지 컷·가림도 의무를 지우지 않으며 의도적 리셋과 상태 리셋 오류를 구분한다.\r\n- **가림**: 가려진 동안 안 보인 특징을 상태 역전·삭제로 판정하지 않는다. 가림 전 관측과 재등장 관측을 비교하고, 재등장이 없으면 미확인으로 둔다.\r\n- **결합 응답**: 인계된 대상쌍이 있으면 양쪽의 응답을 각각 본다. 응답 구간을 검사할 수 없으면 unverified로 남기고, 검사했는데 요구된 응답이 실제로 빠져 있으면 모션/물리 실패로 분류해 needs_revision으로 되돌린다.\r\n- **생략**: 승인된 서사 생략은 전후 상태와 관객이 읽는 인과가 브리프를 충족할 때만 허용한다. 생략 표기만으로 필수 시연을 면제하거나 보이지 않은 동작을 증명하지 않는다. 생략된 동작 자체는 unverified로 남기고, 관찰된 필수 행동 누락은 needs_revision으로 되돌린다. 경계·인과 누락을 빠른 컷이나 음악으로 감추지 않는다.\r\n- 새 활성 조건과 상속된 유지 의무가 모두 없는 `N/A` 샷에만 이 패스를 적용하지 않는다.\r\n\r\n### 실행·상태 수명 주기\r\n\r\n선택 실행자의 실제 호출 계약(API·CLI·연결 도구 중 실제 것)으로만 승인된 범위를 제출한다. 비동기 작업은 그 도구의 대기/폴링 규칙을 따르고 실제 요청·작업·결과 ID와 대기 상태를 연결된 실행 산출물에 기록한다. 상태가 불명이면 먼저 그 도구의 상태 확인으로 결정하고, 실패·부분 성공을 그대로 보고한다 — 제출 성공 여부를 확인할 수 없을 때 다시 호출해 중복 실행·과금을 만들지 않는다. 실제 결과 파일을 받아 검사한 뒤에만 성공으로 기록한다. 자신의 검사와 사용자의 관찰 보고를 구분하고, 수정은 성공 속성을 보존한 채 한 번에 한 주요 변수만 바꿔 §5에 기록한다. 과거 시도 기록은 보존하며 입력 버전 변경 시 영향받는 종속 산출물·승인만 stale로 표시한다; 시도에 별도 stale 상태를 만들지 않는다.\r\n\r\n## 4. 완성 시퀀스의 모션·리듬·오디오 QA\r\n\r\n클립별 생성 QA를 통과한 것만으로 광고/몽타주의 역동성이나 편집 싱크를 승인하지 않는다. 완성 타임라인에서 확인한다.\r\n\r\n1. 편집본·오디오·타임라인의 artifact ID와 버전을 고정한다. 검사 범위(전체 재생, 표본 프레임, 오디오 단독)를 각각 기록한다.\r\n2. 역동성 요청이면 샷마다 실제 피사체 동작, 카메라 동작, 제품/정보 공개, 정지/정착 중 무엇이 시간에 따라 바뀌는지 적는다. 컷 속도나 디졸브만으로 모션을 대체했다고 판단하지 않는다.\r\n3. 실제 편집본을 정상 속도와 최종 믹스로 재생해 전체 페이싱·전환을 확인한다. 중요한 접촉·충격·제품 공개는 프레임/타임코드와 오디오 동기 기준점을 대조한다. 무음·오디오 단독 검수는 요청과 문제 유형에 맞게 추가한다.\r\n4. 샘플 프레임만 검사했으면 모션의 중간 프레임, 전환의 실제 길이, 전체 음악 적합성은 미검증으로 둔다. 청취하지 않은 음원의 품질이나 싱크를 통과로 쓰지 않는다.\r\n5. 오디오가 참조 영상의 단일 혼합 트랙이면 분리 BGM/SFX stem이 없음을 기록한다. 분석 도구가 찾은 파형 피크는 청취 판정이 아니며, 음원 권리는 별도 확인한다.\r\n6. 정지/거의 정지된 원본은 요청된 비트가 실제 움직임을 요구하는지 먼저 판단한다. 의도된 제품 히어로 홀드로서 화면 내용·가독성·타이밍이 이를 뒷받침할 때만 보존한다. 정지 상태라는 이유만으로 보조 컷이나 엔드카드 역할을 추정하지 않는다. 동작이 필요한 비트가 성립하지 않으면 더 강한 실제 동작 구간을 선택하거나 샷 교체안을 낸다. 확대/전환 효과만으로 움직임을 꾸며내지 않는다. 새 생성·유료 실행은 별도 승인과 기존 비용/재시도 상한을 따른다.\r\n\r\n보고에는 타임라인 범위·실제 검사 모드·도구/파일·관찰된 타임코드·미검증 항목·재검수 기준을 포함한다. `assets/generated-qa-report-template.md`를 사용한다.\r\n\r\n## 5. 인과 재시도 제어\r\n\r\n실패한 생성은 진단 문제다. 매번 전부 다시 쓰지 말고 가장 이른 통제 가능 원인을 고친다.\r\n\r\n### 실패 분류\r\n\r\n- 정체성: 얼굴 표류·신체 비율 변화·의상/액세서리 표류·종/연령 변화.\r\n- 제품/그래픽: 형태 표류·캡/라벨 변화·로고/텍스트 손상·재질 불일치·틀린 스케일.\r\n- 모션/물리: 초과 사지·발 미끄러짐·깨진 접촉·텔레포트·불가능한 균형·사물 관통·이상한 유체.\r\n- 시간: 플리커·모핑·질감 기어감·사라지는 사물·불안정 배경·불연속 조명.\r\n- 카메라/구도: 틀린 프레이밍·의도 없는 줌/팬·피사체 이탈·지평선/원근 불일치·시선/화면 방향 단절.\r\n- 연기: 틀린 감정·늦은 반응·입 불일치·죽은 눈·의도와 다른 제스처.\r\n- 합성: 나쁜 가장자리·빠진 접촉 그림자·틀린 깊이·불일치 블러/노이즈/색·스케일/원근 불일치.\r\n- 창작: 불명확 아이디어·약한 보상·중복 샷·낮은 감정 가치. 맹목적 재생성 대신 상위로 보낸다.\r\n\r\n### 실패 → 수정 매핑\r\n\r\n| 관찰된 실패 | 첫 수정 | 상승 경로 |\r\n|---|---|---|\r\n| 부합 불일치(요청한 대상/행동이 아님) | 프롬프트를 요청 의도·주 행동·끝 모호 · 약한 참조 제어 · 과도한 행동 복잡성 · 모델 능력 불일치 · 나쁜 초기 프레임 · 연속성 의존 · 합성 필요 · 확률적 분산.\r\n4. 고칠 가능성이 큰 가장 작은 개입을 고른다. 실용적으로 한 번에 한 주요 변수만 바꾼다.\r\n5. 재시도 시 성공한 속성을 명시적으로 보존한다.\r\n6. 반복 실패 시 무차별 재시도 대신 상승한다: 행동 단순화 → 샷 분할 → 레이어 분리 → 모델/워크플로 변경 → 더 나은 참조 에셋 → 정확한 요소 합성 → 서사 목적을 유지한 샷 재설계.\r\n7. 재시도 예산을 지킨다. 다음 생성의 기대 가치가 전략 전환보다 낮으면 멈춘다.\r\n8. 성공 설정이 재사용되도록 매 시도를 `project.json`의 `generation_attempts`에 기록한다(계약 v1.1). 샷 `retry_budget`은 승인된 `video_execution_plan`의 상한에서 온다.\r\n\r\n### 재시도 사다리\r\n\r\n프롬프트 명료화 → 참조/첫 프레임 교정 → 행동 단순화 → 길이/타이밍 조정 → 샷 분할 → 모델/워크플로 재라우팅 → 레이어 분리/합성 → 서사 목적 유지 샷 재설계.\r\n\r\n### 규칙\r\n\r\n- 한 번에 한 변수: 재시도마다 하나의 주요 변수만 바꾸고 변경 내용을 generation_attempts.changes에 남긴다. seed는 재현 힌트일 뿐 정체성·품질 보장 수단이 아니며, seed만 고정한 재시도를 원인 수정으로 세지 않는다.\r\n- 경계 있는 재시도: 샷 retry_budget과 승인된 실행 계획의 비용·시간 상한 안에서만 시도한다. 상한 초과 전에 전략 전환(분할/재라우팅/합성) 또는 unverified 보고로 닫는다.\r\n- 관객이 인지하는 연속성 실패를 빠른 편집으로 숨기지 않는다.\r\n- 정체성 표류를 수십 개 형용사로 고치지 않는다: 정규 참조를 강화하고 상충 지시를 줄인다.\r\n- 정확한 텍스트/로고는 반복 생성보다 합성을 우선한다.\r\n- 접촉 중심 물리는 동시 행동을 줄이고 초기/접촉/끝 상태를 정의한다.\r\n- 생성 실패와 창작 실패를 구분한다. 완벽히 렌더링된 지루한 샷은 재시도가 아니라 콘셉트/편집으로 돌아간다.\r\n\r\n### 26-state-causality-continuity.md\r\n# 상태·인과·연속성 인계 (온디맨드 심화)\r\n\r\n모듈 11(AI 인계)·21(생성 QA)·09(편집)·25(레퍼런스 분석)의 공통 인터페이스. 샷 사이에서 변한 상태와 유지해야 할 속성을 다음 모듈로 넘기는 **선택적** 인계 슬롯이다. 실행 순서·모션 비트·합성·카메라 제어·재시도 절차 자체는 각 모듈에 남아 있으며, 여기서는 재현하지 않는다. 프로젝트 스키마·전역 상태 DB·새 JSON 계약을 만들지 않는다 — 기존 shot/artifact ID와 버전에 행만 추가한다.\r\n\r\n## 언제 연다\r\n\r\n해당하는 조건의 행만 적용한다. 샷 자체의 변화뿐 아니라 앞선 샷에서 이어받은 후속 유지 의무도 활성 조건이다. 둘 다 없는 샷·시퀀스에는 이 모듈을 열지 않는다.\r\n\r\n| 활성 조건 | 넘길 최소 계약 | 검사할 증거 위치 | 실행·검수 담당 table을 채워 shot plan에 반환한다.** 컷 phase/hold은 기존 09 편집 슬롯에, 채택 카메라 지시와 지원 상태는 기존 11 인계 슬롯에 기록한다(`UNKNOWN` until endpoint support is checked). 보편적 gait timing은 정하지 않는다. 상세 곡선은 [카메라 무빙 타이밍](../../camera-spatial-design/references/motion-timing-lens.md)을 따른다.\r\n7. 시선·화면 방향·180도 축·행동 축을 검수한다. 축을 넘으면 중립 샷·연속 이동·새 공간 설명 등 관객을 재정위시키는 수단을 명시한다.\r\n8. 편집 핸들, 룸톤, 소품 인서트와 반응 샷을 확보한다. 장소·광원·세팅으로 촬영 순서를 묶고 이야기 순서와 구분한다.\r\n9. 패널에서 핵심 행동의 실루엣, 인물·소품 겹침, 주목점·시선 유도, 필요한 깊이·대비 및 최종 출력 크기에서의 판독성을 확인한다. 필수 정보가 읽히지 않으면 구도·스테이징·시점 또는 패널 분할을 고친다.\r\n10. 동작 중심 비트의 start/action_peak/end 이미지는 실제 시간 상태 차이를 보여야 한다. 인접 패널에 자세·행동·손-제품 접촉·시선·공간 관계의 변화가 없으면 키프레임을 다시 스테이징한다. 제공된 인물/제품 reference를 완성된 컷아웃으로 붙이지 않고, 제품이 장면의 원근·광원·접촉 안에서 읽히는지 확인한다.\r\n11. 스토리보드가 텍스트 설명뿐이면 이미지가 완성됐다고 말하지 않는다. 실제 그림/프리비즈가 있으면 카메라와 블로킹을 비교한다.\r\n\r\n### 정보 단위와 POV/반응 인계\r\n\r\n하나의 scene에 여러 shot이 있을 수 있고, 한 shot도 여러 action-phase를 포함할 수 있다. 장면에서 actor/camera/action 변화가 없다면 event detector나 시각 grain마다 새 shot을 만들지 않는다. 반대로 POV 이동과 상대의 reaction은 서로 다른 정보/관점을 전달할 때 각각 목적·진입/종료 상태가 보이는 shot으로 분리한다. 같은 continuous shot에서 양쪽을 실제로 볼 수 있으면 한 shot 안의 phase로 적고, 관찰되지 않은 reverse/cut을 가정하지 않는다.\r\n\r\n특히 상대의 표정을 보여 주는 host/reverse shot에서 guest의 POV 전환·후속 이동을 같은 shot에 연속 서술하지 않는다. host reaction은 그 shot에 보이는 host/구도에 한정한다. guest의 시선·POV·복귀 동작은 별도의 shot 또는 같은 프레임에서 양쪽을 실제로 볼 수 있도록 의도한 구도로 계획하고, 그 연결이 불명확하면 06의 shot ID/time/blocking/관점·공개 필드를 분리해 09의 컷 순서와 잇는다. shot 한 행/ID에 여러 관점이 들어가도 관객에게 실제로 함께 보이는 근거가 있어야 한다.\r\n\r\n각 shot에는 초점 대상, 새 정보, 행동의 주체·상대, reaction cue, 종료 상태를 기존 shot/beat/cue 필드에 기록한다. 핵심 반응이나 product handoff가 앞 shot의 자극에 의존하면 cut order와 cue를 [09-edit](09-edit.md)에 연결한다. 캐릭터 목표/실행 가능한 action은 [04-performance](04-performance.md), 지속 상태와 가림 뒤 재등장은 해당할 때만 [26-state-causality-continuity](26-state-causality-continuity.md)로 넘긴다. Copy가 행동을 약속하면 텍스트 상태와 행동을 맞추되 shot count나 endcard/CTA를 새로 의무화하지 않는다.\r\n\r\n위계/스케일 농담에서 아동과 성인의 대상/역할을 마주 놓을 때, 두 인물·시간·관계가 같은지 브리프에서 정하고 storyboard의 기존 character/shot identity를 맞춘다. 명시된 허구가 아니면 아동이 실제 차량을 운전하거나 위험한 행동을 하는 것처럼 staging하지 않는다. copy가 한 뜻에서 다른 뜻으로 바뀌면 두 화면 상태와 각각의 대상/행동을 별도로 적는다; 연결점이 불분명하면 단순 cut 또는 copy 변경을 비교한다.\r\n\r\n목격자/대상 반응 사다리가 필요할 때만 사건→개별 시선→집단 반응→원인 대상/역방향 정보→문구 순서를 계획한다. 각 반응을 독립 cut으로 강제하지 않고, 같은 scene의 여러 phase일 수 있는지 검토한다. 확인 가능한 eyeline과 공간 관계를 맞추고 표정만으로 목격, 말, 동의, 동일 사건을 추정하지 않는다. 관련 장르 기대/closure는 실제 comedy brief일 때만 [17-genre-comedy](17-genre-comedy.md)에서 판단한다.\r\n\r\n숙박/서비스/장소를 따라가는 브리프에는 입구→경로→문턱→기준 landmark→목적지와 복귀를 scene/shot fields의 공간 기준으로 선언한다. 프레임/POV가 바뀌어도 landmark·방향·소품 소유 관계를 유지한다. 미니어처/portal scale break는 ordinary space와 분리된 fantasy view 및 복귀 shot/phase를 표시한다; 가림·wipe만으로 실제 floorplan이나 이동 거리를 증명하지 않는다. 수치 spatial/camera 요청은 기존 `$camera-spatial-design` handoff를 사용한다.\r\n\r\n화면 안 화면·인셋이 관객 시선을 나눌 때만 main/secondary 정보, 공개 순서, 기준 anchor, 각 창의 시간·공간·출처가 같은지/다른지 기록한다. 동시 inset이면 동시 동작을 보이는지, 과거/별도 세계의 insert면 그 시간·공간 전환이 읽히는지 명시한다. 실제 출력 크기와 크롭에서 각 창의 대상·행동·타이포를 검사한다; flash나 detector event 수만으로 리듬/beat를 만들거나 동시성을 주장하지 않는다.\r\n\r\n## 산출물 목적 구분 — 스토리보드·샷리스트·애니매틱·프리비즈\r\n\r\n같은 샷 ID를 공유해도 네 산출물은 목적이 다르며 하나가 다른 하나를 대체하지 않는다. 영화 라이프사이클에서는 [영화 제작 라이프사이클](28-film-production-lifecycle.md)의 03 Pre-production 라우팅을 따른다.\r\n\r\n- **스토리보드**: 이야기·정보 공개를 설명하는 시각 설명물. [완전한 스토리보드 계약](storyboard-contract.md)이 panel→shot→scene 연결과 이미지 검수를 소유한다.\r\n- **실행 샷리스트**: 촬영/생성 지시용 기술 목록(`assets/shot-list.csv`, `06-shots-template.md`). 계획된 촬영 순서는 장소·광원·세팅·배우 가용 기준으로 묶고 **이야기 순서와 별도 열**로 기록한다.\r\n- **애니매틱**: 시간축 위의 순서 검증용 임시 편집물(타이밍·임시 소리). 완성 영상이나 실제 녹음이 아니다.\r\n- **3D 프리비즈**: 공간·카메라 경로의 수치 검증(→ `camera-spatial-design`, `blender-previsualization` 인계). 미감·연기를 보장하지 않는다.\r\n\r\n**이야기 순서 ≠ 촬영 순서.** 이야기 순서는 스토리보드 패널 배열과 최종 타임라인 순서다. 촬영 순서는 세팅·자원 기준 실행 순서로서 이 템플릿의 계획 열에 두고, 실제로 촬영된 순서는 실사에 한해 `assets/film-production-day-template.md`의 촬영 순번에 별도 기록한다. 둘을 한 필드로 섞거나 촬영 순서로 이야기 순서를 덮어쓰지 않는다.\r\n\r\n## 완료 조건\r\n보드의 목적에 맞는 촬영 가능한 커버리지와 방향성이 확보됐는가? 각 샷의 관점·구도 선택이 의도한 정보와 감정을 전달하는가? 실제 이미지가 있으면 필수 행동과 주목점이 읽히는가? 동작 중심 panel은 인접 keyframe에서 자세·행동·제품 접촉/위치가 실제로 달라지는가?\r\n\r\n## 근거와 적용 범위\r\n자료 ID: 04,05,06,07,08. `sources.md`에서 파일 상태와 탐색 위치를 확인한다. 절차와 템플릿은 여러 자료의 개념을 결합한 독자 설계다. 저자의 규칙을 그대로 재현한 요약이나 공식 인증된 방법론으로 표현하지 않는다.\r\n\r\n## 출력 템플릿\r\n`assets/06-shots-template.md`를 복사해 채운다.\r\n\r\n스토리보드가 요청되면 `assets/storyboard-panels.csv`를 정본 project.json의 투영으로 작성해 panel_id→shot_id→scene_id와 패널별 `beat_ids`/원문 위치·`visible_character_ids`·`audio_cue_ids`·`speech_ids`를 연결한다. 샷 단위 목록을 패널 목록으로 대신하지 않는다. `frame_time_s`는 패널의 기준 시각이며 연결한 음향 큐와 발화의 시간 구간에 포함돼야 한다. 실제 image_asset_id를 등록하고 텍스트 계획만 있으면 planned/drawing_pending으로 구분한다. 상세 보드는 모든 씬/샷의 시작·필요 정점·끝 패널 또는 정지 hold를 포함하고 이미지 수를 사전 계산한다. 필수 행동이 가려지거나 설명 없이 인과가 끊기면 해당 인덱스를 수정한다.\r\n\r\n## 전문 스킬 인계\r\n`$camera-spatial-design`으로 위치·거리·렌즈·각도·구도·전 프레임 경로를 수치화하고, 장면별 3D 카메라/공간 작업은 `$blender-previsualization`으로 실제 구현·시각 검수를 반드시 수행한다. `camera_spec.json`의 로컬 프레임을 기존 샷의 start_s/end_s와 연결하고 total duration을 대조한다. Blender 미실행 시 3D 화면 검증은 BLOCKED/UNVERIFIED다.\r\n\r\n## 심화 참조\r\n복잡 접촉·동작 분할은 [생성 영상 QA·재시도](21-generated-video-qa-retry.md)의 모션 절차(`../assets/motion-beat-template.md`), 군중·스펙터클은 [비주얼 모드·SSOT](20-visual-mode-ssot.md) §4(`../assets/crowd-map-template.md`).\r\n\r\n### video-production-assets\\references\\09-edit.md\r\n# 편집·리듬·사운드\r\n\r\n## 입력과 산출물\r\n입력: 샷·테이크, 음성, 비트, 목표 길이\r\n\r\n산출물: 컷 계획, 시간표, 사운드 큐, 수정 리스트\r\n\r\n## 실행 절차\r\n1. 테이크를 감정 진실성·서사 정보·동작·기술 상태로 비교한다. 실제 영상을 보지 못하면 설계안으로 표시한다.\r\n2. 컷마다 관객 감정과 이야기 진행을 우선 확인하고 리듬·시선 유도·평면/공간 연속성을 검토한다. Murch의 선호를 자동 점수 공식으로 만들지 않는다.\r\n3. 신체 리듬·감정 리듬·사건 리듬을 구분한다. 컷 길이만 줄이지 말고 들어가는 시점·나오는 시점·반응의 위치를 바꾼다.\r\n\r\n4. 편집은 언제 정보를 숨기고 드러낼지 결정한다. J/L 컷, 오프스크린 소리, 침묵은 장면 목적이 있을 때만 쓴다.\r\n5. 대사·환경·효과·음악·침묵에 기능을 배정한다. 음악이 연기 결핍을 덮거나 대사를 가리지 않도록 확인한다.\r\n6. 실제 오디오 큐·생성·외주 전에 요청의 오디오 의도를 분류하고 실행자가 실제 지원하는 제어를 확인한다(아래 \"오디오 의도와 실행 경로\"). 음악·효과음을 외부에서 가져오면 \"음악·효과음 소싱과 권리\"의 근거 절차를 거친다.\r\n7. 시청 검수는 소리 포함 / 무음 / 화면 없이 듣기로 나눠 전달 결함을 찾는다. 최종 음량·자막·해상도는 목적지 규격을 확인하고 실제 파일에서 측정한다.\r\n동작 중 컷이 발생하면 편집 계획에 컷아웃 action phase/end state와 대응하는 다음 샷 컷인 phase/start state 및 제안한 최종 타임라인 cue 시각을 반드시 기록한다. 일반 연속성 메모만으로 대체하지 않는다. 반응/정착 hold가 러닝타임을 차지하면 그 구간의 제안 시작·끝을 샷의 최종 시간 범위 안에 기록한다. 제안 시간과 측정된 편집 시간을 구분한다.\r\n문자·로고·엔드카드가 실제 비트의 핵심일 때만 각 표시 상태의 시작→정착→읽기 홀드→퇴장/전환을 `assets/09-edit-template.md`의 기존 컷/카피/안전 영역/홀드 설명에 연결한다. 단어 변화(예: 질문→해석 전환)는 서로 다른 정보 상태로 구분하고 시작·종료 cue를 제안 타임라인에 둔다. 읽기 홀드는 최종 출력 크기·문구 길이·언어·사용자가 승인한 기준으로 정하며 보편적인 고정 초를 두지 않는다. 필수 고지와 정확한 아트워크는 승인된 원본/레이어로 잠그고, 읽히지 않으면 타이밍·레이아웃·컷을 고친다.\r\n\r\n엔드카드/CTA에는 브리프가 요구하는 카피·URL·고지만 쓴다. 오퍼/날짜/CTA의 읽기 홀드가 필요한 경우 해당 상태를 먼저 실제 타임라인에 배정한 뒤에만 뒤이은 코다를 비교한다. 코다가 메시지나 법률 문구를 가리면 제거/축약한다. 마지막 검정 구간이나 로고 초기화는 실제 확인한 타임라인의 화면 상태로 적는다. 자동 캡션/ASR는 음성 큐나 발화 시각의 근거가 아니며 원본 컷 시간을 새 카피 싱크로 복사하지 않는다.\r\n\r\n## 완료 조건\r\n컷이 감정 또는 정보를 바꾸는가? 대사가 명료한가? 전체 길이와 컷 간 방향성이 맞는가?\r\n\r\n## 근거와 적용 범위\r\n자료 ID: 04,09,10,11,12. `sources.md`에서 파일 상태와 탐색 위치를 확인한다. 절차와 템플릿은 여러 자료의 개념을 결합한 독자 설계다. 저자의 규칙을 그대로 재현한 요약이나 공식 인증된 방법론으로 표현하지 않는다.\r\n\r\n## 출력 템플릿\r\n`assets/09-edit-template.md`를 복사해 채운다. 영화 라이프사이클의 후반 단계 추적에는 `assets/film-postproduction-template.md`를 함께 쓴다.\r\n\r\n## 배속과 원본\r\n배속·슬로모션 샷은 source_in_s와 playback_rate를 적고 실제 원본 길이와 최종 구간을 구분한다. 디졸브·오디오 중첩은 별도 레이어로 표현하며 기본 JSON 샷 구간은 최종 영상의 대표 구간을 겹치지 않게 배정한다. 실제 전환 프레임은 편집 타임라인에서 재검수한다.\r\n\r\n## 시간 압축·생략의 획득 방식과 상태\r\n\r\n시간을 줄이는 편집은 획득 방식을 먼저 구분한다 — 같은 \"4시간 → 8초\"라도 기록해야 할 근거가 다르다.\r\n\r\n- **연속 소스 배속**: 연속 녹화의 한 구간을 재생 속도로 압축. `playback_rate`와 source 구간에 실제 측정값을 적는다.\r\n- **인터벌 획득(타임랩스)**: 간격 샘플링으로 촬영. 실제 촬영 구간·프레임 간격·중단/공백의 근거(촬영 로그·파일 타임스탬프·사용자 제공 메타데이터)를 적고, 화면 내 단서(시계·조명 변화)와 제공 메타데이터를 구분한다.\r\n- **단계 몽타주**: 과정의 선택 단계를 별도 컷으로 배열. 각 컷이 실제로 커버하는 단계와 그 사이에 생략된 단계를 적는다.\r\n- **의도적 생략(elision)**: 중간 과정을 보여주지 않고 생략 전 상태 → 생략 후 상태로 자른다. 생략 양쪽의 관찰 가능한 상태를 각각 적고, 생략으로 생긴 결과가 다음 컷에서 유지돼야 하면 그 유지 조건(다시 리셋되는 조건 포함)을 인계한다.\r\n\r\n실제 경과시간·촬영 구간·간격·공백은 확인 가능한 근거가 있을 때만 적고 없으면 `미확인`으로 둔다. 원본 길이와 출력 길이의 비율(예: \"4시간 / 8초\")만으로 실제 playback_rate·촬영 간격·획득 방식을 확정하지 않는다 — 그 비율이 촬영 샘플링·편집 배속·구간 선택 중 무엇의 결과인지 구분할 수 없기 때문이다. 획득 방식이 미확인이면 최종 출력 구간과 생략 전후 상태만 기록하고 방식별 근거는 비워 둔다.\r\n\r\n상태가 바뀌는 압축·생략(재료가 익음, 액체가 퍼짐, 조립이 진행됨)에는 생략 전 상태 → 생략 후 상태와 후속 유지 조건을 [상태·인과·연속성 인계](26-state-causality-continuity.md)의 선택 슬롯으로 넘긴다. 시간 압축이 없는 실시간 편집에는 이 절차를 적용하지 않는다.\r\n\r\n\r\n## 실행 가능한 편집·사운드 큐\r\n\r\n편집 표는 source 구간과 최종 타임라인 구간을 별도로 기록한다. 배속 샷은 `playback_rate`와 원본 구간을 함께 두며, 전환 중첩은 `transition`과 실제 길이로 표기한다. 출처 타임라인을 모르면 정밀한 원본 in/out을 추정하지 않는다. 원본 영상에 접근할 수 없고 사용자가 가상 배분을 요청하지 않았다면 샷별 최종 타임코드·길이를 만들지 말고 비트 순서와 역할만 제안한다. 명시적으로 가상 배분을 요청하면 `proposal / 비실행용`임을 표시하고 측정된 EDL과 분리한다.\r\n\r\n편집·큐 ID는 `project.json`과 실제 에셋 원장에서 이어받는다. 출처에 없는 shot_id/sound_id나 임의 JSON 계약을 만들어 실행 가능한 산출물처럼 제시하지 않는다. 실제 타임라인이나 에셋이 아직 없으면 ID와 source 구간을 비워 두거나, 비정본 제안서에서만 역할명으로 부른다.\r\n\r\n`assets/sound-cues.csv`의 `sound_id`는 `project.json`의 `audio_cues[].id`와 같게 쓴다. `start_s/end_s`는 최종 타임라인의 시작 포함/끝 미포함, `source_in_s/source_out_s`는 음원 파일 구간의 시작 포함/끝 미포함 초다. 샷 간 음악처럼 시퀀스 전체에 걸친 큐는 `shot_id`를 비워 둔다. 추가 실행 메타데이터는 버전이 있는 편집 산출물에 기록하고 `project.json`에서는 artifact/asset ID로 연결한다.\r\n\r\n각 큐에는 레이어, 파일, 적용 gain(dB), fade 길이, 믹스 자동화 메모, 동기 기준점/오프셋, 권리 상태를 연결한다. `sync_offset_s`는 실제 소리 사건 시각에서 화면 기준점 시각을 뺀 값이며, 음향이 먼저면 음수다. 자동화는 `mix_note`에 구간과 목표를 적는다. 단일 혼합 참조 음원은 `mixed_reference` 레이어로 기록하고, 없는 stem을 가정하지 않는다. 권리 상태는 `unknown`, `user_asserted`, `evidence_recorded`, `restricted` 중 실제 근거에 맞춰 쓰고, 증거 위치나 제한은 `mix_note`에 둔다. 표기만으로 권리 허가나 게시 승인을 의미하지 않는다.\r\n\r\n제품 공개·접촉·충격·전환을 음악에 맞출 때는 기준점을 `action_peak`, `reveal`, `cut` 등으로 이름 붙이고 기준 타임코드와 실제 오프셋을 측정한다. 허용 오차는 브리프나 승인된 검수 기준에서 가져오며 보편적인 임의 수치를 적용하지 않는다. 권리 미확인 음원은 검토본에 사용하더라도 상태와 게시 제한을 표시한다.\r\n\r\n비트 기반 그래픽·몽타주에서는 승인된 최종 오디오 마스터의 실제 박/다운비트/드롭 시각을 기준으로 삼고, 해당 파일·버전과 측정 근거를 편집 아티팩트에 연결한다. 초 단위 사건 시각은 타임라인 프레임레이트의 절대 프레임 경계로 변환하며, 반올림한 박 간격을 반복 누적해 드리프트를 만들지 않는다. 마스터나 프레임레이트가 바뀌면 종속 컷·그래픽 타이밍을 다시 계산하고 실시간 재생으로 확인한다. 박 기반 편집이 브리프 요구가 아니면 이 절차를 강제하지 않는다.\r\n\r\n동적 편집 검수는 전체 영상을 실시간으로 소리와 함께 재생하고, 필요한 경우 무음 화면·오디오 단독·전환 경계 프레임을 추가 확인한다. 표본 프레임만 확인했으면 전체 리듬이나 청취 품질을 통과로 판정하지 않는다.\r\n\r\n편집 명세는 실행기에서 해석 가능한 타임라인과 음원 계층을 제공해야 한다. 실제 편집은 별도 요청·승인과 사용 가능한 실행기 확인 뒤 수행하며, 계획표·스크립트 작성만으로 렌더 완료를 주장하지 않는다.\r\n\r\n## 오디오 의도와 실행 경로\r\n\r\n오디오 작업 전에 요청을 분류한다: 무음(`no_audio`) · 대사 없음(`no_dialogue`) · 효과음만 · 음악 제외 · 단일 혼합 참조. `project.json`의 `audio_mode`와 `audio_cues` 레이어를 그대로 재사용하고 새 enum을 만들지 않는다. 세부 의도는 편집 산출물과 큐 레이어로 기록한다:\r\n\r\n- `no_audio` — 오디오 큐를 두지 않는다. 무음 요청에 음악·효과를 추가하지 않는다.\r\n- `no_dialogue` — 말만 없다. 음악·환경·효과 큐는 유지되므로 무음이나 음악 제외로 해석하지 않는다.\r\n- 효과음만(SFX-only) — 대사 유무에 따라 `dialogue`/`no_dialogue`로 기록하되 큐는 SFX 계열 레이어만 둔다. 음악이나 대사를 암묵적으로 추가하지 않고, 생성 결과에 음악·말이 섞여 나오면 실패로 기록한다.\r\n- 음악 제외 — 음악 레이어를 두지 않는다. 지시 문법은 실행자의 실제 지원 제어로 쓴다; 제어가 없는 endpoint에 지원되지 않는 파라미터나 존재하지 않는 stem을 발명하지 않는다.\r\n- 단일 혼합 참조 — `mixed_reference` 레이어 하나로 기록하고 대사/음악/효과 분리를 약속하지 않는다. 분리 stem은 실제 소스가 제공할 때만 그 레이어로 기록한다.\r\n\r\n요청한 제외·구성을 endpoint가 실제 지원하지 않으면 가짜 지시를 넣지 않는다. 대신 영상 생성과 음향을 분리해 조립하는 경로(별도 음성/효과음 패스, 편집 단계 합성)를 비용·승인 범위와 함께 별도 제안하고, 승인 없이 새 음향 작업·분리·과금을 시작하지 않는다. 사용자가 지정한 음향 실행자·소스·방식은 조용히 대체하지 않는다.\r\n\r\n실제 오디오 결과는 요청한 의도와 대조해 청취 검수한다. 듣지 않은 구간은 미검증으로 두고, 청취 확인 없이 구성(말 없음·음악 없음·분리)이 맞다고 보고하지 않는다.\r\n\r\n## 음악·효과음 소싱과 권리\r\n\r\n카탈로그 또는 사용자 제공 파일에서 후보를 고를 때 브리프의 기능·감정·길이·동기 기준점에 맞춰 비교하고 비교한 기준을 남긴다. 실제 길이와 필요한 구간은 파일을 보고 맞춘다.\r\n\r\n선택 항목마다 실제 출처/트랙·파일 ID와 버전, 권리 근거, 확인 시점·위치를 연결한다. 구독·다운로드·접근 가능 URL은 게시 허가가 아니며, 플랜/프로젝트·채널·지역·기간 제한은 해당하는 것만 `mix_note`나 연결된 편집 산출물에 기록한다(`sound-cues.csv` 필드를 늘리지 않는다). `rights_status`는 실제 근거에 맞춰 쓰고 출처 URL만으로 상업적 사용을 통과시키지 않는다. 권리가 제한되거나 불명이면 게시 가능으로 주장하지 않고, 차단되는 범위와 준비 가능한 범위를 나눠 보고한다. 구매·구독 가입·게시는 자동으로 하지 않고 사용자 승인을 받는다.\r\n\r\n선택한 음원은 실제로 들어서 후보 비교가 실제 소리와 맞는지 확인한 뒤 `source_in_s/source_out_s`, fade, gain, `sync_anchor`/`sync_offset_s`를 측정해 기존 편집 표와 `sound-cues.csv` 필드에 맞춘다. 측정하지 않은 구간·동기는 추정으로 표시한다.\r\n\r\n## 후반작업 단계 추적 (영화 라이프사이클 요청 시)\r\n\r\n영화·단편 요청으로 [28](28-film-production-lifecycle.md)의 05 Post-production이 배정됐을 때, 선택된 후반 단계만 단계 표로 추적한다. `assets/film-postproduction-template.md`를 사용하고, 이 표는 `project.json` artifact/dependency/version과 `asset_registry`를 참조하는 인계 문서지 새 원장이 아니다.\r\n\r\n**단계 목록** — 각 단계는 개별 artifact로 버전을 단다: 인제스트/싱크 → 어셈블리 컷 → 러프 컷 → 파인 컷 → 픽처 락 → VFX → ADR → Foley → 사운드 디자인 → 스코어/음악 편집 →
