# Blender adaptation

The upstream project supplies browser/Three.js and media-processing techniques, not `bpy` scripts, a Blender add-on or a Blender renderer. This reference translates reusable craft; it does not pretend the JavaScript runs inside Blender. Actual native work is authored for the installed Blender version using its supported scene/material/animation/export APIs.

## Apply only assigned techniques

| Upstream craft | Native Blender application | Boundary |
|---|---|---|
| `threejs-scene`: measured proportions and box blockout | Record metres/scale and dimension sources; build simple meshes first and inspect locked camera views before detailing | Keep estimated measurements labeled; retain the supplied spatial spec |
| Profile sweeps, lathes, repeated geometry | Use curves/bevel profiles, mesh/Screw-style revolutions and linked data or instances as appropriate; seed procedural variation | Inspect normals, intersections and applied scale; do not port Three.js XZ-ground/Y-up coordinates directly into Blender Z-up |
| Coherent sky, key light, environment, exposure and emissives | Keep light direction, world/reflections and color management coherent across assigned looks; tune materials in the selected engine | Three.js ACES, candela, shadow bias, GTAO/bloom and shader patches are not one-to-one Blender controls; no numeric copy or identical-look claim |
| Vertex animation and matching shadows | Prefer native geometry/rig/deformation so rendered shadow geometry follows motion; test affected frames | GLSL `onBeforeCompile` is browser code, not a Blender node or modifier |
| `exploded-view`: part hierarchy and staged motion | Named part collections/objects, preserved assembled transforms, deliberate explode vectors and ordered keyframes; separate shell materials; composed labels | Readable disassembly is not a mechanical collision/assembly proof; physically exact internals require supplied evidence |
| X-ray and section presentation | Choose a native transparency/holdout/compositing or geometric cut method supported by the actual engine and required output | A browser clipping plane may leave uncapped surfaces; inspect sections and backsides rather than promising solid cut geometry |
| `scroll-film`: beats, holds and aspect variants | Render the approved timeline to a frame sequence; hold on information beats; render/check requested portrait cameras when crop fails | Scroll interaction is a separate web handoff, not part of a `.blend` deliverable |
| `alpha-cutout`: transparency and edge QA | Prefer native RGBA render output when the Blender scene exists; verify alpha convention, edge colors, shadows and composites on light/dark/brand backgrounds | Key only an existing opaque plate when needed; do not render chroma then remove it unnecessarily. Stacked-alpha MP4 is a web transport, not a native RGBA master |
| `cursor-rig`: consistent pose grid and body | If assigned, render fixed-camera head yaw/pitch poses from the same native character and body, with IDs/angles/crops for web handoff | The upstream builder consumes its documented clips and pixel box, not a Blender armature or arbitrary pose-grid directory; full character rigging is not provided by the previs adapter |
| `motion-assets`: loops and source preservation | Check start/end pose, camera, lighting and motion across the wrap; run loop diagnostics only on requested rendered clips | A numeric seam score or crossfade does not prove smooth velocity or preserve every detail |
| `frame-capture` / `site-check` | Use only for an explicitly requested web presentation of exports or rendered clips | Blender renders use native frames/fps and actual playback; browser virtual-clock recording is not Blender rendering or performance measurement |

## Native work procedure

For native workflows not derived from browser tools, use the assigned section of [native Blender workflows](native-blender-workflows.md). Official source mechanics and creator demonstrations are distinguished in its [source register](blender-source-register.md); older tutorial UI, numeric recipes and third-party add-ons are not current runtime guarantees.

1. Preserve the existing `.blend` and source assets; use a new working copy or isolated Blender process and a fresh output path. Record Blender version, source IDs, unit scale, engine, color management, resolution, fps/frame range and requested exports before execution.
2. Read only the assigned craft reference after this adaptation. Use supplied dimensions, assembly facts and locked camera/continuity. For actual scene-specific camera/path/contact feasibility, the coordinator assigns `camera-spatial-design` and `blender-previsualization`; reuse their `camera-spatial-1.0` spec and evidence. Do not broaden that proxy adapter into a beauty renderer, rigging system or physics simulator.
3. Build and inspect blockout from front/side/three-quarter and the delivery cameras, then detail only what those views need. For an exploded assembly, inspect assembled, intermediate and fully exploded states plus each requested cut/x-ray state. Fix proportion, grounding, occlusion and label collisions before polishing.
4. Make a small native preview before the assigned final render/export. Reopen the saved `.blend`; inspect actual requested frames, alpha composites and the loop boundary when applicable. For animation, inspect motion through transitions, not just endpoints. Check render time/memory for native output separately from browser fps/draw calls.
5. For a requested GLB/web handoff, verify exporter availability and actual supported materials/animations for the installed Blender version. Preserve named parts and transforms, map axes/units explicitly, and reimport/open the export to check scale, orientation, materials and animation. Add web QA only if the owner assigned a web deliverable.
6. Return actual `.blend`, renders/sequences/exports, inspected frame/view IDs, settings, problems and unsupported effects to the coordinator. Native authoring, rendered quality, spatial feasibility, web compatibility and user acceptance remain distinct evidence claims.
